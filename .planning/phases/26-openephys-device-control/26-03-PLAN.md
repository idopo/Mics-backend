<objective>
The early rig checkpoint: confirm the Open Ephys REST surface against the lab's actual instance
BEFORE any path-construction code is finalized.

Purpose: every OE field name in `26-RESEARCH.md` came from official documentation fetched over the
web, never probed against this lab's GUI version. Two things are outright undocumented — the literal
`Record Node <id>` directory-name separator, and whether `experiment_number`/`recording_number`
reset when the target directory changes. Writing `compose_resolved_path` before knowing them would
persist a path the data is not actually at, which is the exact failure EPHYS-03 exists to prevent.
This checkpoint is deliberately in wave 1, ahead of implementation, and NOT folded into the phase's
end-of-phase rig session — waiting would invert the dependency.

Output: a small curl probe script, and a written ground-truth record plans 26-06/26-07/26-10 read.

**This does not block the generic layer.** Plans 26-04 (path resolver) and 26-05 (artifact table +
API) contain zero Open Ephys knowledge by design and run in parallel with this checkpoint.
</objective>

  <name>Task 1: Write the curl probe script</name>
  <files>scripts/oe_rest_probe.sh</files>
  <action>
    Create `scripts/oe_rest_probe.sh` — a small, dependency-free bash script the USER runs from any
    machine that can reach the Open Ephys box. It takes the OE host as `$1` and the port as an
    optional `$2` (default 37497) and prints raw responses with clear section headers.

    Sections, in this order:
    1. `GET /api/status` — record the exact JSON. Which key carries the mode? What are the literal
       mode strings?
    2. `GET /api/recording` — record the exact JSON. Confirm which of `parent_directory`,
       `base_text`, `prepend_text`, `append_text`, `default_record_engine` exist, and confirm the
       `record_nodes` array with `node_id` / `experiment_number` / `recording_number`.
    3. `GET /api/processors` — record the signal chain, to know how many Record Nodes exist (the
       resolved path depends on which node writes).
    4. A commented-out `PUT /api/recording` with a probe `parent_directory` and `base_text`, plus a
       commented-out `PUT /api/status {"mode":"RECORD"}` and its `{"mode":"IDLE"}` partner. These
       are commented BY DEFAULT — the script must never start a recording just by being run. The
       user uncomments them deliberately.
    5. A commented-out `PUT /api/message {"text":"mics_probe"}`.

    Print, at the end, the exact list of questions the user must answer (mirroring the checkpoint
    below) so the script is self-documenting when someone reruns it in six months.

    Make it `chmod +x`. Do NOT run it — the agent has no route to the OE box and must not attempt
    one.
  </action>
