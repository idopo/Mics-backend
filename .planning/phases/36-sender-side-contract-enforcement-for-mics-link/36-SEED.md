# Phase 36 seed — evidence gathered 2026-08-30

Captured from the Phase 34 rig session. **Not a plan.** Run `/gsd-discuss-phase 36` before
planning; the scope questions at the bottom are genuinely open.

## The problem, stated precisely

The contract IS enforced. It is enforced on ONE side, after the fact, and the verdict is thrown
away.

| | knows the contract | detects violations | tells anyone |
|---|---|---|---|
| Sender (SDK) | no | no | — |
| Wire | — | — | no channel exists |
| Pi | **yes** | **yes** | its own journal only |

A sender publishing `left_paw_X` (capital X) for six hours reports
`sent=21600 dropped=0 send_failed=0` — a perfectly clean run — while the Pi's `unknown_name`
counter climbs to 21600 in a log nobody reads.

## What already exists (do not rebuild these)

**The contract is already machine-readable.** `@signal` / `@event` / `@command` decorators are
extracted by `api/extlink_ast.py::extract_extlink_metadata` into
`hardware_lib_versions.ast_metadata["extlink"]`. Verified shape, lib 177 v2 (version_id 137):

```json
{"ExtlinkDemo": {
  "signals": {
    "left_paw_x":  {"dtype":"float","default":0.0,"stale_policy":"return_default","stale_after_ms":200},
    "right_paw_x": {"dtype":"float","default":0.0,"stale_policy":"hold_last","stale_after_ms":200}},
  "events":   {"object_detected": {"payload": {"object":"str","confidence":"float"}}},
  "commands": {"ping": {"args": [], "returns": "bool"}},
  "decoder":  null}}
```

**It is already served.** `api/routers/hardware_libs.py` puts the `extlink` block on its result.

**It already has one consumer.** The FDA editor's view-operand picker (EXTLINK-19) reads it via
`api/extlink_keys.py::extlink_signals_from_ast`. **That helper narrows to `[{"name","dtype"}]` and
DISCARDS `stale_after_ms`, `stale_policy` and `default`** — precisely the fields a sender needs.
Widening it (or adding a sibling) is likely the smallest useful change.

**The Pi already counts violations.** `external_hardware_wire.py` increments
`stats.unknown_name`, `stats.type_mismatch`, `stats.malformed`; `external_hardware_ingress.py::
log_decode_issues` logs them rate-limited (>=1s per kind). `_decode_stats` is constructed in
`external_hardware.py:149` and **never leaves the Pi** — grep confirms no NAK or error reply on
the SIG path; `ack_frame` serves only the Pi->sender CMD direction.

## Why NOT protobuf / an IDL

Rejected on evidence, not taste:

1. **It would be a second source of truth.** The `@signal` decorators are what the Pi actually
   enforces. A generated-or-hand-written IDL alongside them can drift and lie.
2. **It would not have caught the bug that actually cost us two rig runs.** Run 581 sent a
   correctly-named, correctly-typed `float` — and every FDA read still saw the default, because
   `left_paw_x` declares `stale_after_ms=200` and the sender published every 2000ms. No type
   system catches "your publish rate is 10x slower than this signal's staleness window."
   `stale_after_ms` is a contract field; protobuf has no place to put it.

## Failure classes and whether a contract-fetch catches them

| Failure | Caught by contract? | Today |
|---|---|---|
| Signal name typo | yes — not in `signals`, fail at `connect()`/first send, list valid names | silent, `unknown_name` climbs |
| Wrong dtype (bool into a float signal) | yes — declared `dtype` vs value's exact type | silent Pi-side drop, `type_mismatch` |
| **Publish rate > `stale_after_ms`** | **yes — the highest-value check** | silent; cost runs 581 + 582 |
| Event payload wrong keys/types | yes — `payload` map | silent |
| Unknown command name | yes — `commands` map | silent |
| **`source_id` mismatch** | **NO** — ROUTER identity, not schema. Only a Pi-side NAK fixes it. | silent, no NAK (EXTLINK-02) |
| Lib changes under a running sender | no — contract fetched once at connect | silent |

The last two are why the counter-surfacing option below is a complement, not an alternative.

## Two candidate directions (both, or either — this is the discussion)

**A. Fetch the contract at `connect()`.** Opt-in kwarg, e.g. `connect(..., contract=<url|path>)`.
Fails at the researcher's call site, at startup, before a frame is sent. Three tiers considered:
1. URL — fetch from the backend at connect.
2. File — `contract.json` generated by a CLI, shipped beside the script. This is the "contract
   file" the user asked about, but GENERATED from the decorators, never hand-written, so it
   cannot drift silently. Right answer for an air-gapped vision box.
3. Absent — today's behaviour (local scalar-type check only). Nothing breaks for non-adopters.

**B. Surface the Pi's existing counters.** `unknown_name` / `type_mismatch` / `malformed` are
already computed per frame and already thrown away. Pushing them up with existing telemetry makes
silent drops visible. Cheaper than A, catches drift A cannot, but only after the damage.

## Open questions for `/gsd-discuss-phase 36`

1. A, B, or both? A is the real fix; B is the safety net.
2. How opt-in must A be? The user's stated constraint: *"I don't want to force too much on user."*
   Hard-fail on violation, or warn-and-continue? Does `connect()` reach the network by default?
3. Which contract source is primary — URL or generated file? The DLC vision box may be
   air-gapped, which argues for the file being first-class rather than a fallback.
4. Does the sender need the module NAME to look up its block, or is `source_id` -> module
   resolvable server-side from `pilot_hardware_config`? (Row 33 carries `class_name` +
   `source_id`, so probably yes — worth confirming.)
5. Is the publish-rate check a `connect()`-time warning (compare declared `stale_after_ms` against
   a caller-declared intended rate) or a runtime observation (measure actual send spacing and warn
   once)? The runtime version needs no new API from the caller and is probably stronger.
6. Does `source_id` mismatch deserve its own fix here (a Pi-side NAK) or is that Phase 18
   substrate work? It is the single biggest time-sink per the SDK README, and no contract
   mechanism can reach it.
7. Does the SDK need to handle a contract it cannot fetch (offline, backend down) without
   degrading the researcher's run? Almost certainly yes — fail open, warn loudly.
