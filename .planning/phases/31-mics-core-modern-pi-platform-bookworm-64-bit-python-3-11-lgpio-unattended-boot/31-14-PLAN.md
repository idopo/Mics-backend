<objective>
Make the kernel-timestamp claim visible in the data.

Purpose: this is the change that turns the phase's central argument into something an analyst can
see in Elasticsearch. Today `dispatch_event()` (`Event_Dispatcher.py:77`) calls
`self.pi.get_current_tick()` **in the calling thread** — i.e. it stamps when *Python* runs, and
throws away the edge time the callback already carried. The sender thread then converts that tick
with `self.pi.ticks_to_timestamp()`, a **non-upstream Autopilot patch** to pigpio implementing
Cristian's algorithm: a mini-NTP round-trip estimate of the offset between the daemon's clock domain
and the host's.

Three failure modes, all worse under 24/7:
1. The tick is **32-bit microseconds** and wraps every **71.58 minutes** — ~20 times a day in
   continuous operation. Each wrap triggers a re-sync.
2. The offset is re-estimated **only** when `ticks < _last_synced_tick`. A system-clock **step**
   between wraps silently corrupts every timestamp until the next wrap.
3. The whole mapping is an estimate of a round trip, not a measurement.

After this plan: the timestamp is the kernel's, taken in hardirq context on `CLOCK_MONOTONIC` as
64-bit nanoseconds (wraps in ~584 years), and the wall-clock mapping is two vDSO reads of the same
kernel timekeeper — exact by construction, nothing to re-sync, nothing to go stale.

**Honest boundary, and it must be stated in the module docstring so the claim does not inflate:**
this makes each rig's *own* timing robust — inter-event intervals become immune to clock steps. It
does **not** synchronise a rig's clock to the backend's or to an ephys system. That needs chrony
slewing (plan 05), dual logging (this plan), and the TTL hardware pulse remaining ground truth for
cross-device alignment — which is Phase 28's territory, not this one.

Output: a dual-timebase dispatcher, a deliberate single-key manifest update, and tests that prove a
clock step does not move an interval.
</objective>

edge timestamp is worse than falling back to a software stamp, because it is indistinguishable

property the test asserts: an injected edge timestamp reaches the payload **unchanged**.

<verified_design>
**The dual-timebase contract**, to be written into the module docstring AND carried into the ES
mapping:

| Field | Clock | Use for | Never use for |
|---|---|---|---|
| `t_mono_ns` | `CLOCK_MONOTONIC`, kernel, at interrupt | **all** interval / latency / rate analysis within a session | joining across machines |
| `t_utc` | derived (`t_mono_ns + offset`) | display, joining to backend/session records | interval analysis across a clock step |

**Offset computed per event, not cached:**
```python
offset_ns = time.clock_gettime_ns(time.CLOCK_REALTIME) - time.clock_gettime_ns(time.CLOCK_MONOTONIC)
```
Two vDSO reads, tens of nanoseconds, and it is **the only form that stays correct across a wall-clock
step**: each event's UTC derives from the REALTIME<->MONOTONIC relation that held when it was
recorded. A cached offset is exactly the pigpio failure mode, reimplemented.

**A subtlety that looks like a contradiction and must be written down:** `CLOCK_MONOTONIC` on Linux
*is* affected by NTP/adjtime frequency adjustments — it is slewed, but never stepped and never runs
backwards. For this rig that is the desirable property: chrony's frequency discipline improves the
long-run rate accuracy of inter-event intervals, while the absence of steps is what makes 24/7 safe.
**Do not "fix" this by switching to `CLOCK_MONOTONIC_RAW`** — and lgpio could not ask the kernel for
it anyway.

**Fallback policy.** Not every dispatch has an edge timestamp: software-originated events
(state entries, trial counters) have no interrupt. `dispatch_event` must accept an optional
`ts_mono_ns` and fall back to `time.clock_gettime_ns(CLOCK_MONOTONIC)` **only when none is given**,
recording which it used in a field so an analyst can tell a hardware-stamped event from a
software-stamped one. That distinction is worth a field; conflating them is how a latency
measurement quietly becomes a scheduler measurement.

`_dropped_no_clock` keeps its name but changes meaning: reading `CLOCK_MONOTONIC` cannot realistically
fail, so the counter now guards the fallback path rather than an IPC round trip. Say so in the
summary and in a code comment — a counter whose meaning silently changed is worse than a renamed one.
</verified_design>
