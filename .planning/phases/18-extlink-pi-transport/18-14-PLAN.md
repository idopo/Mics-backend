<objective>
Make an ExternalHardware signal pickable in the FDA editor's view-operand selectors — the
condition builder and the action-argument input — so ROADMAP success criterion 1 is authorable
through the UI instead of only by PUTing `fda_json`.

Purpose: `buildViewOptions(hwNames, flagNames, detectors)` builds its Hardware group from
`toolkit.semantic_hardware` keys and its channel groups from detector configs
(`device_name + index`). Dotted extlink keys like `dlc_cam1.left_paw_x` are enumerated nowhere,
and there is no escape hatch — `ConditionBuilder.tsx:95` renders the free-text `view key` input
ONLY when `viewGroups.length === 0`, so any toolkit with hardware is select-only.
`ConditionBuilder.tsx:76` already names this exact case in prose: an ExternalHardware signal
"must survive a round trip". It survives. It cannot be CREATED. This plan is the create half.
Output: a fourth parameter on `buildViewOptions`, two consumers updated, tests.
</objective>

<design_decision>
## The operand shape: RESOLVED KEY, not a ref. Rationale, because this is a real tension.

DVK-11's rule is "never store a resolved key that is pilot-specific — store a ref". That is why a
detector channel is stored as `{"view_detector": {"ref": "MPR121", "channel": 2}}` and never as
`"LICKER2"`. An extlink view key is `f"{source_id}.{signal}"`, and its `source_id` half comes from
per-pilot `pilot_hardware_config.config` — structurally the same hazard. DVK-11's logic genuinely
argues for a ref-shaped operand here. It is nonetheless **rejected**, for four reasons:

1. **EXTLINK-05 forbids the call sites a ref shape needs.** "FDA reads via existing
   `view.get_value(...)` with zero new call sites" is a locked requirement, and the FDA JSON is
   dispatched to the Pi as-is. A `{"view_extlink": {...}}` operand would need a new resolver branch
   in `mics_task._build_transition_lambda` **and** a second one in `_resolve_arg` (which is how an
   action argument reads a view value). **No Phase 18 plan touches either function** — 18-11 adds
   only `init_hardware` and the `load_fda_from_json` pre-state — and those plans are frozen after a
   six-iteration checker verdict. A ref shape silently forces a Pi change this phase has no plan
   for and no rig slot to prove.

2. **A resolved extlink key is not a prediction; it is the literal Tracker name.** A detector key
   is *computed* on the Pi from a per-pilot `device_name` template, so storing it stores a guess.
   `f"{source_id}.{signal}"` is exactly the string `.bind()` registers with the View
   (18-CONTEXT § Tracker naming) and exactly the string `view.get_value` takes. Storing it stores
   the truth.

3. **The residual risk is answered where this project already answers cross-pilot hazards.**
   Plan 18-13 adds the target pilot's extlink keys to `preflight_validate`'s `valid_keys`, so an
   FDA authored against pilot A's `source_id` and run on pilot B surfaces as the EXISTING
   `view_key_unresolved` issue — before the animal is in the box. That is Phase 13's
   preflight-as-gate pattern, with no new issue kind and no new machinery. DVK-11 chose to make
   the mismatch *resolve automatically*; here it is made *visible* instead.

4. **Nothing in the encode/decode layer changes.** `optionValueToViewOperand` already returns
   `{view: value}` for any value that is not an offered detector token, and
   `viewOperandToOptionValue` already returns `op.view`. `isKnownViewOption` works unmodified. A
   ref shape would instead need a new branch in both, plus `api/fda_validation.py`
   (`validate_condition_operands`), plus `api/detector_keys_scan.py` (`scan_fda_view_keys`) — four
   more surfaces, two of them in files frozen plans already edit.

**Cost, accepted and recorded:** an FDA authored for pilot A does not silently work on pilot B
whose module uses a different `source_id` — it is flagged at preflight and must be re-authored or
the config aligned. **Mitigations that are part of this plan, not aspirations:** each option's
`title` states plainly that the stored key is pilot-specific, and 18-13's cross-pilot `conflict`
flag renders as the same `warning` line the detector groups already use.

**If a future phase wants the ref shape**, the migration is purely additive (a new operand kind, a
Pi resolver, a `scan_fda_view_keys` branch) and nothing here blocks it. Say so in the SUMMARY.
</design_decision>
