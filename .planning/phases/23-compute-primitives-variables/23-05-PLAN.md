<objective>
Unify version resolution onto one chain and apply it at every site that decides which
`source_code` is written, exec'd, or introspected — then finally activate the dormant
`test_import` round-trip.

Purpose: today the chain is pin → `active_version_id`; `stable_version_id` is NEVER consulted,
and an unvalidated active version is dropped with only a log warning. Research found the fix is
needed in TWO places, not the one CONTEXT named: `orchestrator_station._send_hardware_libs_if_needed`
(what gets WRITTEN to disk) and `api/routers/toolkit_dispatch.get_dispatch_spec` (what actually
gets EXEC'D — the more consequential site, and the only one that matters for the
backend-authored/sourceless toolkits that are now the only shape being developed). A third
site, `hw_introspect.toolkit_hw_capabilities`, uses `active_version_id` for AST introspection.
Output: one resolver, three consumers, and `HARDWARE_LIB_TEST_RESULT` alive for the first time.

**DESIGN DECISION requiring your attention — read before implementing.** CONTEXT lists the
chain as pin → toolkit default → stable → *nothing deployable*. Implemented literally, any lib
with no promoted stable version stops dispatching entirely, which would break every existing
backend-authored toolkit on the rig (modules 7/8, MPR121 and TOUCH_INT, and every task def
using them). This plan therefore implements a FOURTH rung before giving up: the active version,
**only if its own `state` is `beta` or `stable`**. That is strictly better than today (it adds
the missing stable rung and turns the silent drop into a surfaced issue) and introduces zero
regression. The 5th outcome — nothing at all — becomes a preflight issue, per CMP-17(4).
State this deviation prominently in the summary.
</objective>
