<what_the_soak_must_actually_watch>
The obvious soak criterion is wrong for this substrate, and following it would produce a false pass.

The Pi has **no ingress queue**. `_recv_buffer = collections.deque(maxlen=256)` is append-only and
never read by anything, and `bind_socket` wires `ZMQStream(...).on_recv(owner._on_recv)`, so the whole
ingress path - identity check, decode, `tracker.set()`, event dispatch - runs **synchronously on the
Tornado IOLoop thread** that also serves every other module's ingress, the pilot's own orchestrator
DEALER, and the STOP channel. Three consequences the checkpoint must carry (D-21):

1. The high-rate failure mode is **IOLoop starvation degrading FDA transition timing and STOP
   responsiveness**, not a queue overflow. So the soak watches transition timing and how long STOP
   takes to be honoured - not merely a drop counter.
2. A frame lost at ZMQ's socket high-water mark is counted **nowhere** on the Pi; `DecodeStats` only
   counts frames that arrived. So the sender's own `stats.dropped` is the only end-to-end drop
   accounting that exists, and DLC-04's "no silent drops" is **not satisfiable Pi-side as built**.
   Record that as a permanent limitation - do not imply a Pi-side drop visibility that does not exist.
3. Every accepted signal calls a tracker carrying `@log_action` and emits one CONTINUOUS
   Elasticsearch event: a **1:1 amplification**. So the observed messages per second IS the
   Elasticsearch load per pilot, and Elasticsearch keeping up is a soak criterion in its own right.
</what_the_soak_must_actually_watch>
