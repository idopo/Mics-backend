```ts
export interface XY { x: number; y: number }

/**
 * One transition's canvas geometry, derived purely from the transition list.
 * `index` is the position in `fdaJson.transitions` — the same integer that makes the
 * react-flow edge id `e-${index}`. It is the edge's identity and must be preserved.
 */
export type EdgeKind = 'pair' | 'self' | 'back'

export interface EdgeGeometry {
  index: number
  kind: EdgeKind
  /** How many transitions share this edge's group (see the grouping rule below). */
  groupSize: number
  /** 0-based position within the group, ordered by `index`. */
  memberIndex: number
  /**
   * Perpendicular bow in px, expressed in THIS edge's OWN frame — i.e. along the normal of
   * (target - source). Already sign-flipped for `reversed` edges. For self-loops this is the
   * loop's extra radius, always >= 0. For back-edges this is the clearance control offset.
   */
  offset: number
  /** True when `from > to` lexicographically: the edge runs against canonical pair order. */
  reversed: boolean
  /** Fraction along this edge's own curve (0..1) where its label rides. */
  labelT: number
  /** Columns spanned leftward. 0 for every non-`back` edge; always >= 2 for a `back` edge. */
  backSpan: number
}

/**
 * Group transitions and assign each member an offset and label position.
 *
 * `ranks` is `columnRanks(...)` from `fdaLayout.mts` — the SAME BFS the layout uses, passed in
 * rather than recomputed (see the back-edge section below for why). It is optional: without it
 * no edge is ever classified `back`, so every Task-1 test keeps passing untouched.
 */
export function assignEdgeGeometry(
  transitions: ReadonlyArray<{ from: string; to: string }>,
  ranks?: Readonly<Record<string, number>>,
): EdgeGeometry[]

/** Control point of the quadratic Bezier that bows `offset` px off the a→b chord. */
export function quadraticControlPoint(a: XY, b: XY, offset: number): XY

/** SVG path string `M ax,ay Q cx,cy bx,by`. */
export function quadraticPath(a: XY, c: XY, b: XY): string

/** Point on the quadratic Bezier at parameter t (t=0 → a, t=1 → b). */
export function pointOnQuadratic(a: XY, c: XY, b: XY, t: number): XY

/** Loop path anchored between a node's source handle and its target handle. */
export function selfLoopPath(source: XY, target: XY, extraRadius: number): { path: string; labelPoint: XY }

/** Point on the cubic Bezier a→c1→c2→b at parameter t. */
export function pointOnCubic(a: XY, c1: XY, c2: XY, b: XY, t: number): XY

/**
 * Return-path curve for a back-edge: leaves the source, drops `controlOffset` below the chord,
 * runs left PAST the target, and re-enters the target's left handle heading rightward.
 */
export function backEdgePath(a: XY, b: XY, controlOffset: number): { path: string; labelPoint: XY }
```

<!-- THE TRAP. Read this before writing assignEdgeGeometry. -->

`TransitionEdge` only ever knows its own `source`/`target` endpoints, so it can only bow along the
normal of its own direction vector. For `A→B` that normal points one physical way; for `B→A` it
points the opposite physical way. Naively handing the two members of a pair `-S` and `+S` therefore
puts BOTH curves on the same physical side — the hourglass, unfixed.

The rule:
1. Canonicalise each edge's pair to `[min(from,to), max(from,to)]` lexicographically. `reversed`
   is true when `from > to`.
2. Within a group of size `n`, member `k` (ordered by `index`) gets a CANONICAL offset
   `(k - (n - 1) / 2) * SPACING`.
3. The emitted `offset` is `reversed ? -canonical : canonical`.

Sanity check the implementation must reproduce:
- `[A→B, B→A]` → canonical `-S/2`, `+S/2`; emitted `offset` **-S/2 for both** (each bows to its own
  left by the same amount ⇒ they bow to opposite physical sides). A test asserting the two emitted
  offsets are *different* is the wrong test and will enshrine the bug.
- `[A→B, A→B]` → neither reversed → emitted `-S/2`, `+S/2`, distinct.
- Physical offset (what a test should compare for distinctness across a mixed group) is
  `reversed ? -offset : offset`.

<!-- Self-loops -->
`StateNode` exposes one target handle on the LEFT (rendered only when `!isInitial`) and one source
handle on the RIGHT. For `A→A`, react-flow hands the edge `source` = A's right handle and `target`
= A's left handle, so a self-loop must leave right, arc above the node, and return to the left.
`selfLoopPath` owns that shape. Self-loops group by node name, not by pair, and their `offset`
widens the arc per `memberIndex`. `reversed` is always false for a self-loop.

<!-- BACK-EDGE ROUTING (CANVAS-13). Added 2026-08-05 after real data showed it is not an edge case. -->

Definition 186, verified against the live DB: states `init, rand, play_led, trial_onset`, initial
`init`, transitions `init→trial_onset`, `trial_onset→play_led`, `play_led→rand`,
`rand→trial_onset`, `rand→play_led`. `columnRanks` gives `{init:0, trial_onset:1, play_led:2,
rand:3}`, so:

```
[init] ──▶ [trial_onset] ──▶ [play_led] ⇄ [rand]
              ▲                              │
              └──────────────────────────────┘   rand → trial_onset: spans 2 columns, UNPAIRED
```

`rand→trial_onset` runs straight through `play_led`, and pair grouping can never help it: there is
no `trial_onset→rand`, so it is a group of one and its offset is 0.

**Classification is by graph column, NOT by live x-coordinates.** The obvious alternative —
`targetX < sourceX` inside the edge component — was considered and rejected for three reasons:
1. It flips mid-drag. Dragging a node past another would re-route unrelated edges under the cursor.
2. It is not unit-testable from a transition list, so the routing decision would fall outside the
   `.mts` layer the whole phase's verification strategy rests on.
3. Magnitude needs "columns spanned", which has no positional equivalent without reintroducing
   obstacle detection — explicitly deferred in `29-CONTEXT.md`.

Consequence, stated honestly: after a user hand-drags nodes, a "back-edge" may no longer be the
visually leftward one. That is accepted — `29-CONTEXT.md` already defers routing around arbitrary
geometry after manual drags.

**Rules:**
- `backSpan = ranks[from] - ranks[to]`, computed only when BOTH endpoints are ranked.
- `from === to` → `self`, checked FIRST.
- `backSpan >= 2` → `back`. `backSpan === 1` → `pair` (adjacent, nothing to clear — this boundary
  is locked by CANVAS-13). `backSpan <= 0` → `pair`. Either endpoint unranked → `pair`, always.
  (Unranked means unreachable, and CANVAS-14 packs those into a 2-D block where a single column
  index is meaningless.)
- **Precedence over CANVAS-01: partition before grouping.** `back` edges form their own groups,
  keyed on the unordered pair, SEPARATE from any `pair` edges between the same two nodes. This is
  what makes the required 186 assertion true by construction: `play_led ⇄ rand` (both `backSpan`
  0 and 1 → both `pair`) group together and keep byte-identical offsets, while `rand→trial_onset`
  is alone in a `back` group. Never apply both treatments to one edge.
- Back-edges do NOT use the canonical/sign-flip rule. Every back-edge runs right-to-left, so a
  single consistent side is achievable directly.
- **Side: BELOW the chord, always**, so a reader learns "under the row = return path". Express the
  requirement physically, not as a sign — the normal convention is the executor's choice. The test
  asserts the curve's apex has a LARGER screen y than the chord midpoint.
- Magnitude: `offset = BACK_EDGE_BASE + (backSpan - 1) * BACK_EDGE_PER_COLUMN + memberIndex * BACK_EDGE_MEMBER_STEP`.

**⚠ The control offset is not the clearance.** For the cubic `backEdgePath` uses, with both control
points `controlOffset` below the chord, the apex at t=0.5 sits `0.75 * controlOffset` below it
(`(a + 3c1 + 3c2 + b) / 8`). A `StateNode` is `minWidth: 180px` and about 70px tall, and the
handles sit at its vertical centre, so a back-edge must clear roughly 35px plus margin. Size
`BACK_EDGE_BASE` from the required CLEARANCE and assert the clearance — asserting the constant
would pass while the curve still clipped the node. Suggested start: `BACK_EDGE_BASE = 150`
(≈112px apex clearance), `BACK_EDGE_PER_COLUMN = 90`, `BACK_EDGE_MEMBER_STEP = 60`.

**Accepted residual:** the bow is a clearance heuristic, not obstacle avoidance. On a multi-row
graph a back-edge bowed below the top row can pass near the row beneath. General obstacle
avoidance stays deferred per `29-CONTEXT.md`; do not grow this into a router.
