<objective>
Build the instrument the phase is graded on, before there is anything to grade.

**Purpose changed with the scope on 2026-08-17.** This harness was built to compare pigpio against
lgpio. The lgpio migration was removed (`31-REVISED-SCOPE.md` §1); pigpio stays and the **clock
layer** is replaced. So the harness's job is now to **prove the clock fix**, in two halves:

1. **No timing regression (PLAT-24).** The acceptance gate is a paired before/after pulse-timing
   measurement on the same spare hardware — "before" = the tree as it stands, "after" = the tree
   with the clean-room clock module (plans C1-C3). Same program, same format, same board, same
   session. Building it now, before anything changes, is what makes the "before" arm obtainable.
2. **The defect itself (PLAT-25/29/30).** The phase's central claim is that every GPIO event
   timestamp currently jumps **backwards by 4294.97 s every 71.6 minutes**, because the patched
   client's callback thread converts ticks with no wrap detection (`pigpio.py:1206-1207`) and holds
   its offset by value (`:5264` -> `:1157`). That claim needs *evidence*, not arithmetic — hence
   `wrap_witness.py`, which records what the client actually hands a callback against a monotonic
   reference, and `analyse.py --check-wrap`, which is the same assertion in two modes: "the defect
   is present" (plan 08, before) and "there is not one backward jump" (C4, after).

**Ordering constraint that is easy to get wrong and expensive to discover late:** the "before"
capture is taken on the CURRENT rig image (Buster, **Python 3.7.3**, armhf). Both capture tools
must therefore run on Python 3.7 — no walrus operator, no `dict |` merge, no `list[str]` builtin
generics, no `dataclass(slots=)`, no `from __future__ import annotations` reliance for runtime
introspection. `analyse.py` has no such constraint: it runs on the dev machine only.

**The constraint is not local to the harness's own files.** `capture.py` imports the real
`Digital_Out`/`Solenoid`/`TTL`/`Pulse20Hz` from `autopilot/autopilot/hardware/gpio.py` — that is the
whole point of driving the production path — and plans **02 and 03 edit `gpio.py` before plan 08
takes the baseline on Buster**. An agent working on a Python 3.11/3.12 dev host can introduce a
walrus, a `match`, a `dict |` or a positional-only parameter into that import closure and every
dev-host test still passes; the failure surfaces on the Pi. So the gate covers the **transitive
in-repo import closure** of both entry points, not the files this plan happens to own.

**And `ast.parse(..., feature_version=(3,7))` alone is NOT sufficient — measured on this dev host,
do not re-derive it.** `feature_version` constrains the **grammar only**. It correctly REJECTS the
walrus, positional-only `/`, `match` and `except*`. It **ACCEPTS** all four of these, every one of
which raises `TypeError` on Buster's Python 3.7.3 at import or call time:

| Construct | Example | Why 3.7 dies |
|---|---|---|
| Builtin generics in annotations | `def f(x: list[str]) -> dict[str, int]:` | `TypeError: 'type' object is not subscriptable` — PEP 585 is 3.9 |
| PEP 604 unions | `def f(x: int \| None):` | `TypeError: unsupported operand type(s) for \|` — 3.10 |
| `dict` merge operator | `{'x': 1} \| {'y': 2}` | `TypeError: unsupported operand type(s) for \|` — 3.9 |
| `dataclass(slots=True)` | `@dataclass(slots=True)` | `TypeError: dataclass() got an unexpected keyword argument 'slots'` — 3.10 |

Builtin generics in an annotation are the single **most likely** thing an agent working in
`gpio.py` on a modern host writes, and they are the one this gate would otherwise wave through. So
the gate does explicit AST checks **in addition to** `feature_version`; see Task 1 step 3(e).

Output: a capture tool with before/after arms, a wrap-witness tool, an analyser that exits non-zero
when the phase fails, and committed synthetic captures with known answers so the analyser itself is
tested.

<instrument_design>
From `31-RESEARCH.md` `## Validation Architecture`. Reproduce the reasoning in
`tools/pulse_timing/README.md` — an instrument nobody can justify is an instrument nobody trusts.

**Method.** Jumper a spare output pin to a spare input pin. Claim the output normally; claim the
input for BOTH edges with **no glitch filter** (`set_glitch_filter` shifts every reported timestamp
by exactly the filter window, which would silently bias every number). Command a pulse through
**the production code path**, and read the resulting edge timestamps from the callback. Measured
width = `t_falling - t_rising`.

**Why this is right, not a compromise:** the measurement clock is `pigpiod`'s DMA sample tick,
taken by hardware every 5 µs, before any of our code runs. Both edges of a pulse ride the same
clock through the same path, so **sampling and delivery latency largely cancel in the width
difference** even though they do not cancel in the absolute timestamp. Width accuracy is therefore
much better than absolute-timestamp accuracy.

**Its honest limit, which must be in the README:** a loopback cannot distinguish "the output edge
was late" from "the input edge was sampled/reported late", and under heavy load the input-side
jitter contaminates the measurement. That is why plan 08 includes a ONE-TIME cross-check with an
external observer (a ~£10 24 MHz USB logic analyser via `sigrok-cli`, 41.7 ns resolution, or a
scope). After that calibration, the loopback is the routine instrument — a scope is worse for
routine use because it cannot produce n>=1000 automatically.

**Arms.** The comparison is **before vs after the clock refactor**, on the same board, not one GPIO
library vs another:

| Arm label | What it is | Captured in |
|---|---|---|
| `before` | the tree as it stands, on the pre-migration image | plan 08 |
| `after-other` | post-C3 tree, unit at default scheduling | plan C4 |
| `after-fifo10` | post-C3 tree, unit at `CPUSchedulingPolicy=fifo` / priority 10 | plan C4 |

The two `after` arms are what makes PLAT-17's `SCHED_FIFO` choice a measurement rather than a
belief. `--arm` is recorded in the header; the flag never changes the code path, only the label.

**Profiles** (`profiles.py`, one dict per profile so a capture is named, not hand-typed):

| Profile | Stimulus | Why |
|---|---|---|
| `valve` | 1000 x one-shot 200 ms pulse, 300 ms apart | The reward-volume path. 200 ms is the duration actually in prefs. |
| `valve_short` | 1000 x one-shot 40 ms pulse | The odour / air-puff duration. |
| `ttl` | 1000 x TTL pulse at the configured `pulse_width`/`interval` | Sync-pulse width. |
| `train` | 60 s continuous `Pulse20Hz` train | Period jitter AND cumulative drift. |
| `mixed` | `valve` + `train` concurrently | The daemon services all GPIOs from one sampler; contention is the realistic case and is invisible in single-profile runs. |

Each profile x two load conditions (**idle**; **loaded** = `stress-ng --cpu 4 --io 2 --vm 1
--vm-bytes 128M --timeout 120s` plus a live ZMQ session generating CONTINUOUS traffic) x three arms
= 30 captures, of which plan 08 takes the 10 `before` ones.

**Statistics** per profile x load x arm, n >= 1000 (`train` gives ~3600 at 62.5 Hz over 60 s):
`n`, `n_missing` (commanded vs observed edge pairs — **`n_missing > 0` is an automatic fail**),
`err_median` (systematic bias), `err_sd` (the jitter figure), `err_p99`, `err_max`, `err_iqr`
(reported alongside SD because the distribution is expected right-skewed), and for trains
`period_sd` and `rate_ppm` (slope of a least-squares fit of edge index vs edge time, as ppm
deviation from commanded — this is the cumulative-drift test). Report a table plus an ECDF of
`|err|` per arm. **Never report only the mean.**

**Gates.**
- **G1 (primary, comparative, needs no arbitrary numbers):** for every profile x load, each `after`
  arm's `err_p99` and `err_sd` must be **<= 1.25x** the `before` baseline captured on the same
  hardware, and `n_missing` must be 0 in every capture.
- **Absolute (secondary — they exist so a JOINTLY BAD baseline cannot pass by comparison alone),
  derived from the science not from what the hardware happens to do:**

| Profile | Statistic | Threshold | Derivation |
|---|---|---|---|
| `valve` (200 ms) | `err_p99` | <= 1.0 ms (0.5 %) | Reward-volume reproducibility; valve flow is roughly linear in open time and 0.5 % is well inside the solenoid's own volumetric variance. |
| `valve_short` (40 ms) | `err_p99` | <= 0.5 ms (1.25 %) | Same argument where relative error is larger. |
| `ttl` | `err_p99` | <= 200 us | The TTL is the cross-device alignment ground truth (Phase 28); its width need only be unambiguously detectable, but its EDGE is the alignment point. |
| `train` | `period_sd` | <= 200 us | ~1.2 % of a 16 ms period; below the temporal resolution of any downstream behavioural analysis. |
| `train` | `rate_ppm` | abs <= 100 ppm | Guards the drift-free property of the daemon's scheduling. A failure here means something is re-basing the schedule — a genuine bug. |

`31-RESEARCH.md` rates these thresholds MEDIUM confidence: they are proposed from the science, not
measured. **G1 is the gate that carries the weight.** Say so in the README.

**`--check-step` (PLAT-25):** given a capture taken across a forced clock step, assert
`t_mono_ns` strictly increasing with **no discontinuity** (the interval between the pulses
straddling the step equals the commanded interval within the profile's jitter budget); the derived
`t_utc_ns` steps by **exactly** the applied amount and by nothing else (this is CORRECT behaviour,
not corruption — saying so is what keeps the claim honest); and the field width is 64-bit.

**`--check-wrap` (PLAT-25/29/30) — the new one, and the phase's central evidence.** Given a
`wrap_witness` capture it reports and asserts:
- the raw 32-bit `tick` series decreases at least once (a wrap), with the observed interval between
  wraps quoted against the predicted **71.58 min** derived from the file's own `t_mono_ns`;
- `t_mono_ns` is strictly non-decreasing over the whole file — the reference that proves any jump
  is in the *delivered* timestamp and not in reality;
- the `delivered` timestamp series is scanned for **backward jumps**, each reported with its
  magnitude in seconds and its index. The expected magnitude for the deployed defect is
  ~**4294.967296 s** (`2**32 / 1e6`); say so, and report the measured value rather than assuming it.
- **Two modes, one assertion.** Default (`--check-wrap`) exits **non-zero** if any backward jump is
  found — that is the form plan C4's soak uses after the fix, where zero backward jumps across >=3
  wraps is the acceptance criterion. `--check-wrap --expect-defect` **inverts** it: exit 0 only if
  at least one backward jump IS present, which is the form plan 08 uses to prove the defect exists
  before anything is changed. A tool that could only assert one direction would let the "we fixed
  it" claim rest on a test that never demonstrated the bug.
</instrument_design>

<backend_facts>
- **The pulse path is pigpio daemon scripts.** The tree drives pulses through
  `Digital_Out.store_series()`/`series()`, which use `store_script`/`run_script`/`script_status`/
  `stop_script`/`delete_script`, with a `PI_SCRIPT_INITING` polling loop at `gpio.py:673-681`. These
  execute inside the C daemon, not in Python. **That path is NOT being replaced by this phase** —
  the lgpio rewrite was dropped — so `capture.py` measures the same mechanism before and after.
- **The patched `pigpio.py` is NOT in this repo.** `synchronize()` (`:5306`) and
  `ticks_to_timestamp()` (`:5320`) are Autopilot patches present only in the live rig's
  site-packages, not upstream and not vendored — and PLAT-28 deletes them. `capture.py` must
  therefore **not** depend on them: use raw callback ticks and do the tick->seconds conversion in
  the harness. That is what keeps one tool valid across both arms, on stock or patched clients.
- **Callback shape:** `func(gpio, level, tick)` — 3 positional args; `tick` is 32-bit microseconds
  from a 12-byte `struct.unpack('HHII', ...)` notification. `level == 2` is a watchdog timeout.
- **Counter wraparound:** the tick wraps every `2**32 / 1e6 / 60` = **71.58 minutes**, ~20 times a
  day under 24/7 operation. `capture.py` must detect and record a wrap rather than silently
  producing a negative interval — a capture longer than 71.58 min otherwise reports nonsense.
- **`wrap_witness.py` is the one tool that deliberately DOES use whatever client is installed.**
  Its whole purpose is to record what that client hands a callback. On the pre-migration image that
  is the patched client, and the backward jump is the finding. It must record, in its header,
  the client's `__file__`, its sha256, and whether it carries the patch (detected by
  `hasattr(pi, 'synchronize')`), so the artifact is self-describing and cannot be confused with a
  stock-client run six months later.
- Do **not** read a wall clock inside a callback and call it the edge time. The `tick` argument is
  the sample time; anything read in the callback includes the full socket + Python dispatch latency.
  Record both — `tick` for the measurement, `t_mono_ns` for the reference — and label them.
</backend_facts>
