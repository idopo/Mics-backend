<decisions>
## Decisions locked by this plan

1. **Exactly ONE thread touches the transport: the IO thread.** ZMQ sockets are not thread-safe.
   The caller's thread only ever calls `BoundedSender.enqueue` (a `queue.Queue` operation, which
   IS thread-safe). The command worker only ever calls `enqueue` too, via its `ack_sink`. If a
   future reader is tempted to send directly from `send_signal` "just for the ACK path", this
   comment is why they must not.

2. **IO loop shape, per iteration:**
   a. `transport.events()` -> `connection.apply_all(...)` (edges fire `on_state_change`)
   b. drain up to N frames from `sender.pop(timeout=0)` -> `transport.send(frame)`;
      `stats.sent += 1` on success. Bound N (e.g. 64) so inbound and heartbeat never starve under
      a saturating producer.
   c. `for raw in transport.poll(poll_ms)`: `wire.decode_cmd(raw)`; if not None,
      `command_worker.submit(cmd)`. Non-CMD inbound frames are counted and ignored (the Pi sends
      nothing else today).
   d. if `heartbeat.due()`: enqueue `wire.hb_frame(seq.next())` at the FRONT of the work — i.e.
      send it directly on this same thread rather than round-tripping the queue, so a saturated
      queue cannot starve liveness. **This is deliberate**: a dropped heartbeat makes the Pi
      declare the source dead, which is worse than dropping one more data frame.
   e. every successful `transport.send` calls `heartbeat.note_sent()`.
   The WHOLE body of the loop is inside `try/except Exception` with a rate-limited warning log —
   decision 3.

3. **No exception ever escapes, absolute.** `send_signal`/`send_event` may raise
   `InvalidValueError` — that is the ONE deliberate exception, it is SDK-04's call-site contract,
   and it is a programmer error the researcher fixes once, not a runtime condition. Everything
   else — transport failures, monitor hiccups, callback exceptions, handler exceptions, encode
   failures — is caught, counted and logged on the IO thread. The IO thread must be unkillable by
   anything short of `close()`.

4. **`close()` rule, stated and tested (SDK-09):**
   "close() stops accepting new sends, gives the IO thread up to `drain_timeout_s` (default 2.0s)
   to flush the queue, then ABANDONS whatever remains and records the count in
   `stats.abandoned`, stops the command worker, and closes the transport (LINGER=0)."
   `close()` is idempotent, is safe to call from any thread, and never raises. After `close()`,
   `send_signal` returns `False` and increments `stats.dropped` rather than raising — a
   researcher's loop that outlives the `with` block must not crash.

5. **`seq` is one `SeqCounter` per client, created in `__init__`, never recreated.** Reconnect does
   not touch it. This is CONTEXT.md's resolution of SDK-07's either/or: MAINTAINED, because a reset
   is a discontinuity the caller would have to understand.

6. **`seq` is never surfaced.** No public property, no return value, no kwarg. It appears only in
   frames on the wire.

7. **The `zmq_loopback` test is opt-in and deselected by default** (`addopts = -m "not
   zmq_loopback"` from plan 34-01). It binds a real ROUTER on `127.0.0.1` on an EPHEMERAL port.
   This is the dev host's own loopback — it is NOT the rig, not a Pi, and touches no lab hardware.
   It exists to answer 34-RESEARCH.md Open Question 2 (does the socket monitor actually report
   connect/disconnect on this host's pyzmq 27.1.0, given libzmq#3745 / pyzmq#1340?) BEFORE plan
   34-09 asks a human to restart a pilot. If the monitor turns out not to work here, that is a
   finding to record and route into `client.py`'s design — not something to discover on the rig.

8. **`on_state_change(True)` does NOT mean the Pi is accepting your identity.** TCP-level
   connection and ROUTER-level identity acceptance are different layers, and only the former is
   observable from the sender (EXTLINK-02 — the Pi drops a mismatched identity with no NAK).
   Say this in `client.py`'s docstring and in the `on_state_change` parameter doc. Plan 34-08's
   README must repeat it.
</decisions>
