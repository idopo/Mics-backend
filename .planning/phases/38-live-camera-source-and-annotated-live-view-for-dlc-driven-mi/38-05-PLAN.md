<objective>
Make the path from *a* trained model — not *the* trained model — to a working live camera run
something a researcher can follow without re-deriving anything by hand. Two things: fix the probe so
the documented order is possible, and rewrite the runbook so it is about DeepLabCut rather than about
one project's ten bodyparts.

Purpose: CAM-09, and the standing DLC-13 bar that an un-collapsible honest runbook is a deliverable
in its own right.

Output: a probe that runs with no signal map and prints a paste-ready pose order, and a runbook whose
camera, viewer and keep-up sections carry the numbers plan 38-04 measured.
</objective>

<why_this_is_last>
This is the general-framework half, and it is deliberately sequenced AFTER the rig session. The
researcher's camera is installed and the week of 2026-09-08 is real; a plan set that delivers a
general framework late is better than one that delivers the specific thing late. Nothing here blocks
the camera working, and everything here is better for having a measurement behind it.

If plan 38-04 did not happen, this plan still executes: the runbook then says the keep-up number has
not been measured yet and gives the procedure, which is exactly what `--min-rate` having no default
already forces.
</why_this_is_last>

<the_two_defects_this_plan_closes>
From `35-HARDWARE-VALIDATION.md` §9, found on the rig:

**9c — the probe/generate chicken-and-egg is real.** `RUNBOOK.md` step 6 says to probe *before*
generating, but `--probe-pose` requires `--signal-map`, and the map is what generating produces. The
runbook describes an order the tool does not support. Fixed here **in code**, not by rewording the
runbook to match the limitation.

**§4 — the pose row order is not programmatically discoverable.** `_discover_pose_order` tried
`cfg`, `dlc_config` and `pose_cfg` on the constructed runner and found nothing, so for the MultiMice
model the order was established *indirectly*: `config.yaml`'s `multianimalbodyparts` was the only
10-item list in the project and the array had exactly 10 rows. That reasoning does not generalise —
another project may have several same-length lists, or a flat single-animal `bodyparts`. So the loop
probe -> read the row count and order -> `--pose-order` -> re-probe -> confirm `row_count_match=True`
and `POSE_ORDER_SOURCE: 'probe'` is the only honest path, and it has to be documented as the normal
path rather than as a recovery step.

Also carried: `pose.shape` was `(10, 5)` where DLC-Live's docs say `(num_bodyparts, 3)`. **What
columns 4 and 5 carry is unknown.** Nothing depends on them, and the probe should print them so the
next model's array is measured rather than assumed.
</the_two_defects_this_plan_closes>

**Then write the worked example, because this rig hit T5 and the resolution is instructive** (D-75,
`38-HARDWARE-VALIDATION.md` §1). The installed camera is a `DMK 33GP1300` — The Imaging Source,
monochrome, GigE Vision, serial `5810436`. Four points, each of which a reader with a different
machine-vision camera will need:

- **How to read the model string**, so a reader can classify their own camera from its label
  instead of from a failed capture. `DMK` = mono, `DFK` = colour; `33G` = GigE Vision, `33U` = USB3
  Vision; the trailing number is the serial and is the handle a GenICam library selects the device
  by.
- **T5 splits.** Vendor DirectShow wrappers exist — The Imaging Source ships one — and where one is
  installed the camera presents as an ordinary capture device and the T4 relay works with **no code
  change at all**. `ffmpeg -list_devices true -f dshow -i dummy` is the one command that decides
  this, it writes nothing, and it should be the **first** thing a reader with a machine-vision
  camera runs. Say so before describing any shim.
- **The port-forward does not rescue a GigE Vision camera.** GVCP (control) and GVSP (stream) are
  both **UDP**, discovery is broadcast, and `portproxy` carries TCP only — so the T3 row is
  inapplicable to this whole class of camera, and a reader must not spend a day on it. State this
  in the T3 row itself, not only in prose.
- **T6 is usually the right answer when the wrapper is absent.** GigE means the camera travels over
  a cable, so moving that cable to the vision box (or adding a NIC there) removes the lab computer
  from the path entirely, along with the relay, the second always-on process, and the unsupervised
  host. Note the two standard requirements — same L2 segment, MTU 9000 — and that GigE Vision
  packet loss shows up as **dropped frames, not as an error**, which is what the `--capture-only`
  baseline is there to catch.

Two facts about this class of camera that belong in the runbook because nothing else will surface
them:

- **A mono camera needs a 3-channel expansion before DLC.** State it as a required step, and state
  separately that a model trained on colour footage will behave differently on mono input for
  reasons no plumbing fixes.
- **GigE Vision allows one primary application but also multicast monitors.** If the acquisition
  software must keep recording during a run, that is the escape hatch — a config change on the
  recorder, not a fight over the device, and not something a DirectShow camera can offer.
