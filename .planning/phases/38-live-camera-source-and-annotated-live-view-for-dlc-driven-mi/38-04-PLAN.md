FDA transitions in ElasticSearch, and the researcher watching it happen. Then measure what the
camera and the model actually do together, and derive the keep-up criterion from that measurement
rather than from anyone's expectation.

2026-09-08 deadline is about.

`--min-rate`, and an honest per-truth ledger in the shape of `35-HARDWARE-VALIDATION.md` §7.
</objective>

<standing_rules_this_plan_operates_under>
1. **Never run git, Python or process control on any Pi.** Every rig action below is USER-RUN: the
   plan supplies the exact command, the user runs it, the agent waits. The agent's own actions are
   confined to this repository and to the backend HTTP API.
2. **Never write into the researcher's DLC project directory.** Reading is always fine. Phase 35
   violated this (`35-HARDWARE-VALIDATION.md` §8) and could not make the claim afterwards because no
   manifest existed. A before/after manifest is mandatory here (D-64). This phase runs **no
   `export_model` at all** — the model is already exported to `C:\MICS\dlc_test\exported-models-pytorch\`
   — so the expected diff is empty by construction.
3. **The vision box is Windows, driven by a human, and long single-line commands break on paste**
   (`35-HARDWARE-VALIDATION.md` §9e). Every command below uses the `set VAR=...` then `%VAR%` idiom
   and no line exceeds roughly 70 characters.
4. **Every command states what it writes and where, or says it writes nothing** (D-48).
5. **No latency claims.** Counts and rates only; the vision box's clock and the Pi's clock are
   different domains and Phase 28 owns timing.
6. **`opencv-python` is never installed.** `opencv-python-headless` stays; both ship the same `cv2`
   module and the second one to land clobbers the first, taking the DLC stack with it.
</standing_rules_this_plan_operates_under>
