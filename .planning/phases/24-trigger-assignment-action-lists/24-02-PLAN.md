```python
def scan_fda_for_refs(fda_json: dict) -> list[dict]:
    results = []
    states = fda_json.get("states", {})
    if not isinstance(states, dict): return results
    for state_name, state_body in states.items():
        if not isinstance(state_body, dict): continue
        results.extend(_scan_actions(state_name, state_body.get("entry_actions") or []))
    return results

def _scan_actions(state_name: str, actions: list[dict]) -> list[dict]:
    results = []
    for action in actions:
        if not isinstance(action, dict): continue
        action_type = action.get("type")
        if action_type in ("hardware", "flag", "timer", "method"):
            results.append({"state_name": state_name, "action_type": action_type,
                            "ref": action.get("ref") or action.get("action"),
                            "method": action.get("method")})
        elif action_type == "if":
            results.extend(_scan_actions(state_name, action.get("then") or []))
            results.extend(_scan_actions(state_name, action.get("else") or []))
    return results
```

Public surface:

```python
VALID_ACTION_TYPES     = {"hardware", "flag", "timer", "special", "method", "if", "view"}
VALID_TRIGGER_HANDLERS = {"default", "log_only", "touch_detector", "digital_input"}
VALID_SPECIALS         = {"INC_TRIAL_COUNTER"}
VALID_TRIGGER_CONTEXT_KEYS = {"level", "tick"}

def validate_variables(fda_json: dict, toolkit) -> list[str]: ...
def validate_trigger_assignments(fda_json: dict, toolkit) -> list[str]: ...
def collect_hard_errors(fda_json: dict, toolkit) -> list[str]:
    """Every hard (422-worthy) error for this FDA. Phase 23 appends its compute checks here."""
    if not fda_json or toolkit is None:
        return []
    return validate_variables(fda_json, toolkit) + validate_trigger_assignments(fda_json, toolkit)
```

These constants intentionally mirror `autopilot/autopilot/tasks/fda_vocabulary.py` (Plan 01).
True cross-language single-sourcing would need codegen (out of scope — see 24-RESEARCH.md's note on
TRIGA-10); the honest fix is that THIS module is the enforcement point, so React/Pi drift fails at
save with a 422 instead of silently at Pi session start. Put that sentence in the module docstring.

Resolution rules (mirror what the Pi runtime actually does, so a save that passes here loads there):
- **hardware/timer ref.** Build `known_hw`:
  - `set((toolkit.semantic_hardware or {}).keys())`
  - plus module names when `toolkit.is_backend_authored` — mirror `_validate_fda_against_toolkit`'s
    posture: only enforce when `known_hw` is non-empty, so classic toolkits with no declared
    semantic hardware are not falsely rejected.
  - an action carrying an explicit `"group"` key is direct-ref (GUI-built) → skip the ref check,
    matching `_build_action_callable`'s `self.hardware[group][ref]` path which the backend cannot resolve.
- **flag ref / output target / key_template token / condition operands.** Valid names =
  `set((toolkit.flags or {}).keys()) | set((fda_json.get("variables") or {}).keys()) | {"trial_counter"}`.
- **method ref.** Must be in `toolkit.callable_methods or []` — but only enforce when that list is
  non-empty (legacy toolkits may not have shipped it).
- **key_template tokens.** Extract with `re.findall(r"\{(\w+)\}", template)`.
- **args/kwargs scanning.** Walk `action.get("args")` (list) and `action.get("kwargs")` (dict) and
  for any dict operand containing `"trigger"`, check the key is in `VALID_TRIGGER_CONTEXT_KEYS`.
- **Recursion.** `if` actions recurse into `then` and `else`.
- **Legacy `config` keys.** Only when the entry has no non-empty `actions` list:
  - `touch_detector` → `config["hardware_ref"]` must be present, a non-empty string, and in
    `known_hw`. The Pi resolves it through `self._semantic_hw[hw_ref]`
    (`mics_task.py:1104-1110`, bare `ValueError`) after `config["hardware_ref"]` itself would raise
    a bare `KeyError` — so both failure modes move to save time.
  - `digital_input` → `config["view_key"]` must be present and a non-empty string. **Presence only —
    do NOT try to resolve it.** Valid view keys include the touch-channel trackers
    (`LICKER0…LICKER3`), which are derived at runtime from the Pi's `prefs.json`
    (`device_name` × `num_detectors`) by `check_for_detectors`. The backend has no visibility into
    `prefs.json`, so a resolution check here would produce false rejections. State that limitation
    in the function's docstring rather than guessing.
    **Name the correct future home in that docstring:** view-key *resolution* belongs to Phase 13's
    pilot-specific preflight (`api/routers/toolkit_dispatch.py::preflight_validate`), which keys off
    `pilot_id` and reads `pilot_hardware_config` — the only place that knows a given pilot's
    `device_name` × `num_detectors`. Task definitions are pilot-agnostic at save time, so save-time
    validation can only check presence. Without this forward reference the limitation reads as an
    oversight rather than a deliberate split, and nobody will know where to add the real check.
  - `default` / `log_only` → no config requirements.

Every error string must be self-locating and must NOT match `/^State '...': /`:
`f"Trigger '{trigger_name}' action[{i}]: unknown action type 'telepathy'. Allowed: ..."`.
