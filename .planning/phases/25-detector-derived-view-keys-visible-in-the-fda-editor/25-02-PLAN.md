**Q1 — `view_detector` resolves ONCE AT BUILD TIME, not per evaluation. Locked here.**

CONTEXT D1 says "the Pi resolves `f"{device_name}{channel}"` at build time"; this states exactly
what that means and why, since the `view` **action** it is modelled on resolves per call.

- **Ordering makes it safe — verified.** `MicsTask.__init__` runs `init_hardware()` (line 125),
  then `check_for_detectors()` (127), then `init_flags()` (129), and only then
  `load_fda_from_json()` (161). `self._semantic_hw` is built at `mics_task.py:922-942`, before
  transitions are built at `:991-1036`. So at the moment `_build_condition_operand` runs, both the
  hardware object and every detector Tracker already exist. On hot-reload `hot_update_fda` →
  `load_fda_from_json` re-enters the same point with hardware already up.
- **The `view` action resolves per call because it must** — its `{pin_number}` token varies with
  every interrupt (`mics_task.py:706-716`). A `view_detector` operand's channel is a fixed integer,
  so nothing about it can change between evaluations. Deferring the lookup would buy nothing and
  cost a dict lookup on every FDA tick.
- **Fail fast, and fail with information.** `View.get_value` is
  `return self.view.view[name].get_state()` (`autopilot/core/View.py:43-44`) — a **bare `KeyError`
  carrying only the key name**. Raised per evaluation it would surface inside a transition lambda
  during `wait_for_condition`, at an arbitrary point in a live session, naming neither the ref, the
  channel, nor what was available. Resolving at build time turns that into a `ValueError` at task
  start, in the same place and the same style as the `view` action's own `source_ref` failure
  (`mics_task.py:699-703`) and every other `load_fda_from_json` load error.
- **It therefore cannot silently no-op.** The three ways it could have: (a) unknown `ref` →
  `ValueError` at load naming the available refs; (b) hardware with no `device_name` → `ValueError`
  at load; (c) resolved key absent from `self.view.view` → `ValueError` at load naming ref, channel,
  resolved key and available keys. There is no path where the operand builds and silently reads
  nothing.
- Rejected: resolving per evaluation with a cached key, or letting `View.get_value`'s bare
  `KeyError` propagate. Both trade a load-time failure the researcher sees immediately for a
  mid-session failure they see in a log.

**Q2 — the resolution reuses `_semantic_hw`, exactly as the `view` action's `source_ref` does.**
`mics_task.py:689-703` resolves `source_ref` via `self.hardware[action["source_group"]][ref]` when
a `source_group` is present, else `self._semantic_hw[ref]`, raising `ValueError` with
`sorted(self._semantic_hw.keys())` on failure. The `view_detector` branch does the same, accepting
an optional `"group"` key for symmetry with the existing `{"hardware": ..., "group": ...}` operand
form (`mics_task.py:557-568`). The editor emits `ref` only — every `Modules` entry is registered in
`_semantic_hw` by name.

**Q3 — the legacy `{view, op, rhs}` transition form gains nothing.**
CONTEXT: out of scope, GUI never emits it. `_build_transition_lambda`'s legacy branch
(`mics_task.py:1214-1223`) reads `cond["view"]` directly and does not go through
`_build_condition_operand`; leave it byte-identical. Noted so a reviewer does not read the
asymmetry as an oversight.

**Q4 — a matching branch in `tools/validate_fda.py` is deliberately NOT added.**
Checked this session: `_validate_condition_operand` (`tools/validate_fda.py:170-215`) handles
`tracker` / `flag` / `param` / `hardware` and has **no `view` branch at all**, and its transition
