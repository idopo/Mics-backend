<objective>
Stage 2, part 2. Write the systemd units and the system config drop-ins that turn a hand-started
script into an unattended 24/7 rig.

Purpose: the live rig has **no autostart of any kind** — no unit, no crontab, no rc.local. The
pilot is started by hand via `run_pilot.sh`. That autostart gap is what this plan closes, and it is
where the phase's most dangerous landmines live. (The pilot also spawns its own `pigpiod` at
`pilot.py:949 external.start_pigpiod()` — that is **deliberate and stays**; see the PLAT-33
withdrawal below.) Two landmines kill the rig **silently**:

1. systemd's default start-rate limit (5 starts / 10 s) latches a crash-looping unit into `failed`
   **permanently**. `Restart=always` then stops meaning always, and the rig is down until a human
   intervenes — the exact failure this phase exists to eliminate.
2. `systemd-timesyncd` (the Bookworm default) **steps** the clock whenever the offset reaches
   0.4 s, at any point in uptime, with no config option to prevent it. Verified in systemd's own
   source (`NTP_MAX_ADJUST` in `timesyncd-manager.c:52`).

**Scope change, 2026-08-17 (`31-REVISED-SCOPE.md`).** The lgpio migration was removed; **pigpio
stays**. Two consequences land here:

- The `LG_WD` clause of PLAT-10 is **gone**. `import lgpio`'s relative-path notification FIFO was
  an lgpio landmine and there is no lgpio. `WorkingDirectory=` + `RuntimeDirectory=` stay, for the
  ordinary reason that a long-lived service should not run with cwd `/`.
**PLAT-33 WITHDRAWN 2026-08-17 — user decision. There is no `pigpiod` unit in this plan.** A
previous draft added one (`deploy/pigpiod-mics.conf` plus `After=`/`Requires=pigpiod.service`). The
user reviewed it and chose to leave the daemon spawned by the pilot, because
`external.start_pigpiod()` (`external/__init__.py:31`) registers a `kill_proc` hook on `atexit` and
`SIGTERM` (`:54-59`) that **kills the daemon when the session ends** — and since `pigpiod` is what
actually drives the pins, killing it is what **drops every output**. An independently supervised
daemon would **outlive** a crashed pilot, leaving `VALVE1-4` / `AIR_PUF` / `ODOR1-5` energised with
nothing left to close them. The current design fails safe; the supervised one would not. Supervision
is worth less than a closed valve. See `31-REVISED-SCOPE.md` §5.

**Do not re-add it.** `deploy/pigpiod-mics.conf` is not written here, `mics-pilot.service` carries
**zero** `pigpiod` references, and a counted assertion in Task 1 enforces both. `PIGPIOARGS` /
`PIGPIOMASK` therefore stay single-sourced in `prefs.json`, which is why this plan hands C3 no
two-sources-of-truth problem.

**One consequence for `KillSignal=SIGINT` below, and it is load-bearing now.** `kill_proc` is
registered for `atexit` and `SIGTERM`, not `SIGINT`. On `SIGINT` CPython raises `KeyboardInterrupt`,
unwinds, and runs `atexit` handlers on the way out — so the daemon is still killed and the outputs
still drop, **provided the pilot exits cleanly within `TimeoutStopSec=20`**. If it does not, systemd
escalates to `SIGKILL` and no handler runs at all. Say that in the unit comment: the fail-safe
depends on a clean stop, and `TimeoutStopSec=` is the budget for it.

Output: three MICS units, two system config drop-ins, and a parsing test that asserts every
load-bearing directive.

Every directive below was verified against systemd/chrony/pigpio sources in `31-RESEARCH.md` and

**`mics-pilot.service` — each line load-bearing:**
- `StartLimitIntervalSec=0` in **`[Unit]`** (not `[Service]`) plus `RestartSec=5`. Defaults are
  `StartLimitIntervalSec=10s` / `StartLimitBurst=5`.
- `RuntimeDirectory=mics`, `RuntimeDirectoryMode=0755`, `WorkingDirectory=/run/mics`.
  **No `LG_WD`** — that environment variable existed only for lgpio's relative-path notification
  FIFO and the lgpio port is gone (`31-REVISED-SCOPE.md` §5, PLAT-10 revised). The two directives
  that remain are kept for the ordinary reason: systemd's default working directory is `/`, which a
  long-lived service should not inherit, and `RuntimeDirectory=` gives a tmpfs-backed, correctly
  owned, automatically cleaned directory to own instead. Put that reason in the comment so nobody
  re-adds `LG_WD` and nobody deletes `WorkingDirectory=` as "leftover".
- `Environment=PYTHONNOUSERSITE=1` (PLAT-06): the venv is built WITHOUT
  `--system-site-packages`, but this belt-and-braces stops a stray `pip install --user` shadowing a
  pinned rig dependency.
- `CPUSchedulingPolicy=fifo`, `CPUSchedulingPriority=10` — **not 99**. The justification changed
  with the scope (PLAT-17 revised): it is no longer about lgpio's software-timed transmit path,
  which does not exist here. It is **notification-drain headroom**. `pigpiod` samples the GPIO
  block by DMA every 5 µs and pushes notifications over a socket; the client's notify thread must
  drain that socket faster than the daemon fills it, or notifications back up and — beyond the
  daemon's buffer (`-b`, 120 ms default) — **samples are dropped**, which PLAT-32 requires to be
  detected rather than silently lost. A max-priority CPython process can make the box unreachable;
  the kernel RT throttle (`sched_rt_runtime_us` 950000/1000000) is the safety net.
  **This is a hypothesis until the C4 acceptance soak measures it with `chrt -p` and a dropped-
  notification count.** Write it, comment it as unverified, name C4 as the measurement, and let the
  measurement decide whether it stays. Note also that `pigpiod` itself already runs its whole
  process at `SCHED_FIFO` max (`pigpio.c:8340-8343`) — that is the daemon, not our client, and it
  is not something this unit changes.
- **No `pigpiod` ordering, and no `pigpiod` reference at all.** PLAT-33 was withdrawn 2026-08-17
  (see `<objective>`): the pilot still spawns its own daemon, so there is no `pigpiod.service` for
  this unit to order against. `After=`/`Requires=pigpiod.service` must **not** appear, and the
  test counts `pigpiod` occurrences in the file and requires **zero**. A stray `Requires=` on a unit
  that does not exist would keep the pilot from starting at all.
- `After=network-online.target chrony-wait.service mics-prefs.service`,
  `Wants=network-online.target`, `Requires=mics-prefs.service`.
  `After=` chrony-wait **without** `Requires=` is deliberate: a network-free rig still boots the
  pilot, just late. `chrony-wait.service` ships in Debian bookworm's chrony package, runs
  `chronyc waitsync 0 0.1 0.0 1`, and caps at `TimeoutStartSec=180`.
  **PLAT-21 is RELAXED (2026-08-17):** with timestamps derived from a monotonic counter rather than
  from an estimated tick→wall-clock mapping, waiting for clock convergence is **no longer required
  for correctness** — a late-converging clock no longer corrupts event timestamps or intervals. The
  ordering is kept because it is free and it makes the first session's derived UTC fields sane from
  the start. State that in the comment, so the directive is understood as a convenience rather than
  as a safety property someone later "hardens" into a `Requires=`.
- `KillSignal=SIGINT` + `TimeoutStopSec=20` so the pilot can stop transmissions and drive outputs
  to their safe level before exit (see the fail-safe note below).
- **Do NOT add** `ProtectSystem=strict`, `PrivateDevices=yes` or `DevicePolicy=closed`.
  `PrivateDevices=yes` hides `/dev/gpiochip*` and `/dev/i2c-*` and produces a unit that starts and
  does nothing. Do not copy `chrony-wait.service`'s hardening block.
- `User=pi`, and **no `DynamicUser=`** (PLAT-11): `raspberrypi-sys-mods` `99-com.rules` gives
  `SUBSYSTEM=="gpio", GROUP="gpio", MODE="0660"` and `SUBSYSTEM=="i2c-dev", GROUP="i2c",
  MODE="0660"`, so the running user must be a real member of `gpio` and `i2c`.
- `ExecStart` runs the pilot module from `/home/pi/.venv/mics/bin/python`. Read
  `run_pilot.sh` and `pilot/launch_autopilot.sh` in the repo for the arguments the pilot actually
  needs today (`-f`/`--prefs` among them) — do not invent an invocation.

**There is no `deploy/pigpiod-mics.conf` in this plan.** It was written into an earlier draft under
PLAT-33 and is removed with it. The daemon's argument set stays where it already is — `PIGPIOARGS`
(`-t 0 -l`) and `PIGPIOMASK` (`1111110000111111111111110000`) in `prefs.json`, assembled by
`autopilot/external/__init__.py:39-50` into `sudo pigpiod -t 0 -l -x <mask>`. **One source of truth,
which is the outcome the drop-in would have broken.** Note for the record what that means for the two

**Unit split (PLAT-07/08):** two units, not one.
- `mics-firstboot-once.service`: `Type=oneshot`, `RemainAfterExit=yes`,
  `ConditionPathExists=!/var/lib/mics/.firstboot-done`, `DefaultDependencies=no`,
  `After=local-fs.target`, `Before=sysinit.target`, `WantedBy=sysinit.target`, and an

  **Not `ConditionFirstBoot=yes`:** that keys off `/etc/machine-id` being unpopulated, and the unit

- `mics-prefs.service`: `Type=oneshot`, `RemainAfterExit=yes`, `After=local-fs.target`,

**`firstboot-once.sh` (once-only device identity):**
- Hostname is **always `mics-<serial8>`**, independent of `PILOT_NAME`: unique by construction, and

  CPU serial from `/proc/cpuinfo` — the high half (`10000000`) is not per-board.

  Then restart avahi.

  logs "Host name conflict, retrying with raspberrypi-6", `raspberrypi.local` resolves to a

**Clock (PLAT-20/21):** `chrony` replaces `systemd-timesyncd`. Debian's stock `/etc/chrony/chrony.conf`
**already** ships `makestep 1 3` + `rtcsync` + `driftfile` + `maxupdateskew 100.0` — i.e. step only
during the first three updates, slew forever after, which is exactly the wanted policy. So
`deploy/chrony-mics.conf` is a **drop-in for `/etc/chrony/conf.d/`** that adds lab NTP sources and
nothing else. **Do not rewrite `chrony.conf` and do not restate `makestep`** — that would be
reimplementing the default and would silently diverge on the next Debian update.

**NTP is now actively wanted, not merely tolerated.** The revised design derives every event
timestamp from a monotonic counter, so a disciplined wall clock can no longer corrupt an interval —
it only improves the derived UTC field. That is why plan C3 deletes the commented clock-freeze
block at `pilot.py:1071-1082` (PLAT-22) rather than restoring it. Say so in the chrony drop-in's
header comment: the historical reason for freezing the clock was that a wall-clock jump corrupted
an *estimated* tick→timestamp mapping, and that estimate is gone.

**journald (locked decision, CONTEXT §11.3):** `Storage=volatile` with a size cap
(`RuntimeMaxUse=`, `RuntimeMaxFileSize=`, `Compress=yes`). ES is the system of record and 24/7
operation must not write logs to the SD card — SD wear is the top failure mode in continuous
operation. Note this **overrides** `31-RESEARCH.md` Open Question 7, which recommended persistence
with a cap; the user decided volatile. Ship a `/etc/systemd/journald.conf.d/` drop-in, never an
edit of `journald.conf` itself.

**Fail-safe outputs — and this is now the reason PLAT-33 was withdrawn, so state it carefully.**
With pigpio the daemon drives the pins and the pilot is only a socket client, so a client that dies
does **not** by itself release anything. What saves the rig today is that the pilot **owns the
daemon**: `external.start_pigpiod()` registers a `kill_proc` hook on `atexit` and `SIGTERM`
(`external/__init__.py:54-59`) that kills `pigpiod` when the session ends, and a dead daemon drops
every output. Making the daemon an independently supervised unit would have removed exactly that,
which is why the user withdrew PLAT-33 (2026-08-17).

Two consequences for this unit:

- `KillSignal=SIGINT` + `TimeoutStopSec=20` stay, and they now carry weight. `kill_proc` is
  registered on `atexit` and `SIGTERM`; a `SIGINT` reaches it **via `atexit`** during a clean
  interpreter exit. So the fail-safe holds only if the pilot exits cleanly inside
  `TimeoutStopSec=`; past that systemd sends `SIGKILL` and **no** handler runs. Put that in the
  comment — the timeout is a fail-safe budget, not a politeness setting.
- A `SIGKILL` (systemd's escalation, an OOM kill, a power event) still leaves whatever `pigpiod` was
  driving latched, because the daemon survives and nothing tells it to stop. That is the
  **pre-existing** risk, unchanged by this phase, and C4's per-device meter check measures it rather
  than assuming it. Record it in a unit comment so nobody reads `KillSignal=SIGINT` as a guarantee.

The handler that drives outputs to a documented safe level on SIGINT is plan **C3**'s work; record
that dependency in the comment so the two halves stay connected.
