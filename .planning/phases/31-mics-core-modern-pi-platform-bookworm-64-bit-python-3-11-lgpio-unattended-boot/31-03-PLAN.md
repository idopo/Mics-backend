<objective>
Stage 1, part 2. Make the source Python-3.11-safe and rebuild the dependency file from measured
evidence.

Purpose: the numpy alias breakages and the numpy bump are **coupled** — `np.int`/`np.bool` were
removed in numpy 1.24, so they break the moment numpy moves off the current `1.20.0` pin. Fixing
them separately from the pin is how you ship a rig that imports fine and then dies on first pulse.

**This plan must also correct an optimistic number.** CONTEXT §3 and `31-RESEARCH.md` both state a
"7 direct dependencies" floor. A direct import scan of the post-shed tree on 2026-08-16 found the
tree also imports `pytz` (including `tasks/mics_task.py:1`, squarely on the pilot path), `tzlocal`
(`utils/common.py:18`), `packaging` (`utils/requires.py:15`), `requests` (`utils/wiki.py`,
`utils/plugins.py`), `validators` (`utils/types.py:5`), `pygame` (`hardware/mixer.py:2`) and
`psychopy` (`stim/visual/`). The 7-dep figure is a target, not a measurement. Reaching it requires
deciding each of those on evidence — which this plan does — or the figure goes in the summary as
"7 + N, here is N and why".

Output: an importable-on-3.11 tree, a real `requirements.txt` pinning **stock upstream pigpio**,
and two permanent static gates.

**<pigpio_pin> — the new pin, and the one place the wheel test needs an explicit carve-out**

PLAT-03 (revised) and PLAT-28 require `requirements.txt` to pin **stock upstream pigpio**. Four
things about this pin are different from every other one, and getting any of them wrong ships a
rig whose clock code is invisible to review:

1. **Two artifacts share one name.** `pigpiod` is a C **daemon** (the DMA sampler; the rig runs a
   v78 source build in `/usr/local/bin`, upstream's final release is v79). `pigpio` on PyPI is the
   **Python client** that talks to it over a socket. `requirements.txt` pins the CLIENT. The daemon
   is installed by `deploy/install.sh` (plan 07) and **started by the pilot itself**
   (`external.start_pigpiod()`) — *not* by a systemd unit. *(Corrected 2026-08-17: PLAT-33, which
   would have made it a supervised unit, was **withdrawn** by user decision, because the spawn's
   `kill_proc` hook is what closes the solenoids at session end.)* Say which artifact is which in
   the requirements comment; they are versioned independently.
2. **The client wheel is `py3-none-any`.** It is pure Python, so it has NO `cp311` tag and NO
   `aarch64` platform tag. `tests/test_requirements_wheels.py` asserts a cp311/py3/abi3 tag **AND**
   an aarch64/manylinux platform; a pure-Python wheel fails the second half. Add it to the SAME
   explicit allow-list `Adafruit-PureIO` uses, with its own comment — `none-any` is *better* than
   an sdist, not a tolerated exception, and the allow-list must distinguish the two cases.
3. **Do NOT vendor, patch or monkey-patch it** (PLAT-28). The deployed rig client carries ~50 lines
   of Autopilot patches (`sync_ticks`, `synchronize()`, `ticks_to_timestamp()`) that are the source
   of every clock defect this phase fixes. Pin upstream and leave it alone; all clock logic lands in
   a MICS-owned module in plans C1/C2.
4. **Verify the pin the same way every other pin is verified** — query the PyPI JSON API at
   execution time for the resolved version's files. Do not copy a version number out of this plan;
   record what you actually resolved, and record the DAEMON version separately once plan 09
   installs it on real hardware.

Record in the summary: the client version pinned, the wheel tag it resolved to, and the fact that
the daemon version is deliberately not pinned here.
