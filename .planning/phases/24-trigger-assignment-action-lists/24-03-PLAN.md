- `detectMode`: add `if ('trigger' in (value as object)) return 'trigger'` before the literal fallback.
- `MODE_COLORS.trigger = '#38bdf8'`, `MODE_LABELS.trigger = '@ Trigger'`,
  `MODE_TOOLTIPS.trigger = 'The level or timestamp of the hardware event that fired this trigger. Only available inside a trigger action list.'`

  rendered ONLY when it is true — this form is meaningless in a state body and `_resolve_arg` would

  `toolkit.flags ∪ variableNames` (deduped, order: flags first, then variables).** Without this the
  reference case cannot be assembled by clicking: the `view` action's Value is `{"flag": "level"}`
  where `level` is a *variable* captured by `output`, not a toolkit flag — and `flagKeys` is
  currently `Object.keys(toolkit?.flags ?? {})` (`ArgInput.tsx:60`) rendered as a closed `<select>`.
  Plan 07 Checkpoint 1 step 5 ("value = flag `level`") is unsatisfiable otherwise. Keep the existing
  free-text fallback for when the merged list is empty. Variables may be visually distinguished from
  flags in the option list, but they share the `{"flag": name}` wire form — on the Pi both live in
  `self.flags` (Plan 01 declares `variables` as Trackers in `self.flags`), so this is one namespace,
  not two.
- `switchMode('trigger')` → `onChange({ trigger: 'tick' })`.
- When `mode === 'trigger'`, render a `<select>` with options `level` and `tick`, wired to
  `onChange({ trigger: e.target.value })`.
- Defensive: if `allowTriggerContext` is false but the stored value already IS a trigger operand
  (e.g. the user edited the trigger list then opened the same action elsewhere), still render the
  trigger select rather than silently corrupting the value. Compute the visible mode list as
  `allowTriggerContext || mode === 'trigger' ? ALL_MODES : ALL_MODES.filter(m => m !== 'trigger')`.
