<objective>
Make detector channels first-class pickable options in the FDA editor — transition conditions,
state-body operands, trigger action lists (DVK-03) and the `view` action's `key_template` (DVK-04)
— **emitting a detector reference, never a resolved per-pilot key (DVK-11)** — while preserving the
keep-current-value escape that lets an unknown stored key survive a round trip (DVK-05) and keeping
detector keys out of the flag picker (DVK-07).

Purpose: `ConditionBuilder.tsx:83-88` renders a `<select>` whenever the option list is non-empty,
so a licker channel is currently unreachable *even by typing*. Attaching MPR121 to a toolkit
surfaces `MPR121` — the device — and never its channels. This is the visible half of the phase, and
the half where the DVK-11 design change lands hardest: the operand editor is built around a single
string, and a detector reference is two fields.

Output: one new pure `.mts` module with real automated tests, plus prop threading and three picker
changes.
</objective>

**S1 — the `<select>` stays string-valued; `detectorOptions.mts` owns the string ⇄ operand
mapping. This is the whole answer to "how does a two-field value thread through a component built
around one string".**

`OperandEditor` is driven by two locals: `type = getOperandType(operand)` and
`key = getOperandKey(operand)` — a `string` — with `buildOperand(type, value)` turning a changed
select value back into an operand (`ConditionBuilder.tsx:7-35, 59-64`). Widening `key` to a union
would ripple through `setType`, `setKey`, all five branch renders, `ConditionRow`,
`ConditionGroupsEditor` and `IfActionEditor`.

Instead: a detector channel is represented **in the select only** by an opaque option token, and
two pure functions convert:

```ts
viewOperandToOptionValue(op)                      // {view_detector:{ref:'MPR121',channel:2}} -> "@detector/MPR121#2"
optionValueToViewOperand(value, detectorIndex)    // "@detector/MPR121#2" -> {view_detector:{...}}
```

`optionValueToViewOperand` decides by **membership in an index built from the backend's own
`detector_channels`**, not by parsing the string. A value that is not in that index is emitted as
`{view: value}` unchanged. Consequences:
- Zero prop-shape change. `key` stays `string`, every existing branch is untouched.
- `ConditionBuilder.tsx:85`'s keep-current-value escape works verbatim: an unknown stored operand
  round-trips through its own token and is offered as an extra `<option>`, exactly as today.
- The round trip is a **pure function pair**, so it is unit-tested by `node --test` rather than
  proven by clicking.

*Known, accepted, non-existent edge:* a stored `{"view": "@detector/MPR121#2"}` — a literal view key
that happens to equal a generated token — would be re-encoded as a detector reference on re-save.
That requires a `device_name` of `"@detector/MPR121#"`. All 149 `task_definitions` rows were walked
(CONTEXT D3); no such key exists, and the token prefix is chosen to be un-typeable as a device
name. Recorded so a reviewer sees it was considered, not missed.

Rejected: encoding the operand as JSON in the option value (unreadable in devtools, and
`JSON.parse` on user-editable free text is a footgun); a parallel `detectorOperand` prop threaded
beside `operand` (two sources of truth for one field); widening `key` to a union (the ripple above).

**S2 — the picker shows `MPR121 — channel 2 (→ LICKER2)`.** (CONTEXT lists the presentation as
Claude's Discretion.)
- The **stable** part of the label is `ref` + channel, because that is what is stored. It comes
  first so the researcher reads what the definition will say.
- The **preview** in parentheses is the resolved name on the configured pilots, from plan 03's
  `keys` / `device_names`. It exists because researchers know the spouts as `LICKER2`, not as
  "channel 2", and hiding it would make the picker unrecognisable to the person using it.
- With `conflict: true` and differing names, the preview shows all of them: `(→ LICKER2 / TONGUE2)`.
- With no name available the parenthetical is **omitted entirely** — never rendered as `(→ ?)`.
- The preview is decoration only: nothing is stored from it, and `optionValueToViewOperand` never
  reads it.

**S3 — switching operand type away from `view` must not carry the token.**
`setType(newType)` calls `buildOperand(newType, key)` with the *current* `key`
(`ConditionBuilder.tsx:63`). With a detector selected, `key` is `"@detector/MPR121#2"`, so
switching to `flag` would produce `{flag: "@detector/MPR121#2"}` — nonsense that saves and then
422s on an undeclared flag. `setType` must use a **display key**: the resolved literal name when
one is available, else `''`. One line, and it is the kind of thing that is invisible until a user
does it.

**S4 — no Vitest. Automated React coverage comes from Node's built-in test runner over pure
`.mts` modules.** Proven working in this repo on node v24.14.0 during planning:
`node --test "tests/**/*.test.mts"` passes, `npx tsc --noEmit` stays clean, and `npx vite build`
still succeeds. Zero new dependencies, no change to `vite.config.ts`, `tsconfig.json` or the
web_ui Dockerfile.

Mechanics that make it work — follow them exactly, they were each a failure during planning:
- The pure module must be `.mts`, not `.ts`. **Corrected reason (the earlier one was wrong and is
  recorded here so nobody re-derives it):** Node does *not* refuse a bare `.ts`. With no
  `"type": "module"` in `web_ui/react-src/package.json`, node v24 emits a
  `MODULE_TYPELESS_PACKAGE_JSON` warning, reparses the file as ESM, and named imports of **real
  runtime exports** resolve fine. The *"does not provide an export named …"* failure seen during
  planning came from importing a **types-only** module as a value import (see task 1) — a
  different bug entirely. `.mts` is kept because it is ESM unambiguously and by extension, emits no
  warning, and does not depend on a reparse heuristic.
- Test files live in `web_ui/react-src/tests/`, **outside** `tsconfig.json`'s `include: ["src"]`,
  so `tsc` never type-checks the `node:test` / `node:assert` imports and `@types/node` is not
  needed.
- `.tsx` files import it as `./detectorOptions.mts` **with the extension** — the repo already sets
  `allowImportingTsExtensions: true` and `noEmit: true`, so `tsc` accepts it and Vite resolves an
  explicit path directly.
- `node --test tests/` (directory form) does **not** pick up `.mts`. The working invocation is
  `node --test "tests/**/*.test.mts"`, quoted.

Rejected: scoping a Vitest + jsdom + testing-library setup in this phase. It changes
`npm install` in the web_ui Docker builder stage for all future work. Rendering and interaction
stay manual-only; the *logic* that decides which options are offered and what JSON they produce
does not — and under DVK-11 that logic is now the risky part, which is exactly why it lives here.

**S5 — one option builder, not per-component logic.** Everything that decides which options
appear, how they are grouped, what they are labelled, whether a stored value is unknown, and what
JSON a selection produces lives in `detectorOptions.mts`. The components stay dumb renderers. This
is what makes DVK-03/04/05/11 automatically testable at all, and it is the reason
`ConditionBuilder` and `ViewActionFields` cannot drift apart.

**S6 — DVK-05 is narrowed, per CONTEXT D3, and must NOT be justified by migration.**
All 149 `task_definitions` rows were walked on 2026-07-29. Six use view operands — `Mixer_AUDIO1`,
`Timers_TIMER_TO_NEW_TRIAL`, `cue_led2`, `counter`, `boolean_flag` (Gili's — do not touch),
`TIMER` — and **not one names a detector channel**, because the editor could never emit one.

So the keep-current-value escape (`ConditionBuilder.tsx:81`/`:85`) exists here for **keys the
backend cannot model** — a tracker some Python toolkit method creates, an `ExternalHardware` signal
key, a hand-authored definition. There is **no legacy detector key** to preserve and no dual-read
to build. Any task action, test name or comment in this plan that frames the escape as
"migrating old `LICKER0` operands" is wrong and must be corrected on sight.

**Option token format** — an implementation detail of this module, asserted only through the round
trip, never parsed by a component:

```
`@detector/${module_name}#${channel}`      e.g. "@detector/MPR121#2"
```

**`buildViewOptions` group order and labels — the grouping IS the requirement, do not flatten:**
1. `{label: "Hardware", items: hwNames}` — devices (`MPR121`), the thing that *produces* channels.
   Each item's `value` and `label` are the plain name.
2. one group **per detector**, labelled by the DEVICE NAME, not the module name:
   `{label: "LICKER channels", items: [...], warning?: ...}`.
   - label = `` `${group.device_names.join(' / ')} channels` ``, falling back to
     `` `${group.module_name} channels` `` only when `device_names` is empty. (CONTEXT D6.)
   - **Never derive the prefix by stripping digits off a key.** That re-implements the key format
     in TypeScript — the duplication DVK-01 exists to prevent — and it breaks for any `device_name`
     ending in a digit (`SPOUT2` × 4 → `SPOUT20…SPOUT23`, from which no regex can recover `SPOUT2`).
     The prefix arrives from the backend or not at all.
   - one item per entry in `group.channels` (**not** per entry in `keys` — channels are what is
     stored, S2/DVK-11):
     `value` = the token, `label` = `` `${module_name} — channel ${ch}${preview}` `` where
     `preview` is `` ` (→ ${names.join(' / ')})` `` built from the `keys` that end in that channel
     for each `device_name`, or `''` when none is available.
     Build the preview as `` `${device_name}${ch}` `` per `device_names` entry — **not** by
     searching `keys`, which would be a second key derivation. `keys` is used only to decide
     whether the backend derived anything at all.
   - `title` on each item: `"stored as {\"view_detector\": {\"ref\": \"MPR121\", \"channel\": 2}} — the name resolves on the pilot at run time"`.
   - When `conflict` is true, `warning` reads
     `"pilots disagree: pilot_a has channels 0-3, pilot_b has channels 1-4"` built from `by_pilot`.
3. `{label: "Flags & variables", items: flagNames}`.
Empty groups are dropped. Values are deduplicated across groups by first occurrence.

**`buildKeyTemplateSuggestions` (DVK-04 — unchanged by DVK-11, see CONTEXT D5)** returns, in order:
- `{insert: "{device_name}", label: "{device_name}", hint: "resolves on the pilot at run time from the action's source device"}` — when `sourceRef` is set. When `sourceRef` is null the entry is
  still returned but `disabled: true` with a hint saying a source device must be picked first,
  because `fda_validation` hard-422s a `{device_name}` template with no `source_ref`
  (`fda_validation.py:302`).
- one `{insert: "{<name>}"}` per declared variable (this replaces the existing raw pill list, same
  behaviour, now single-sourced).
- one literal entry per derived key (`{insert: "LICKER2", hint: "pilot-specific — prefer {device_name}"}`).
  These stay offered because a state body legitimately writes one fixed channel, but the hint must
  say they hard-code a pilot. **This is the one place a literal per-pilot name is still offered,
  and that is CONTEXT D5: the trigger `view` action is untouched by DVK-11.**
