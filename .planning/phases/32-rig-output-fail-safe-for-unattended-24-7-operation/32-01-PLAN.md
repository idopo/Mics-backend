**D1 — What the live daemon actually is, and what PIGPIOMASK actually permits.**
Commands: `ps -o pid,user,args= -C pigpiod` (footprint: none); `command -v pigpiod` (none);
`ls -l /usr/bin/pigpiod /usr/local/bin/pigpiod` (none); `pigpiod -v` (none).
Then the mask test, which is the only way to settle it: `pigs mg 17` and `pigs mg 18` read the
mode of BCM 17 and BCM 18 (none); `pigs r 17` and `pigs r 18` read their level (none); then
`pigs w 17 0` and `pigs w 18 0` (footprint: drives BCM 17 and BCM 18 to logic LOW — the
polarity-1 OFF state for Left_LED/Right_LED and Solenoid/Mid_LED, so it de-energises, it does not
energise); then `pigs r 17` and `pigs r 18` again.
The finding to write: if the mode reads back as output and the level reads 0 after the write, the
mask permits writes to those lines. If `pigs w` returns 0 but `pigs r` still reads 1, the mask is
blocking the write silently and that is the SAFE-07 failure this item exists to catch.

**D2 — Socket, pipe, or neither.**
Commands: `pigs t` (none — returns a tick if the socket interface answers); if it errors, record
the exact error text; `ls -l /dev/pigpio /dev/pigout /dev/pigerr` (none);
`echo "w 17 0" > /dev/pigpio` guarded by testing writability first with `test -w /dev/pigpio`
(footprint for the `echo`: drives BCM 17 LOW — same OFF direction as D1).
The finding to write: name ONE interface — `pigs` socket, `/dev/pigpio` pipe, or neither works.

**D3 — sudoers path vs the built binary.**
Commands: `sudo -k` then `sudo -n true; echo "exit=$?"` (footprint: invalidates the sudo timestamp
cache — the user may be asked for a password on their NEXT unrelated sudo, nothing else changes);
`sudo -n -l 2>&1` (none beyond the cache above).
The finding to write: whether the NOPASSWD rule names the same absolute path that
`command -v pigpiod` resolved in D1. A mismatch means the pilot comes up with no GPIO daemon and
presents as the symptom already recorded in `PI_TRIXIE_INSTALL.txt`.

**D4 — PCA9685 address and MODE1.**
Commands: `command -v i2cdetect i2cget` (none); `i2cdetect -y 1` (none);
`i2cget -y 1 0x60 0x00` and `i2cget -y 1 0x70 0x00` (none — a register read).
The finding to write: which address answers, what MODE1 reads, and whether bit 4 (`SLEEP`, mask
`0x10`) is currently set. Do NOT write any I2C register in this plan — the write is plan 04's,
and it is chosen from this reading.

**D5 — Two questions for whoever wired the rig.**
Not commands. Record them as questions with an `### Answer` block holding `UNRESOLVED`:
(a) Does the solenoid driver board latch its own state, or does it follow the Pi pin? A pull-down
on the Pi pin is worthless if it latches.
(b) Does the motor HAT have a separately switchable/cuttable motor supply rail, distinct from the
Pi's 5 V? This is the SAFE-06 analogue for the I2C side.
Include a physical confirmation for (a) that the user can do while the box is empty: with the
pilot stopped, drive BCM 18 LOW per D1 and report whether the solenoid audibly releases.

**D6 — A daemon-independent fallback (planner-added corollary of D2, not a substitute for it).**
Rationale to state in the doc: a hook that can only de-energise via `pigpiod` is not a fail-safe
in the case where the daemon itself died. Commands: `command -v pinctrl raspi-gpio` (none);
`pinctrl get 17` (none); `id pi` (none — confirms `gpio` group membership);
`pinctrl set 17 op dl` run **as the `pi` user without sudo** (footprint: drives BCM 17 LOW), then
`pinctrl get 17`.
The finding to write: whether an unprivileged `pi` process can drive a line low with no daemon.

**D7 — Mechanism decision.** Leave the section present with the heading `## §7 Mechanism decision`
and body `UNRESOLVED — filled by Task 3`. Plan 03 reads this section by name.
