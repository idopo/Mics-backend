<objective>
Stage 2, part 2. Write the three systemd units and the two system config drop-ins that turn a
hand-started script into an unattended 24/7 rig.

Purpose: the live rig has **no autostart of any kind** — no unit, no crontab, no rc.local. The
pilot is started by hand via `run_pilot.sh`. That is the gap this plan closes, and it is where the
phase's most dangerous landmines live. Three of them kill the rig **silently**:

1. `import lgpio` opens its notification FIFO at `<cwd>/.lgd-nfy<N>`, at module-import time, via a
   RELATIVE path. Under systemd the working directory is `/`. Without `LG_WD` + `RuntimeDirectory`,
   **every edge callback fails with no exception and no log line.** Today's `run_pilot.sh` starts
   from the repo directory, so this has never bitten.
2. systemd's default start-rate limit (5 starts / 10 s) latches a crash-looping unit into `failed`
   **permanently**. `Restart=always` then stops meaning always, and the rig is down until a human
   intervenes — the exact failure this phase exists to eliminate.
3. `systemd-timesyncd` (the Bookworm default) **steps** the clock whenever the offset reaches
   0.4 s, at any point in uptime, with no config option to prevent it. Verified in systemd's own
   source (`NTP_MAX_ADJUST` in `timesyncd-manager.c:52`).

Output: five deploy artifacts and a parsing test that asserts every load-bearing directive.
</objective>

<verified_directives>
Every directive below was verified against systemd/chrony/lgpio sources in `31-RESEARCH.md`.
Reproduce the reasoning as comments in the unit files — a unit whose directives are unexplained is
a unit someone will "clean up".

**`mics-pilot.service` — each line load-bearing:**
- `StartLimitIntervalSec=0` in **`[Unit]`** (not `[Service]`) plus `RestartSec=5`. Defaults are
  `StartLimitIntervalSec=10s` / `StartLimitBurst=5`.
- `RuntimeDirectory=mics`, `RuntimeDirectoryMode=0755`, `WorkingDirectory=/run/mics`,
  `Environment=LG_WD=/run/mics`. lgpio's C side builds `<workdir>/.lgd-nfy<handle>` where workdir
  is `$LG_WD` or `getcwd()`. **Also note `lguGetWorkDir()` calls `chdir()` on the whole process
  when `LG_WD` is set** — so do not assume any relative path elsewhere in the pilot still resolves.
- `Environment=PYTHONNOUSERSITE=1` (PLAT-06): the venv is built WITHOUT
  `--system-site-packages`, but this belt-and-braces stops a stray `pip install --user` shadowing a
  pinned rig dependency.
- `CPUSchedulingPolicy=fifo`, `CPUSchedulingPriority=10` — **not 99**. lgpio has zero
  RT-scheduling calls; pigpio put its whole process at `SCHED_FIFO` max. systemd applies the policy
  at `exec`, before `gpiochip_open()` creates the tx and alert threads, which inherit it
  (`PTHREAD_INHERIT_SCHED` is the POSIX default). A max-priority CPython process can make the box
  unreachable; the kernel RT throttle (`sched_rt_runtime_us` 950000/1000000) is the safety net.
  **This is a hypothesis until plan 10 measures it with `chrt -p`.** Write it, comment it as
  unverified, and let the measurement decide whether it stays.
- `After=network-online.target chrony-wait.service mics-prefs.service`,
  `Wants=network-online.target`, `Requires=mics-prefs.service`.
  `After=` chrony-wait **without** `Requires=` is deliberate: a network-free rig still boots the
  pilot, just late. `chrony-wait.service` ships in Debian bookworm's chrony package, runs
  `chronyc waitsync 0 0.1 0.0 1`, and caps at `TimeoutStartSec=180`.
- `KillSignal=SIGINT` + `TimeoutStopSec=20` so the pilot can stop transmissions and drive outputs
  to their safe level before exit (chardev lines are released when the process dies — see below).
- **Do NOT add** `ProtectSystem=strict`, `PrivateDevices=yes` or `DevicePolicy=closed`.
  `PrivateDevices=yes` hides `/dev/gpiochip*` and `/dev/i2c-*` and produces a unit that starts and
  does nothing. Do not copy `chrony-wait.service`'s hardening block.
- `User=pi`, and **no `DynamicUser=`** (PLAT-11): `raspberrypi-sys-mods` `99-com.rules` gives
  `SUBSYSTEM=="gpio", GROUP="gpio", MODE="0660"` and `SUBSYSTEM=="i2c-dev", GROUP="i2c",
  MODE="0660"`, so the running user must be a real member of `gpio` and `i2c`.
- `ExecStart` runs the pilot module from `/home/pi/.venv/mics/bin/python`. Read
  `run_pilot.sh` and `pilot/launch_autopilot.sh` in the repo for the arguments the pilot actually
  needs today (`-f`/`--prefs` among them) — do not invent an invocation.

**Unit split (PLAT-07/08):** two units, not one.
- `mics-firstboot-once.service`: `Type=oneshot`, `RemainAfterExit=yes`,
  `ConditionPathExists=!/var/lib/mics/.firstboot-done`, `DefaultDependencies=no`,
  `After=local-fs.target`, `Before=sysinit.target`, `WantedBy=sysinit.target`, and an
  `ExecStartPost` that creates the stamp.
  **Not `ConditionFirstBoot=yes`:** that keys off `/etc/machine-id` being unpopulated, and the unit
  itself regenerates machine-id, which makes the condition circular and version-dependent. An
  explicit stamp is auditable and `rm`-able to force re-provisioning. `/tmp` is cleared on boot and
  is not an option.
- `mics-prefs.service`: `Type=oneshot`, `RemainAfterExit=yes`, `After=local-fs.target`,
  `Before=mics-pilot.service`, `WantedBy=multi-user.target`,
  `ExecStart=/opt/mics/deploy/render-prefs.sh`. Runs on EVERY boot — the split exists precisely so
  a later `mics.conf` edit does not silently do nothing.

**`firstboot-once.sh` (once-only device identity):**
- Hostname is **always `mics-<serial8>`**, independent of `PILOT_NAME`: unique by construction, and
  a researcher's cage-naming choice cannot break the network layer. Take the **LOW** bytes of the
  CPU serial from `/proc/cpuinfo` — the high half (`10000000`) is not per-board.
- **Must also rewrite the `127.0.1.1` line in `/etc/hosts`**, or `sudo` warns on every command.
  Then restart avahi.
- Name collision is real and already happening on this LAN: `/etc/hostname` is `raspberrypi`, avahi
  logs "Host name conflict, retrying with raspberrypi-6", `raspberrypi.local` resolves to a
  DIFFERENT machine (`132.77.72.13`), and at least 5 other devices squat the default name. Avahi
  renames silently, leaves `/etc/hostname` untouched, and the suffix is not sticky across reboots.
- Also: regenerate SSH host keys and machine-id, expand the filesystem, and write
  `/boot/firmware/mics-device.txt` with the MAC and serial (for university MAC-registration/NAC).

**Clock (PLAT-20/21):** `chrony` replaces `systemd-timesyncd`. Debian's stock `/etc/chrony/chrony.conf`
**already** ships `makestep 1 3` + `rtcsync` + `driftfile` + `maxupdateskew 100.0` — i.e. step only
during the first three updates, slew forever after, which is exactly the wanted policy. So
`deploy/chrony-mics.conf` is a **drop-in for `/etc/chrony/conf.d/`** that adds lab NTP sources and
nothing else. **Do not rewrite `chrony.conf` and do not restate `makestep`** — that would be
reimplementing the default and would silently diverge on the next Debian update.

**journald (locked decision, CONTEXT §11.3):** `Storage=volatile` with a size cap
(`RuntimeMaxUse=`, `RuntimeMaxFileSize=`, `Compress=yes`). ES is the system of record and 24/7
operation must not write logs to the SD card — SD wear is the top failure mode in continuous
operation. Note this **overrides** `31-RESEARCH.md` Open Question 7, which recommended persistence
with a cap; the user decided volatile. Ship a `/etc/systemd/journald.conf.d/` drop-in, never an
edit of `journald.conf` itself.

**Fail-safe outputs (Pitfall 4):** chardev lines are released when the process dies, so a crash
with a solenoid energised reverts the pin to its default state — unlike pigpio, whose daemon
outlived the client and kept driving the pin. That is probably an improvement, but it is a
**behaviour change on the reward path** and must be verified per device on the rig (plan 16 V4),
not assumed. `KillSignal=SIGINT` plus a pilot-side handler is the mitigation; the handler itself is
plan 15's work. Record the requirement here in a unit comment so the two halves stay connected.
