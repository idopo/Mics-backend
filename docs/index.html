User Guide

System Overview

Traditional experimental approaches require frequent manual intervention, introduce experimenter-dependent variability, and limit throughput, duration, and reproducibility. MICS was built to remove these constraints.

MICS (Modular Interactive Control System) is an open-source platform for automated, scalable experimental control. It separates interactive task logic from hardware implementation: sensors, effectors, and external systems are abstracted as interchangeable functional units, allowing complex experimental environments to be constructed and modified without low-level engineering effort.

Experimental flow is executed through finite state machine logic — called Blueprints — running on dedicated Raspberry Pi controllers ("pilots"). This provides deterministic control at millisecond resolution while supporting adaptive task progression driven by subject behavior. A central orchestration layer coordinates experiment definition, live monitoring, and cohort-level data integration across all setups simultaneously.

MICS is designed for seamless integration with neuroscience technologies including optogenetics, electrophysiology, calcium imaging, and video-based behavioral tracking. Event-locked triggers and closed-loop interactions can be embedded directly in task logic, allowing behavioral contingencies to interact dynamically with external measurement or stimulation systems. The same infrastructure supports purely behavioral studies, chronic home-cage monitoring, circadian-scale experiments, and large-cohort automated training.

ℹ
Everything is defined in the backend — no Pi code editing Hardware drivers, hardware wiring, task capabilities, and the state-machine flow itself are all authored in the web UI and stored in the database. When a session starts, the backend pushes the driver code, the per-pilot hardware configuration, and the state machine to the Pi. The Pi interprets what it is sent at runtime — you no longer edit Python files on the Pi to change a task.

The Four Services

Web UI :8080
The browser interface you interact with. Hosts the React SPA at /react/ and proxies requests to the API and Orchestrator on your behalf.
Orchestrator :9000
The gateway between the web and the Pi devices. Receives ZMQ messages from pilots, maintains live state in Redis, streams events to Elasticsearch, and calls the API for trial increments and graduation checks.
API :8000
The REST backend. Stores subjects, protocols, sessions, and run progress in PostgreSQL. JWT-authenticated; the Web UI holds the token — you never need it directly.
Backup —
Runs a nightly job at 23:59 that takes a PostgreSQL dump and an Elasticsearch snapshot, then uploads them to the lab SMB share on storwiz.

Data Flow at a Glance

Browser  →  Web UI (:8080)  →  API (:8000)  →  PostgreSQL
                          ↘  Orchestrator  →  API (:8000)  [trial / graduation / run status]
                                         →  Redis         [live pilot state]
                                         ↕  ZMQ (:5560)
                                 Pilot (Raspberry Pi)
                                         ↓  events
                              Elasticsearch (:9200, host)

Pi Setup & Onboarding

Each Raspberry Pi arrives as a pre-configured OS image (TAR archive) stored on the lab SMB server. Burning it produces a Pi that is identical to all others — network config, autopilot software, and task plugins are already in place.

⚠
Image source The Pi OS image is stored on storwiz at:
\\isi.storwis.weizmann.ac.il\labs\yizharlab\Mics\
Connect to the Weizmann VPN (or be on campus) before accessing it.

Step-by-step: Burning a New Pi

  1. 1
    Get the image

    Mount the SMB share and copy the .tar Pi image file to your local machine. The file is a full SD card image compressed as a TAR archive.

  2. 2
    Extract the image

    Unpack the TAR to get the raw .img file. On Windows, use 7-Zip or WinRAR. On macOS/Linux:

    bash
    tar -xf mics_pi_image.tar
  3. 3
    Open Raspberry Pi Imager

    Download and install Raspberry Pi Imager if you don't have it. Launch it and insert your SD card (≥16 GB recommended).

  4. 4
    Select the custom image

    Click Choose OS → scroll to the bottom → Use custom → select the .img file you extracted in step 2.

  5. 5
    Select the SD card

    Click Choose Storage and select your SD card. Double-check it is the correct device before proceeding.

    ⛔
    Select the right device. Writing to the wrong drive will destroy its data with no undo.
  6. 6
    Write

    Click Write and confirm. Raspberry Pi Imager will flash and verify the image. This takes a few minutes depending on SD card speed.

  7. 7
    Boot and connect

    Insert the SD card into the Pi, connect ethernet, and power on. The autopilot service starts automatically on boot. Within ~30 seconds the Pi sends a HANDSHAKE to the orchestrator and appears in the pilot grid.

  8. 8
    Verify in the UI

    Open http://localhost:8080/react/. The new pilot should appear as connected within a minute. Its available tasks are auto-discovered from the HANDSHAKE message.

ℹ
Identical setup, every time Because every Pi is burned from the same TAR image, all configuration (network settings, task plugins, autopilot version, OS config) is guaranteed identical. No manual setup is required after burning.

User Guide

Hardware Libraries

A hardware library is a Python driver file (e.g. gpio.py) that defines hardware classes — Digital_Out, Solenoid, LickSensor, and so on. Libraries live in the database, not baked into the Pi image, and are pushed to a pilot only when a task that needs them starts.

Uploading a library

  1. 1
    Open Hardware Libs

    Click Hardware Libs in the sidebar or go to /react/hardware-libs-ui.

  2. 2
    Upload the driver file

    Paste or upload the .py source. On submit the backend parses it with Python's AST (it is not executed) and extracts every class, its methods, and its constructor arguments.

  3. 3
    Fix any errors

    If the file has a syntax error it is rejected with the offending line number. Valid files return their extracted class/method metadata, which you can confirm on the library's detail page.

Versions, stability and rollback

Every save creates a new immutable version. A version moves through three states:

StateMeaning
unvalidatedNewly uploaded; not yet proven on hardware
betaIn testing
stableMarked stable by a user, or promoted automatically after a successful protocol run

Open a library's detail page (/react/hardware-libs/:id) to see its version history, diff any two versions (the AST diff highlights added / removed / changed classes and methods), mark a version stable, or roll the active version back.

ℹ
Why store drivers centrally? Because the backend knows every class and method a driver exposes, the rest of the system can offer them as dropdowns (when you build modules and FDA actions) and can warn you when a change breaks a task that used a now-removed method.
User Guide

Hardware Modules

A hardware module is a named, reusable hardware instance — the friendly name a task refers to, bound to a concrete class from a hardware library. For example Left_LED → gpio.Digital_Out. Modules are global (shared across all pilots); the actual pins are filled in per-pilot on the next page.

Declaring a module

  1. 1
    Open HW Modules

    Click HW Modules in the sidebar or go to /react/hardware-modules-ui.

  2. 2
    Name the module

    Give it a friendly name (e.g. Left_LED) and an optional display name and description.

  3. 3
    Pick the library and class

    Choose a hardware library, then a class from it. The class dropdown is populated from that library's AST metadata, so you can only select classes that actually exist in the driver.

  4. 4
    Save

    The module is now selectable when assembling a toolkit, and its methods become available in the FDA state builder.

ℹ
Module = capability, not wiring A module says "this task has a Left LED of this type". It deliberately does not say which GPIO pin — that is rig-specific and lives in each pilot's hardware config, so the same module works across differently-wired cages.
User Guide

Pilot Hardware Config

This page records which physical pins each named piece of hardware uses on one specific Pi. It is a free-form, name-keyed table that mirrors the Pi's old prefs.json HARDWARE section — each row has a name and a config dict (pin, polarity, class_name, …).

Editing a pilot's hardware

  1. 1
    Open the pilot's config

    From the pilot grid, open a pilot and go to its hardware config (/react/pilots/:pilot/hardware-config).

  2. 2
    Add an entry by name

    Type any name and fill in its config. The name is the only identity key — the entry does not need to exist in the module registry.

  3. 3
    (Optional) pre-fill from a module

    Use the module-registry picker to pre-fill class_name and default params. This is a convenience only — it creates no permanent link to the module.

Renaming an entry is a delete + re-add (the name is the identity). When a task starts, a pre-run cross-check compares the names the toolkit needs against the names configured here, and blocks the start if anything is missing.

ℹ
First boot seeds itself The first time a Pi sends its HANDSHAKE, its existing prefs.json HARDWARE section is copied into this table automatically — so existing rigs work without manual entry.
User Guide

Toolkits

A toolkit defines a task's capabilities — what it can do — separately from its flow (the flow lives in the task definition, next page). You assemble a toolkit on /react/toolkits-ui from four ingredients.

Building a toolkit

  1. 1
    Open Toolkits

    Click Toolkits in the sidebar. The list groups toolkits by name; click New Toolkit to start a backend-authored one.

  2. 2
    Pick locked states

    Choose from the state methods the task file on the Pi exposes (reported via HANDSHAKE). These are reusable Python method bodies the state machine can call but never rewrite — the trusted building blocks.

  3. 3
    Select hardware modules

    Add the named hardware (from the module registry) this task uses. These determine which hardware the FDA editor lets you act on.

  4. 4
    Declare flags

    Flags are tracker variables the task reads and writes — booleans, counts, timers (e.g. hit_trial, lick_count). They become readable in transition conditions and settable in state entry actions.

  5. 5
    Declare params

    Params are tunable values with defaults (e.g. reward_duration_ms, iti_ms). They surface later in the protocol builder and the per-run overrides modal, so a protocol can retune a task without editing it.

  6. 6
    Save

    Unknown state names or hardware modules are rejected (422). The toolkit is now available as the basis for task definitions.

ℹ
Toolkit identity = (name, hardware) A toolkit is keyed by its class name and a hash of its hardware. The same task wired two different ways (e.g. two rig layouts) appears as two variants you can pick between, with a hardware diff. Toolkits auto-discovered from an older HANDSHAKE show a legacy badge; ones you build in the UI are flagged is_backend_authored.
User Guide

Task Definitions — Visual FDA Editor

A task definition is the behavioral state machine itself: which states exist, what happens in each, and what makes the task move between them. It is bound to a toolkit, stored as an FDA JSON document, and built visually — no Python, no Pi restart.

Creating one

  1. 1
    Open Tasks

    Click Tasks in the sidebar (/react/task-definitions-ui). The list shows every task definition; broken ones (see below) carry a warning badge.

  2. 2
    Create from a toolkit

    Start a new task definition, pick its toolkit, and you land in the editor at /react/task-editor/:id with a react-flow canvas.

  3. 3
    Lay out states

    States are draggable nodes. Add them, position them, and connect them by dragging between node handles to create transitions.

  4. 4
    Edit a state, edit a transition

    Select a node to open the State Builder; select an edge to open the Condition Builder (both below).

  5. 5
    Save

    Saving serializes the canvas to FDA JSON and writes it to the database. It does not touch any Pi.

The State Builder (a node is selected)

Each state has an ordered list of entry actions that run when the state is entered. Add, remove and reorder them; each action has a type:

Action typeWhat it does
HardwareCall a method on one of the toolkit's hardware modules. You pick module → method → args; method and arg fields come from the driver's AST, with type hints.
FlagSet one of the toolkit's flags to a value (literal, a param, or another flag).
TimerStart / reset a timer referenced later in transition conditions.
SpecialINC_TRIAL_COUNTER — the explicit trial-complete signal that drives graduation.
Custom methodCall one of the toolkit's callable methods by name.

Locked / passthrough states (backed by a Pi Python method, with no editable entry actions) show a {py} lock badge and are read-only — they reuse the trusted method body as-is.

The Condition Builder (an edge is selected)

A transition fires when its condition is true. A single condition is operand → operator → value: the operand is a view key or a toolkit flag/variable, the operator is eq / ne / gt / lt, and the value is a literal, a param-ref, or a flag-ref.

Conditions are not limited to one comparison. Using per-row +AND / +OR buttons (Kibana-style) you build an arbitrarily nested boolean tree, so (A OR B) AND C is expressible and renders on the edge as (A ∨ B) ∧ C.

Push to a running pilot (hot-reload)

If a pilot is currently running this task definition, the Push to Pilot button hot-reloads it via the UPDATE_FDA message — no restart. The change takes effect the next time the affected state is entered, so the running state is never interrupted.

⚠
Broken-definition badges If a hardware library changes so a method a task used no longer exists, that task definition is flagged broken — a badge in the Tasks list and a banner in the editor name the offending state and method, so you can fix it before running.

Managing Protocols

A protocol (also called a blueprint) is a sequence of task steps. Each step references a task definition, sets a display name and parameter overrides, and carries a graduation rule that determines when the subject advances to the next step.

Creating a Protocol

  1. 1
    Open the Protocol Builder

    Navigate to /react/protocols-create. You'll see a two-panel view: available task definitions (by display name) on the left, protocol builder on the right.

  2. 2
    Add steps from the palette

    Click a task definition in the left panel to add it as a step. Set the step name and any parameter overrides. Steps run in order from top to bottom.

  3. 3
    Configure graduation

    Each step has a graduation rule embedded in its parameters. The most common type is n_trials — the subject moves to the next step after reaching a trial count threshold.

  4. 4
    Name and save

    Give the protocol a name and click Save Protocol. It is immediately available for assignment to subjects.

Step Parameters

Parameters control task behavior (timing, thresholds, reward amounts). Each task definition exposes its own parameter schema — inherited from its toolkit — and the UI shows the available fields automatically when a step is selected. The graduation, step_name, and task_type keys are reserved and shown separately.

Running Sessions

A session pairs a subject with a protocol. A session run is a single execution attempt on a specific pilot. You can start, stop, resume, and restart runs from the session card view.

Starting a Run

  1. 1
    Find the session

    Navigate to the pilot's session list at /react/pilots/:pilotName/sessions-ui, or to a subject's session list at /react/subjects/:subjectName/sessions-ui.

  2. 2
    Choose a pilot and mode

    On the subject's page, select which pilot to run on and choose a start mode. On the pilot's page, click START on the session card.

  3. 3
    Optionally override parameters

    Click the session title (protocol name) to open the Overrides Modal. Set per-step parameter overrides before clicking START — these override the protocol defaults for this run only.

  4. 4
    Confirm and start

    Click START. The orchestrator sends the task payload to the Pi. The pilot status changes to running within seconds.

Start Modes

ModeWhat it doesWhen to use
new Creates a fresh run starting from step 0, trial 0 Normal start; subject has never run this session
resume Reactivates the most recent stopped or errored run in place — same step, same trial count Session was interrupted (power cut, task error); continue from exact point
restart Creates a new run row but copies the current step index — restarts the step from trial 0 Trial data was bad and you want to redo the current step cleanly

Stopping a Run

Click the STOP button on the pilot card (pilot grid page) or on the session card. The orchestrator sends a stop command to the Pi. The run status changes to stopped. The subject's progress is preserved and can be resumed.

Open the Overrides Modal (click the session title) and switch to the Run History tab to see a table of all past runs: start time, end time, status (completed / stopped / error), and the pilot it ran on.

Technical Reference

Architecture

MICS is a set of Docker services orchestrated by Compose — db (PostgreSQL), api, orchestrator, web_ui, backup, and docs (this site, on :8888) — plus supporting infrastructure (Redis, Elasticsearch) and one or more Raspberry Pi devices on the local network.

│  │  :8080   │    │    :8000     │    │         :5432           │ │

The Orchestrator uses network_mode: host so it can reach both the local Docker network (API) and the Pi devices on the physical network via ZMQ without NAT complications.

Elasticsearch runs outside Docker (directly on the host) and is accessed from containers via host.docker.internal:9200.

Technical Reference

Services

API (api/)

FastAPI application served by Uvicorn on port 8000. Owns the persistent data model. All routes require a JWT Bearer token (HS256, audience mics-clients, issuer mics-api). The Web UI holds the token; browser clients never see it.

Uses a dual ORM: SQLModel manages newer tables (subjects, protocols); SQLAlchemy manages legacy tables (pilots, sessions, session runs, run progress, task definitions). Both share the same PostgreSQL engine.

Orchestrator (orchestrator/)

FastAPI + Tornado + PyZMQ. Runs a ZMQ ROUTER socket on port 5560 that Pi pilots connect to as DEALER sockets. Incoming messages are dispatched to handler methods by message key. Write-heavy operations (Elasticsearch ingestion) are handled by worker threads draining bounded queues (maxsize=50,000) to prevent IOLoop stalls.

Live pilot state is maintained as Redis hashes (pilot:{name}). The Web UI polls GET /pilots/live every second and pushes updates to connected browsers over WebSocket.

Web UI (web_ui/)

FastAPI reverse proxy on port 8080. Authenticates all upstream calls to the API and Orchestrator using the MICS_API_TOKEN env var. Browser clients never touch API credentials directly.

Also serves the React SPA at /react/ — a Vite-built TypeScript application using React 18, React Router, and TanStack React Query. Pilot state is delivered to the browser via a WebSocket at /ws/pilots.

Backup (backup/)

Supercronic-scheduled container. Runs at 23:59 (Asia/Jerusalem) every night:

  1. Runs pg_dump against the PostgreSQL service and compresses it
  2. Triggers an Elasticsearch snapshot to the configured repository
  3. Uploads both to the SMB share at \\isi.storwis.weizmann.ac.il\labs\yizharlab\Mics\database_backup
Credentials are injected via Docker secrets (never in environment variables).

Backend-Driven Task Model

The defining property of the current system: a task's drivers, hardware wiring, capabilities, and state-machine flow all live in the database and are authored in the browser. The Pi is an interpreter. Nothing about a task is edited on the Pi itself.

The five layers

LayerTableWhat it holds
Hardware Libraryhardware_libs + hardware_lib_versionsDriver .py source (e.g. gpio.py), versioned, with AST-extracted class/method metadata.
Hardware Modulehardware_modulesA named instance binding a friendly name → a class in a library (Left_LED → gpio.Digital_Out).
Pilot Configpilot_hardware_configPer-pilot, name-keyed pin bindings (free-form config dict). Mirrors the Pi's prefs.json HARDWARE section.
Toolkittask_toolkitsCapabilities: locked states + hardware modules + flags + params schema. Keyed by (name, hw_hash).
Task Definitiontask_definitionsThe FDA JSON state machine bound to a toolkit. Built in the visual editor.

End-to-end: from upload to running task

  1. 1
    Upload a hardware library

    Driver .py is stored and AST-validated; a version row is created.

  2. 2
    Register hardware modules

    Name each hardware instance and bind it to a class from the library.

  3. 3
    Configure each pilot

    Give the pilot the pins/params for each named hardware entry.

  4. 4
    Assemble a toolkit

    Pick locked states + modules + flags + params. Validated against the pilot's available_locked_states and the module registry.

  5. 5
    Build a task definition

    Draw the state machine (states, entry actions, transition conditions) in the visual editor → FDA JSON.

  6. 6
    Add it as a protocol step & assign to a subject

    The protocol step stores a task_definition_id.

  7. 7
    Start a session

    A pre-run cross-check verifies the pilot has every required hardware entry configured (by name). If something is missing, the UI blocks the start and links to the pilot's hardware config.

  8. 8
    Orchestrator dispatches

    It sends LOAD_HARDWARE_LIBS (driver source) then START carrying the resolved HARDWARE config dict and the state_machine (FDA JSON).

  9. 9
    Pi interprets

    It writes the libs to an override directory, builds hardware instances from the received config, and constructs the running state machine via load_fda_from_json().

ℹ
FDA JSON v2 — the document the Pi interprets Each state declares entry_actions (hardware calls, flag/timer updates, INC_TRIAL_COUNTER, custom methods) and transitions. A transition's condition can be a single comparison or a recursive AND/OR condition_tree. Hardware is referenced by semantic name, never raw GPIO — the same JSON runs on differently-wired rigs.

Versioning & impact detection

Hardware libraries are versioned (unvalidated → beta → stable); a version goes stable when a user marks it or after a successful protocol run. When a library changes (e.g. a method is removed), the backend AST-diffs the versions and flags any task definition that referenced the now-missing method — those definitions get validation_status: 'broken', surfaced as a warning badge in the Tasks list and a banner in the editor.

Technical Reference

ZMQ Protocol

Pi pilots connect to the orchestrator's ZMQ ROUTER socket on port 5560 using DEALER sockets. Each pilot's DEALER identity is its configured NAME. The orchestrator's own name is "T".

All messages are multi-part ZMQ frames. The orchestrator dispatches on the message key (second frame), routing to the corresponding handler method.

Message Types

HANDSHAKE
Pi → Orchestrator. Sent on pilot startup. Enriched payload: pilot name, task classes, plus FLAGS, SEMANTIC_HARDWARE, STAGE_NAMES, CALLABLE_METHODS, REQUIRED_PACKAGES, and the prefs.json HARDWARE section. The orchestrator upserts the pilot, populates task_toolkits / toolkit_pilot_origins / available_locked_states, and (first boot) seeds pilot_hardware_config.
PING
Pi → Orchestrator. Keepalive. Updates the pilot's updated_at timestamp in Redis. Used for the 15-second staleness check.
STATE
Pi → Orchestrator. Pilot state transition (e.g. IDLE → RUNNING → IDLE). Updates the Redis state field and propagates to the browser via WebSocket.
CONTINUOUS / STREAM
Pi → Orchestrator. High-frequency behavioral events — hardware sensor reads, lick detection, timer firings, state transitions. Both keys route to on_data(). Events are enqueued and written to Elasticsearch by worker threads.
INC_TRIAL_COUNTER
Pi → Orchestrator. Sent explicitly by the task when a trial completes. Triggers the graduation check: the orchestrator calls the API to increment the trial count and checks if the subject should advance to the next protocol step.
TASK_ERROR
Pi → Orchestrator. The task raised an error. The orchestrator marks the run error so it can be resumed or restarted.
HARDWARE_LIB_TEST_RESULT
Pi → Orchestrator. Result of validating a pushed hardware library on the Pi — used to promote a lib version toward stable.

Orchestrator → Pi

START
Orchestrator → Pi. Begins a task. The payload carries merged params, the resolved HARDWARE config dict for this pilot, and — for task-definition-backed steps — the state_machine key (the FDA JSON the Pi interprets).
LOAD_HARDWARE_LIBS
Orchestrator → Pi. Sent just before START when the toolkit pins hardware libs. Carries driver source; the Pi writes each to its override directory and imports it.
UPDATE_FDA
Orchestrator → Pi. Hot-reload. Pushes a new FDA JSON to a running pilot (from the editor's "Push to Pilot"). Takes effect on next entry into an affected state — never interrupts the current state.
STOP / PING
Orchestrator → Pi. STOP halts the running task; PING is the keepalive the orchestrator sends on its heartbeat loop.
⚠
INC_TRIAL_COUNTER is never automatic Every Pi task must send this message explicitly at the end of each trial. If a subject is not graduating, verify that the task code dispatches this message and that it is reaching the orchestrator (check orchestrator logs).
Technical Reference

Pi Runtime

The Pi runs an autopilot process that acts as an interpreter for what the backend sends it. On START it receives the FDA JSON (in the state_machine key) and a hardware-config dict, then builds the running task at runtime via load_fda_from_json() — it does not hold a hardcoded copy of the task.

What the Pi builds at START

  • Hardware — instances are created from the received config dict, using driver classes from the pushed hardware libs (written to an override directory by LOAD_HARDWARE_LIBS) rather than the autopilot package.
  • States — each state's entry_actions are compiled into a callable; passthrough states with no actions reuse a locked Python method by name.
  • Transitions — each condition (single comparison or recursive AND/OR tree) is compiled into a lambda over the live view; the state blocks on wait_for_condition() until one fires.
  • Hardware is referenced semantically — the FDA JSON names hardware by friendly name (resolved via SEMANTIC_HARDWARE), so the same JSON runs on differently-wired rigs.

Locked states

The only task-specific Python that lives on the Pi is a set of locked states — reusable method bodies in a task file (e.g. appetitive.py). Their names are reported via HANDSHAKE (available_locked_states) and the FDA references them by name. The state-machine flow that wires them together comes entirely from the backend.

Auto-logging

All methods on Hardware and Tracker classes are decorated with @log_action, which automatically dispatches a CONTINUOUS ZMQ event whenever hardware is activated — no manual logging code in task methods. INC_TRIAL_COUNTER is the one exception: it must be emitted explicitly (as a special entry action in the FDA JSON) to trigger the graduation check.

⚠
Legacy declarative tasks still exist Earlier MICS tasks declared everything in Python — class-level PARAMS / HARDWARE / FLAGS dicts and a hardcoded FiniteDeterministicAutomaton. That path remains for backward compatibility (a task started without a state_machine kwarg falls back to its Python FDA), but it is legacy. New tasks are defined entirely in the backend — do not author task logic on the Pi.

Session Run Modes

The mode field on a session_run controls how progress is initialized when a task starts:

ModeDB behaviorPi payload
new New session_run row + new run_progress at step 0, trial 0 Fresh start; no prior state sent to Pi
resume Reactivates the most recent STOPPED or ERROR run — no new rows created Sends current_step_idx and current_trial from existing run_progress
restart New session_run row with same session_run_index as the previous run (records the retry). New run_progress at same step, trial 0 Same step, fresh trial counter

Override Layering

Overrides set in the UI are stored on session_run.overrides as a JSON object with this shape:

json
{
  "global": {
    "iti_duration": 3000   // applies to all steps
  },
  "steps": {
    "0": { "lick_threshold": 1 },  // step-specific wins over global
    "2": { "lick_threshold": 5 }
  }
}

The orchestrator applies global overrides first, then step-specific values (which win). The merged result is sent to the Pi in the START payload.

Future Plans

Where the System Is Going

Everything described in the User Guide and Technical Reference above is the system as it works today: hardware drivers, wiring, task capabilities, and the state-machine flow are all authored in the browser and interpreted on the Pi. The roadmap below builds on that same paradigm rather than changing it — each future capability slots into the existing hardware-library → module → toolkit → task-definition pipeline.

Three directions are planned. None of them ask the Pi to become smarter or require a researcher to write Python; they extend what can be expressed in the backend and how the Pi talks to the outside world.

Pi Code Editor
For developers: browse, edit, and restart Pi code from the browser — read-only viewer first, then a gated terminal, edit + restart, and package management. A convenience layer over SSH, not a change to how tasks are defined.
MICS-Link — External Hardware
Lets external software (DeepLabCut, OpenEphys, photometry) appear to a task as just another hardware module — its data flows into the same view that GPIO and I2C use, so transitions can gate on it with no new concepts.
Compute & Variables
Adds named variables and a small library of compute primitives (random draws, arithmetic) to the FDA editor, so tasks can derive values at state entry and branch on them — closing the loop on no-code task design.

Each is explained below in terms of the design idea behind it.

MICS-Link — External Hardware ○ Planned

Today a task reads sensors through the view: a GPIO edge or an I2C reading lands in view.get_value("LICKER1"), and a transition gates on it. MICS-Link extends that exact idea to software running off the Pi — a pose-tracker like DeepLabCut, an ephys rig like OpenEphys, a photometry stream. The design goal is that none of these should feel special to a task author.

The core idea: an external source is a hardware module

Instead of inventing a new ingestion path, MICS-Link makes external software look like any other piece of hardware. An author writes one ExternalHardware subclass and decorates its fields with @signal (a continuously-updated value), @event (a discrete occurrence), and @command (something the task can send back). That class is uploaded as an ordinary hardware library, registered as a hardware module, and selected by a toolkit — the same pipeline used for GPIO drivers. Its per-pilot network settings (listen_port, source_id, stale_ms) live in the free-form pilot_hardware_config — no schema change, no new tables.

What changes on the Pi — almost nothing

At task start, each external-hardware instance binds its own ZMQ ROUTER socket on its configured port and accepts only the one configured DEALER identity. Inbound values are written into a view Tracker, auto-registered under the source's name. From there a transition reads view.get_value("dlc_cam1.left_paw_x") > 0.5 through the same API as a lick sensor — zero new call sites, zero new message shapes. Liveness is built in: if heartbeats stop, the source flips to "not alive" after its stale window and per-signal defaults kick in, so a dropped camera never silently freezes a task.

ℹ
Why this shape Closed-loop neuroscience (trigger a stim when a paw crosses a line, reward on a detected behavior) needs external measurement to drive task logic in real time. By routing it through the existing hardware + View abstraction rather than a bespoke pipeline, the entire visual FDA editor, preflight check, and logging stack work on external data for free.

Compute & Variables ○ Planned

The visual FDA editor lets you wire states and gate transitions, but a task often needs to decide something at runtime — pick a random target side, count up a running value, derive a threshold. Today that decision has to be baked into a locked Python state. Compute & Variables closes the last no-code gap by letting a GUI-assembled task produce computed values and branch on them.

Two small additions, kept deliberately simple

  • A variables registry declared at the top of the FDA JSON. Each variable becomes a Tracker that lives in both flags and the view — so it is readable by transitions exactly like a sensor value.
  • A compute entry action that calls one curated primitive (random_choice, random_bool, add, clamp, …) and writes the result into a named variable. Recomputed once per state entry, last-write-wins.

The paradigm guardrail: branching stays in transitions

The primitives only produce values — they intentionally include no boolean-logic operators. All branching continues to live in transition conditions (the same AND/OR condition trees you already build). A trial-onset state computes target = random_bool(0.5); two transitions then gate on target == true and target == false. This keeps the control flow visible on the canvas instead of hidden inside an expression, and keeps the Pi's determinism guarantees intact (compute actions are pure reads + one write).

ℹ
Library-backed, not a scripting language The primitives are stored and versioned through the same hardware-library + AST mechanism as drivers, so the editor can offer each primitive's signature with type hints. A free-form expression escape-hatch was considered and deliberately deferred — the curated library covers current needs without opening a sandbox-evaluation surface.
