<objective>

reach pilot 3 through the Phase 34 SDK, and a transition **authored in the browser** on
`dlc_cam1.led_on_likelihood` ANDed with `dlc_cam1.led_on_x` fires and shows up in Elasticsearch.
The demo is gated on the operator-controllable `LED_on` unique bodypart (D-38), so the first proof
does not depend on an animal cooperating.

Purpose: DLC-07, DLC-08 and the first half of DLC-10, plus roadmap success criteria 1 and 2.

</objective>

<what_is_expected_to_go_wrong>
Named in advance so a failure is diagnosed rather than improvised. Report which of these it was:

1. **The export.** A DLC 3.0 `export_model` emits a single `.pt` while DLC-Live can still complain
   about a missing pose_cfg (DeepLabCut-live issue 137, image.sc). D-09 calls this the likely first
   real obstacle. It is an upstream packaging problem, not a MICS one.
2. **The picker.** `buildViewOptions` has never been observed enumerating dotted extlink keys against
   a live toolkit in a browser. Plan 35-06 proved the API payload carries the signals and that the
   served bundle is current, so if the picker is empty the fault is in the frontend and not in the
   data - say which.
3. **Start order.** Pilot 3's DLC config row is `required: false`, so there is no readiness gate
   holding the run for the sender: the correct order is RUN FIRST, then sender. Starting the sender
   first produces a flushed DEALER backlog delivered in a burst on connect, which looks like a
   working run but is not live streaming - exactly Phase 34 run 582's caveat 1.
4. **`single_animal=True`.** The Gili project is multi-animal. Without the flag the pose array is
   three-dimensional and `DLCProcessor` refuses loudly by design. That refusal is a correct result,
   not a bug.
5. **The pose array may not contain what the lib assumes (D-42, OPEN QUESTION).** DLC-Live's
   documentation states only `(num_bodyparts, 3)`. It does not say whether `single_animal=True`
   returns the 10 multianimal parts or all 32 including the 22 unique ones, nor in what row order.
   The demo is built on `LED_on`/`LED_off`, which are unique parts - so if unique parts are ABSENT
   under `single_animal=True`, the demo cannot work as generated. The contingency is named in Task 2
   and must be taken deliberately, not improvised.
6. **The threshold may be meaningless (D-41).** This project sets `pcutoff: 0.01`, two orders of
   magnitude below DeepLabCut's 0.6 default. A transition authored as `> 0.9` a priori may fire never
   or always. The threshold is measured in Task 2 and only then authored in Task 3.
</what_is_expected_to_go_wrong>

**Step 5 - THE D-42 PROBE. Do this before anything else that depends on the pose array.**

This is the highest-priority observation in the whole plan and everything downstream is provisional
until it is reported. Plan 35-06's lib was generated with `POSE_ORDER_SOURCE = config-declared-UNVERIFIED`,
which means its pose-array indices are a guess.

    dlc-link-live --probe-pose --video <one of the project's own videos> --model-path <the exported .pt> --signal-map <dlc_cam1_signals.py> --geometry-frames 30

It connects to nothing and sends nothing. Report all six printed answers verbatim:
1. `pose.shape` and the row count. Is it 10 (multianimal parts only), 32 (10 + the 22 unique), or
   something else?
2. The runner's bodypart ordering and which attribute carried it - or the NOT FOUND line listing the
   attributes tried.
3. Are the unique bodyparts present, and specifically is `LED_on` among them?
4. The per-row dump: every bodypart in the discovered order with its normalised `(x, y)` and
   likelihood.
5. The verdict line comparing the observed order against the map's `POSE_ORDER`.
6. **The `CORNER GEOMETRY:` line and the four measured corner positions and likelihoods**, whatever
   the verdict.

**Why item 6 decides this checkpoint.** Items 1, 2 and 5 are count and introspection checks, and the
adapter's runtime guard is a count check too. None of them can catch a SAME-LENGTH REORDERING: if
DLC-Live's true runtime row order differs from what the probe introspected while the count still
matches, the adapter sends one keypoint's values under another's name and every one of those checks
stays green. The corner geometry is the only assertion here that tests the order against physical
reality - `NW` must be top-left, `NE` top-right, `SE` bottom-right, `SW` bottom-left - and the arena
corners do not move, so it needs one frame, no animal and no human judgement.

**Contingencies, to be taken deliberately rather than improvised.**
- `CORNER GEOMETRY: FAIL` - the discovered order is WRONG. **No signal mapping may be accepted.**
  Report which inequalities failed and by how much; the corrected order is read off the per-row dump
  (item 4) by placing each corner in its true quadrant, and the probe is re-run with that order until
  the geometry passes. Do not proceed to Task 3 on a FAIL.
- `CORNER GEOMETRY: UNRELIABLE` - a corner was not detected confidently enough to test the order on
  this frame. Re-run with a larger `--geometry-frames` or a different video segment. This is neither
  a pass nor a failure and must never be recorded as a pass.
- `CORNER GEOMETRY: UNAVAILABLE` - one or more corners is absent from the discovered order. Record
  that the geometric evidence is unavailable for this model, and record in writing that the ordering
  then rests SOLELY on Task 3's temporal LED correlation, which is weaker because it pins only the
  two LED rows and nothing else. That tradeoff is stated, not skipped.
- `UNIQUE PARTS ABSENT` at item 3 - the LED demo cannot work as generated: it would need
  `single_animal=False` plus explicit detection selection, which changes the adapter's shape. Report
  it and STOP; that is a design decision, not a retry.
- Geometry PASS but the ORDER differs from the map's - the ordinary case. Task 3 regenerates the lib
  with the measured order.

**Note the limit of item 6, so it is not over-trusted.** The corners pin the ordering at four
positions. A permutation that leaves all four corners in place but swaps `LED_on` with `LED_off`
still passes. That is exactly what Task 3's temporal check covers, and neither check substitutes for
the other.

stretch where the LED is ON and, if you can, for a stretch where it is OFF - the useful threshold is
the one that separates those two populations, and that separation is the actual measurement wanted.
Use the `--dry-run` mode's own output if it reports per-signal values; otherwise say what you used.
