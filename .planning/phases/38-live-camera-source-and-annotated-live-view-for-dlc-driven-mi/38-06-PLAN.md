<objective>
Make `dlc_link` installable and startable on a computer nobody has prepared by hand — including a
computer that has never had DeepLabCut on it.

The researcher asked, verbatim: *"the notebook should come with the bundle for dlc (and sdk) with a
simple bootstrap receiving the yaml for the project. make sure it is easy to install and with
isolated env in order to deploy on any computer (most likely windows)"* and, on the same thread:
*"the computer might not have a dlc installed so make sure you also provide the required dlc download
in the newly bootstrapped env. I'll probably train on one computer and move project folder with
essential to the other computer. list what files are actually needed to make it lightweight and keep
the project structure intact to fit existing dlc sdk plugin."*

Purpose: CAM-10 through CAM-15. Everything plans 38-01 through 38-05 build is reachable today only by
someone standing at the vision box with a repo checkout and a conda environment assembled by hand
over two phases. This plan closes that, and it makes the two-machine split — train here, run there —
a first-class, documented, *verified* arrangement instead of an assumption nobody wrote down.

Output: the notebook inside the wheel; three new console scripts (`dlc-link-notebook`,
`dlc-link-bootstrap`, `dlc-link-doctor`); a model-file probe that proves what actually has to move
between the two machines; an `INSTALL.md` that is honest about what a from-nothing install costs and
what it must not break; a 0.3.0 wheel; and a validation log from a machine that is not the vision box.
</objective>

<the_three_gaps_this_plan_closes>
All three verified against the tree and against the shipped `deeplabcut_live-1.1.0-py3-none-any.whl`,
not inferred.

**Gap 1 — the notebook is not in the wheel.** `dlc_link/pyproject.toml` carries
`[tool.setuptools.packages.find] where = ["src"]` and nothing else about data files. Plan 38-03
writes the notebook to `dlc_link/notebooks/live_view.ipynb`, which is **outside `src/`**, so
setuptools does not see it and it is not in the built wheel. **This gap is unchanged by D-86** and is
the reason that decision does not close this plan: distribution moved from an SMB share to PyPI, but
either way the user receives a *wheel*, and a file the wheel does not contain does not reach them.
"It is in the repo" was never the delivery mechanism and is even less so now — the researchers this
package exists for have no checkout at all. Someone who runs `pip install mics-dlc-link` on a fresh
machine today gets `dlc-link-live --view --view-sink notebook` and no notebook to open.

This also makes plan 38-04's checkpoint step 2 quietly optimistic: it tells the researcher to "open
`notebooks/live_view.ipynb`" on a box whose only install path is `pip install mics-dlc-link`. On the vision
box there is a checkout to fall back on, and `--view-sink mjpeg` needs no notebook at all, so 38-04
is not blocked — but every machine after it would be, and under D-86 "every machine after it" now
means anyone on the internet who installs by name.

**Gap 2 — no plan creates an environment, and every plan assumes DeepLabCut is already there.**
Plan 38-04 installs a wheel with `--no-deps` into the existing `mics-dlc` conda env, itself a clone
of `DEEPLABCUT`. Nothing takes a fresh Windows machine from zero to running, and nothing turns *"here
is my project's config.yaml"* into *"ready to run"*. The gap between those two states is about fifteen
manual steps spread across `RUNBOOK.md`, `35-HARDWARE-VALIDATION.md` and two conda invocations that
exist only in a shell history.

**Gap 3 — the documents assume one machine, and the researcher has two.** `RUNBOOK.md`'s vision-box
half opens with `conda create --clone DEEPLABCUT`, which is only possible on a machine that already
trained the model. The researcher intends to **train on one computer and run on another**. Nothing in
the phase says what has to move between them, and the honest answer turns out to be far smaller than
"the project folder" — see the evidence block below, which is why this gap is cheap to close and
expensive to leave open.

<verified_evidence_the_pt_is_self_contained>
Read this session, directly out of the shipped `deeplabcut_live-1.1.0-py3-none-any.whl`. Task 3's
probe re-proves it on the researcher's own file rather than trusting this block, but the block is
what the transfer manifest is derived from and the executor should not re-derive it.

**1. The PyTorch runner loads everything from the single `.pt`.**
`dlclive/pose_estimation_pytorch/runner.py`, `load_model()`:

```python
raw_data = torch.load(self.path, map_location="cpu", weights_only=True)
self.cfg = raw_data["config"]
self.model = models.PoseModel.build(self.cfg["model"])
self.model.load_state_dict(raw_data["pose"])
...
if self.dynamic is None and raw_data.get("detector") is not None:
    self.detector = models.DETECTORS.build(self.cfg["detector"]["model"])
    self.detector.load_state_dict(raw_data["detector"])
```

`read_config()` in the same module re-opens **the same file** and returns `raw_data["config"]`.
`DLCLive.read_config()` (`dlclive/dlclive.py`) just delegates to it. There is no other disk read: no
`config.yaml`, no `pose_cfg.yaml`, no `dlc-models-pytorch/`, no `training-datasets/`, no project
directory.

**2. For the PyTorch engine, `model_path` must be a FILE.**
`dlclive/engine.py`, `Engine.from_model_path`: a `.pt` **file** resolves to `PYTORCH`; a
**directory** containing both `pose_cfg.yaml` and a `*.pb` resolves to `TENSORFLOW`; anything else
raises. So the "keep the project structure intact" requirement has a precise, checkable answer:
**for a PyTorch export there is no structure to keep** — the model path is one file. Directory
structure matters only on the TensorFlow engine, which this project does not use
(`config_read.read_dlc_config` records `engine="pytorch"` from the project's own key).

**3. `deeplabcut-live` does not import `deeplabcut`.** `grep -rn "import deeplabcut" dlclive/`
returns nothing. The training package is needed for `export_model` and for nothing at runtime.

**4. Its dependency metadata, which decides several arguments below.**
`Requires-Python: <3.13,>=3.10`. Core requires include `numpy<2`, **`opencv-python-headless>=4.5`**,
`pandas`, `tables`, `ruamel.yaml`, `dlclibrary`, `scipy`, `colorcet`, `einops`, `Pillow`, `tqdm`,
`py-cpuinfo`. The `pytorch` extra adds `timm`, `torch>=2.0.0`, `torchvision>=0.15`.

Three consequences worth stating because they change what the documents must say:
- `opencv-python-headless` is a **hard core dependency of `deeplabcut-live` itself**. The collision
  hazard is structural, not incidental — installing `opencv-python` afterwards is guaranteed to
  clobber the build the DLC stack is standing on.
- `numpy<2` is a hard pin, which is why it is on the refusal list beside `pyzmq` and `torch`.
- `pandas` and `tables` are already core, so `dlc-link[convert]` is a **no-op** on any machine that
  has `deeplabcut-live` installed. Say so rather than making the reader install it twice.

**Uncertainty, stated:** a top-down model (`cfg["method"] == "td"`) needs `raw_data["detector"]` in
the same file, and `load_model` raises `ValueError` if it is a top-down model with no detector and no
dynamic cropper. That failure lands at runtime on the machine with the camera. Task 3's probe reports
`method` and whether a `detector` key is present, so this is caught on the **training** machine where
a re-export is cheap.
</verified_evidence_the_pt_is_self_contained>

**Also correct on schedule.** The researcher's 2026-09-08 deadline is about the **vision box**, which

it is one more tag push, and the user upgrades with `pip install --upgrade mics-dlc-link` instead of
fetching and staging a file a second time. It was already cheaper than the alternative; it is now
cheaper still.

**If 38-04 has not run when this plan executes**, nothing changes: 0.3.0 is still strictly greater
than the 0.1.0 on the box, and one staging happens instead of two. The version is set to 0.3.0
unconditionally so no executor has to reason about which world it is in.

<decisions_this_plan_makes>
Continuing the phase's numbering, which ended at D-64. Appended to `38-DECISIONS.md` by Task 1 so the
phase's decision registry stays the single place to look.

**D-76 — The notebook lives under `src/` and ships as package data; a console script copies it out.**
Not "also copied to the repo root", not "documented as a download". One file, inside the package,
reached through `importlib.resources`, and `dlc-link-notebook --out-dir` writes an editable copy where
the researcher asks. site-packages can be read-only, shared, or replaced by the next `pip install`;
editing the copy in it is wrong in all three cases and this design makes it impossible rather than
discouraged.

**D-77 — `dlc-link-bootstrap` is a kit builder, not a runner. It never invents an address.**
It fills in what it can *derive* — the signal map path, the source id, the signal names, the pose
order and its provenance — and leaves `SOURCE`, `MODEL_PATH`, `HOST`, `PORT` and
`VIEW_MIN_LIKELIHOOD` as `None` with a comment naming what goes there. Two reasons, both from this
project's own record: a wrong-but-open `--port` reaches a **live fixture** on pilot 3 (which binds
5599 for `ExtlinkDemo` as well as 5601 for `dlc_cam1`), and Phase 35 guessed a likelihood threshold
once and produced 4 ms state dwells (`35-HARDWARE-VALIDATION.md` §5c). A guessed default here is a
defect wearing the costume of a convenience.

**D-78 — Single-animal is the primary case, not an edge case.** `38-CONTEXT.md` §5 establishes that
DLC-Live's PyTorch runner discards the `unique_bodyparts` head, so LEDs and arena markers are
unreachable live *regardless of `single_animal`*. The researcher's stated response is to train a
**single-animal LED model**. So the bootstrap's first-class path is a flat `bodyparts` list, and the
maDLC `MULTI!` sentinel path is the one that must merely keep working. `config_read.read_dlc_config`
already resolves both (its D-40 resolution), so this is a documentation and test-coverage matter, not
new parsing — but both the bootstrap **and** the transfer manifest must be exercised against a
single-animal config, not only against the MultiMice one.

**D-79 — The D-44/D-46 write refusal is extracted and shared, never reimplemented.** It moves from
`generate_cli._check_out_dir_not_in_project` into `dlc_link/paths.py` and both callers import it. A
second copy of a rule that exists to protect a collaborator's project directory is a second place for
it to be subtly wrong, and this project has already written into that directory once
(`35-HARDWARE-VALIDATION.md` §8).

**D-80 — Version 0.3.0, unconditionally; released to PyPI and installed by the USER.** Same
reasoning as D-63: the wheel's *contents* change, so `pip show mics-dlc-link` must be able to prove
which build is running. **Amended by D-86 (2026-09-10):** the release is a tag push, not a staged
file, and the version bump is now enforced by the index — PyPI is immutable and rejects a re-upload
of an existing version outright. `mics-link` is **not** modified, not rebuilt and not restaged by this plan — the
cosmetic `python -m mics_link.selfcheck` warning is worked around on the `dlc_link` side precisely so
that stays true.

**D-81 — Two install paths, honestly distinguished; the from-nothing cost is measured, never
asserted.** Path A (clone an existing DeepLabCut env) is the proven one and is what the vision box
did. Path B (from nothing) is real and is dominated by the CUDA torch wheel, whose size differs per
platform and per CUDA build. `INSTALL.md` therefore tells the reader how to *measure* it on their own
machine before committing, and carries a slot for the recorded answer, rather than printing a number
nobody checked.

**D-82 — `dlc-link-doctor` calls `selfcheck()` as a function.** `mics_link/__init__.py` imports
`selfcheck` (because `connect()` calls it), so `runpy` finds it already in `sys.modules` and
`python -m mics_link.selfcheck` emits a `RuntimeWarning` every time
(`35-HARDWARE-VALIDATION.md` §9b). Cosmetic, and guaranteed to alarm a new user on their first command
on a new machine. Fixed here by not going through `runpy`, and named in `INSTALL.md` for anyone who
types the `python -m` form anyway. Not fixed in `sdk/`, because that would mean rebuilding and
restaging `mics-link`, which D-63 deliberately avoids in this phase.

**D-83 — Two machines, named, everywhere.** The **TRAINING machine** has full `deeplabcut`, holds the
project directory, does the labelling and training, and is the only machine that runs `export_model`.
The **RUNTIME machine** has the camera, runs `dlc-link-live`, and **may have no DeepLabCut at all**.
Every document produced by this plan states which machine each instruction is for. `RUNBOOK.md`'s
`conda create --clone DEEPLABCUT` opener is only possible on a machine that already trained the model,
which is why it becomes one of two paths rather than the path.

**D-84 — The transfer manifest is derived from a verified fact, and the verification ships as a
command.** `<verified_evidence_the_pt_is_self_contained>` establishes that a DLC 3.0 PyTorch export is
one self-describing `.pt`. That is a fact about `deeplabcut-live` 1.1.0 read out of the wheel, not an
inference — but a researcher should not have to take this plan's word for it about *their* export, and
a top-down model without a bundled detector would fail at runtime on the machine with the animal in
it. So `dlc-link-doctor --model-path <yours>.pt` loads their file with the same call
(`torch.load(weights_only=True)`) and reports `config` present, `pose` present, `method`, and whether
a `detector` is bundled. Verification is a command the researcher runs on the **training** machine,
where a re-export is cheap.

**D-85 — The runtime machine installs `deeplabcut-live`, never `deeplabcut`; CPU-only live inference
is UNDECIDED and is prohibited for a live-animal run until it is measured.**
`deeplabcut-live` does not import `deeplabcut` (verified), so the training package buys the runtime
machine nothing. That distinction is worth stating loudly because it is the difference between two
install sizes — though `torch` dominates either way and this plan quotes no figure it did not measure.

On CPU-only, the honest position, which is stronger than "unknown": the phase already owns the
instrument. D-54 requires a `--capture-only` baseline and a `--dry-run` inference run, and `--min-rate`
has **no default** exactly so this question is answered per machine by measurement. The question is
also not "does CPU match the camera's frame rate" — the decimator caps each signal at 10 Hz on the
wire regardless — it is whether CPU inference sustains a rate at which the animal's position
meaningfully changes. Nobody has measured that. Until someone has, a CPU-only runtime **must not** be
used for a live-animal run, because the failure is silent and lands on the animal: unserviced frames
are gone, signals go stale, and `stale_ms: 3000` makes the Pi serve declared defaults. CPU-only is
fine, today, with no measurement, for kit preparation, for `dlc-link-generate`/`dlc-link-bootstrap`,
and for offline `dlc-link-convert` + `mics-link-replay`, none of which touch a live animal.
</decisions_this_plan_makes>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI -> a fresh machine's Python environment | A public index over TLS, carrying a data file (the notebook) travelling inside it. |
| a shared / read-only `site-packages` -> the researcher's working directory | The notebook now has an installed copy that must never be edited and a working copy that must be. |
| the training machine -> the runtime machine | A ~100 MB binary model file crosses a network share and is loaded by `torch.load` on the other side. |
| the researcher's DLC project directory | A collaborator's read-only asset. A second tool now reads it, and a second `--out-dir` now has to be refused. |
| a generated, pre-filled notebook -> a live pilot | A file that can be copied between machines and now contains a partially-populated command line aimed at hardware in an animal's cage. |
| a `pip install` -> an environment holding a working GPU stack and `mics-link`'s transport | The dependency resolver can silently replace `pyzmq`, `numpy`, `torch` or `cv2`. |
