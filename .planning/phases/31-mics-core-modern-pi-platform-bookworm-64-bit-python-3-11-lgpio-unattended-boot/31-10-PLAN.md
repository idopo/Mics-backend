<objective>
Finish the single-clock invariant. C1-C3 put the **two event paths** on one clock. They did not
touch the other places a timestamp gets written into a record, and C3 deliberately turned NTP back
on (PLAT-20) - so those places became **steppable** in the same change that made the event paths
step-proof.

Purpose: the phase's headline claim is "one clock aligns every event in the system" (CONTEXT §13,
a user requirement). Today that claim is true of `task.py:283` and `logging_utils.py:97` and false
of at least five other fields that reach Elasticsearch. One of them is actively corrupting: the FDA
`view` action injects the trigger's tick as `pi_timestamp` (`mics_task.py:855-856`), C2 changed
that tick from an ISO string to monotonic nanoseconds, and
`event.event_data.pi_timestamp` is mapped **`date`** in the live index - a numeric into a `date`
field is read as **epoch_millis**, so ~25 minutes of uptime (1.5e12 ns) renders as a perfectly
valid **2017** date. It is accepted, it is wrong, and nothing downstream can tell.

This plan must land **before the C4 soak is run**. C4 measures the deployed code path; measuring it
and then changing the code that stamps half its records makes the evidence stale.

Output: every logged timestamp derived from `autopilot.utils.clock`, a behavioural test that a
forced wall-clock step moves no interval, and a static guard (F7) that keeps it that way.
</objective>

<the_rule_this_plan_enforces>
**One clock. Every record. NTP may run and may step.**

- `t_mono_ns` (and any `*_mono_ns` field) is the interval source. It comes from
  `get_clock().observe(tick)` for hardware edges and `get_clock().now_mono_ns()` for everything
  else. A wall-clock step cannot move it.
- Any human-readable / joinable field is **derived**: `get_clock().to_utc_iso(t_mono_ns)` or
  `to_utc_ns`. Derived means one epoch offset, owned by `utils/clock.py`, re-read per call - never
  a private `datetime.now()`.
- Provenance (`TS_HARDWARE` / `TS_SOFTWARE`) travels with the value. A software-read timestamp is
  a legitimate answer; a software-read timestamp **labelled hardware** is not.
- The failure mode being designed against is not a crash. It is a plausible wrong number that no
  downstream consumer can detect - which is exactly what a monotonic integer in an ES `date` field
  produces.
</the_rule_this_plan_enforces>
