**P1 — DVK-02 source of truth: the UNION across pilots that have a `pilot_hardware_config`
row named for that module, carrying per-pilot provenance — ADVISORY ONLY (CONTEXT D4).**
Rejected alternatives, re-stated so nobody re-opens them:

- *A declared default on `hardware_modules`.* That table stores only `name` / `class_name` /
  `hardware_lib_id` / `description` — verified 2026-07-29 via `\d hardware_modules`. A
  `default_config` column would be a **second** store of `device_name`/`num_detectors` that the Pi
  never reads: the Pi receives `prefs_hardware` built from `pilot_hardware_config`
  (`toolkit_dispatch.py:96-104`), merged by `mics_task._merge_prefs_hardware`. The moment somebody
  edits the pilot row and not the module default, the editor offers channels the Pi will not create.
- *A per-toolkit declaration.* Worse: a toolkit is bound to no pilot at all.
- *The union (chosen).* Reads the exact rows the dispatch spec ships, keyed the same way.
  Preflight (DVK-06, plan 03) resolves against the same table scoped to one `pilot_id`.
  **One table, one helper, two scopes.**
- **Disagreement is surfaced, not merged.** The return carries `by_pilot` provenance and a
  `conflict` flag. Under CONTEXT D4 this is now benign: the union decides only what the picker
  *offers*, never what is *stored*, so a mis-configured second pilot cannot corrupt a definition.

**P2 — `channels` is a first-class field of the union return, not derivable client-side.**
This is the concrete consequence of CONTEXT D1. A condition operand stores
`{"view_detector": {"ref": "MPR121", "channel": 2}}` — a channel **index**. The editor therefore
needs the index set, and it must not recover it by stripping digits off `keys`: that
re-implements the key format in TypeScript (the DVK-01 duplication) and breaks for any
`device_name` ending in a digit (`SPOUT2` × 4 → `SPOUT20…SPOUT23`, from which no regex recovers
`2`). `keys` stays, because the picker shows a resolved-name *preview* (`MPR121 — channel 2 (→
LICKER2)`) and plan 03's preflight reports the resolved key in its message.

**P3 — the derivation exists twice, once per language runtime, and that is deliberate.**
`api/detector_keys.py` (container) and `autopilot.tasks.fda_vocabulary` (Pi, plan 02) cannot
import each other. Same situation `fda_validation.py:30-33` already documents for
`RUNTIME_KEY_TEMPLATE_TOKENS`. Mitigation, mandatory: **both test suites pin the same literal
golden table**, reproduced verbatim below and in plan 02. Within each side the format is
single-sourced.

**P4 — a malformed `first_channel` yields no keys on the backend and raises on the Pi.**
Absent/`null` → `0` (today's behaviour, byte-identical). Present but not a non-negative integer →
the backend returns **no keys** (an API read must never 500 on a bad config row), while the Pi
raises `ValueError` at task start (plan 02). Loud where it matters, safe where it is only a render.

**P5 — DVK-11's save-time gate lives in `api/fda_validation.py`, and the pilot-specific half does
not.** This is CONTEXT's "the validator must reject a reference to a module that is not a

- *Is `ref` a detector?* is a **toolkit** fact, not a pilot fact, so it belongs at save time.

- Rejected: putting the ref check in plan 03's preflight scanner only. A non-detector ref is
  wrong on every pilot; catching it at save time is where the researcher can still fix it, and

`module_detector_channels` return shape — this exact JSON is what plan 03 puts on the toolkit
read and plan 04's React code consumes:

```json
[
  {
    "module_name": "MPR121",
    "device_names": ["LICKER"],
    "channels": [1, 2, 3, 4],
    "keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"],
    "conflict": false,
    "by_pilot": [
      {"pilot_id": 1, "pilot_name": "pilot_raspberry_lior", "device_name": "LICKER",
       "channels": [1, 2, 3, 4],
       "keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"]}
    ]
  }
]
```

- **`channels` — REQUIRED (P2).** Sorted unique union of `derive_channels` across `by_pilot`.
  This is what the editor stores; `keys` is what it previews. A group with an empty `channels`
  is omitted entirely.
- **`device_names` and the per-pilot `device_name` are REQUIRED, not conveniences (CONTEXT D6).**
  `device_name` is user-chosen per pilot — "LICKER" is this rig's value, not a constant. The editor
  labels the channel group with the device prefix (plan 04) and must **never** recover that prefix
  by stripping digits off a key.
  - `device_names` — sorted unique `device_name` across `by_pilot`. Normally one entry. Two entries
    mean pilots disagree on the *name*; `conflict` must be true in that case too.
  - A pilot whose config derives no channels is dropped from `by_pilot` entirely.
- `keys` — sorted union across `by_pilot`, ordered by (device prefix, channel index ascending).
  Deduplicated. `LICKER2` before `LICKER11`, never lexicographic.
- `conflict` — `true` iff two or more `by_pilot` entries derive **different key sets**. (Different
  channels ⇒ different keys; different `device_name` ⇒ different keys. So the key set subsumes
  both.) A pilot with no config row for that module is absent from `by_pilot` and is **not** a
  conflict.
- Modules deriving nothing anywhere are omitted (an empty list is the normal case for a toolkit
  with no detector).

```python
def scan_fda_condition_operands(fda_json: dict) -> list[dict]:
```

Territory it must walk — verified against `web_ui/react-src/src/types/index.ts:216-283` and

```
fda_json
├── states: { <name>: { entry_actions: FdaAction[], wait_condition?: FdaCondition } }
│     entry_actions may contain {"type":"if", "condition": FdaCondition, then:[], else:[]} — recurse
├── transitions: FdaTransition[]          # TOP-LEVEL array, not per-state

```

`FdaCondition` = `{left, op, right}`. Emit one entry per side. Location strings a human can act on:
`transitions[0].condition_tree.left`, `states.wait.wait_condition.right`,
`states.s1.entry_actions[2].then[0].condition.left`,
`trigger_assignments[0].actions[1].condition.right`.
