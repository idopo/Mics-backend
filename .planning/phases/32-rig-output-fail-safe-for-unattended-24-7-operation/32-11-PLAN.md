<objective>
Make the resume happen by itself, but only where resuming is correct.

Purpose: RECOV-03 — the endpoint exists (`start-on-pilot` with `mode: "resume"`, reusing the row and
keeping `run_progress`) but only a human calls it. The missing piece is the trigger: pilot reconnects
-> backend finds an interrupted run -> applies policy -> dispatches resume with the recorded
`current_trial`. RECOV-04 — policy is per `error_type` and conservative by default: `TaskError` never
auto-resumes because it recurs (bad params, bad FDA, bad hardware) and must be surfaced instead;
an unrecognised `error_type` does not auto-resume. RECOV-05 — **no resume onto unknown output
state.** `_set_initial_state()` only touches what the *new* run instantiates, so a pin or motor
energised by the crashed run that the resumed task does not declare survives the resume untouched.

RECOV-05 is not satisfied by "plan 05 passed once". It is satisfied by the orchestrator being able to
see, per resume, that the de-energise ran since this run started. That is what the stamp file in
Task 1 is for, and it is the difference between a precondition and a hope.

Output: a fail-safe stamp the Pi reports, a pure policy function, the trigger, and a resume counter.
</objective>

<!-- The existing resume machinery. It works; nothing here reimplements it. -->

**`POST /session-runs`** (`api/main.py:1236-1300`) already takes `mode`. With `mode="resume"` it
finds the most recent `STOPPED`/`ERROR` run for that `(session_id, pilot_id)`, sets it back to
`PENDING`, resets `started_at`, clears `ended_at`, `error_type` and `error_message`, and **returns
the same row** — so `run_progress` (`current_step_idx`, `current_trial`,
`session_progress_index`) is untouched. With `mode="restart"` it creates a new row with the same
`session_run_index`.

**`OrchestratorStation.start_run(run_id)`** (line 276) already resumes correctly: it fetches
`get_run_with_progress`, and when `progress.current_step` is not None it builds the task with
`_build_step_task(..., step_idx=...)` and sets `task["current_trial"] = prog.get("current_trial", 0)`.
Nothing about the dispatch needs changing.

**`MicsApiClient.create_session_run(session_id, pilot_id)`** (`mics/mics_api_client.py:237`) posts
`{"session_id":..., "pilot_id":...}` and does **not** send `mode`. That is the one client gap.

**The web_ui `start-on-pilot` proxy** (`web_ui/app.py:243`) is the human path: it posts
`/session-runs` then `POST {ORCHESTRATOR_URL}/runs/{run_id}/start`. The automatic path is the same
two steps taken inside the orchestrator, so it must not go out through HTTP to itself — call
`self.api.create_session_run(..., mode="resume")` then `self.start_run(run_id)` directly.

**`_reconcile_on_reconnect`** (plan 10) is where the trigger belongs: it already establishes that the
pilot process restarted and has just marked the run `ERROR`. The resume decision follows in the same
call, on the run it just closed.

**`error_type` values in play:** `TaskError` and `TaskTeardownError` (reported by the Pi, plans 09
and 10), `PilotRestarted` (inferred at reconnect, plan 10), `WatchdogTimeout` (inferred from
prolonged silence), `OrchGatewayError` (the orchestrator failed to send STOP).

**DB migrations** are `run_*_migration(engine)` functions in `api/db.py` using
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, called in order at `api/main.py:141-153`. There is no
Alembic. Follow that pattern exactly.

**The fail-safe stamp's location matters.** `mics-pilot.service` sets `RuntimeDirectory=mics`, which
systemd **removes when the unit stops** — so a stamp written by `ExecStopPost` into `/run/mics/`
would be deleted moments later. Write it to `/run/mics-failsafe.json`, outside the RuntimeDirectory.
`/run` is tmpfs and is cleared on reboot, which is the correct semantics: after a reboot there was no
de-energise, but there was a power cut, which is the pull-downs' case and not an auto-resume case.

Every failure mode of the stamp resolves to "do not resume" |
| T-32-39 | Denial of service | A crash loop auto-resuming forever and burning an animal's session overnight | mitigate | `auto_resume_count` on the row plus a cap of 5 in the policy (Test 25); the count is also the RECOV-06 surface, so the loop is visible as well as bounded |
