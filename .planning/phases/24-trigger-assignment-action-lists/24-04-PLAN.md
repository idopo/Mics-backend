**1b — new method `_build_trigger_action_list`**, placed immediately after
`apply_trigger_assignments`:

```python
    def _build_trigger_action_list(self, trigger_name: str, actions: list):
        """
        Build ONE trigger callback that runs an ordered FDA action list.

        Deliberately thin: it delegates every action to _build_action_callable(), the SAME builder
        a state body uses. Nothing about specific hardware lives here. A new action type added to
        _build_action_callable (e.g. Phase 23's `compute`) therefore works inside a trigger with no
        change to this method.

        The returned callable explicitly declares `level` and `tick` because execute_trigger()
        dispatches on inspect.signature parameter NAMES (task.py:285-296). It publishes them on a
        THREAD-LOCAL context for the duration of the action list only — see
        <trigger_context_lifetime> for why a plain attribute is wrong.
        """
        action_callables = [self._build_action_callable(a) for a in actions]

        def _run_trigger_actions(level=None, tick=None,
                                 _callables=action_callables, _self=self):
            _self._trigger_ctx.level = level
            _self._trigger_ctx.tick  = tick
            try:
                for fn in _callables:
                    fn()
            finally:
                _self._trigger_ctx.level = None
                _self._trigger_ctx.tick  = None

        _run_trigger_actions.__name__ = f"trigger_actions_{trigger_name}"
        return _run_trigger_actions
```
The default-argument capture (`_callables=`, `_self=`) mirrors the convention in
`_build_action_callable` (lines 546/554/567) and the DNF transition builder (line 842), and prevents
the late-binding closure bug when several assignments are built in one loop.

<trigger_context_lifetime>
**The trigger context must be thread-local AND cleared in a `finally`. A plain `self._trigger_tick`
attribute set-and-left is a correctness bug, not a style preference.**

Two distinct failures, both from the same shortcut:

1. **Staleness — deterministic, not a race.** Nothing resets the stash after the action list runs, so
   after the very first lick `self._trigger_tick` permanently holds that lick's timestamp. The `view`
   action injects `pi_timestamp` implicitly (Plan 01 `<implicit_pi_timestamp>`), so **every later
   `view` action in a state body would be stamped with the timestamp of an unrelated earlier
   trigger** — a wrong timestamp that looks entirely plausible in ES. It also makes Plan 01's stated
   behaviour ("the same action outside a trigger passes no `pi_timestamp` key at all") impossible to
   satisfy, and turns `{"trigger": "level"}` in a state body from the documented `None` into a stale
   value.

2. **Cross-thread read — `trigger_lock` does not cover it.** Trigger action lists run on
   `self.worker_thread`, the daemon consuming `self.event_queue` (`task.py:153-155`), and
   `process_queue` holds `trigger_lock` only across `execute_trigger` (`task.py:263`). State bodies
   run on the stage thread. The lock therefore serialises trigger-vs-trigger and nothing else: a
   state-body action can read the stash while the worker thread is mid-write. Thread-locality removes
   the sharing entirely rather than adding a second lock to a path that must stay fast.

Implementation — in `apply_trigger_assignments`, before the loop:
```python
        # Trigger context is per-thread and lives only for the duration of one action list.
        # Trigger actions run on self.worker_thread (task.py:153); state bodies run on the stage
        # thread. A shared attribute would leak a fired trigger's tick into unrelated state-body
        # view writes, which the implicit pi_timestamp injection would then record as fact.
        if not hasattr(self, "_trigger_ctx"):
            self._trigger_ctx = threading.local()
```
Create it ONCE (guard with `hasattr` — `apply_trigger_assignments` may run again on hot-reload, and
a fresh `threading.local()` would drop context mid-flight). `threading` is already imported.

Readers use `getattr(self._trigger_ctx, "tick", None)` — the attribute is genuinely absent on any
thread that never entered a trigger, so `getattr` with a default is required, not defensive noise.
Plan 01's `_resolve_arg` `{"trigger": ...}` branch and the view branch's implicit-`pi_timestamp`
injection both read through this accessor. If Plan 01 already landed with `self._trigger_level` /
