  <how-to-verify>
    Follow `26-HARDWARE-VALIDATION.md` and paste each result into it. The agent runs none of this:
    no git on the Pi, no starting or stopping the pilot, no Python on the Pi.

    1. **Deploy + restart.** Sync the Pi files per the checklist and restart the pilot yourself.
       Confirm the pilot comes up and HANDSHAKEs.

    2. **Pi-side unit tests on the rig** —
       `cd ~/Apps/mice_interactive_home_cage && python3 -m pytest tests/ -q`. This is the first time
       the new module is imported under Python 3.7.3; a syntax feature that works on the dev host and
       not on the rig surfaces here.

    3. **Preflight (EPHYS-05).** With the OE box **powered off**, start a session on the pilot.
       Confirm the modal shows `external_device_unreachable` naming the device and host, and that the
       run is blocked. Then power the box on, put it in RECORD by hand, and confirm
       `external_device_busy` — a distinct issue, and still blocking. Set the box back to IDLE.

    4. **Full lifecycle (EPHYS-01/02/03).** Start a session normally. Confirm:
       - OE enters RECORD with no human touching the GUI;
       - the FDA's first state is not entered until recording has started (the readiness gate keys
         on `on_run_start`, not on liveness — see 4a for why these are genuinely different);
       - the session card shows a resolved path for the device;
       - **open that exact path on the OE machine and confirm the data is there.** This is the one
         check that proves the read-back rather than the prediction. Paste the literal directory
         listing.
       - the path's project/experiment/subject segments match the session's actual metadata.

    4a. **Liveness is separate from readiness, and the `role: "none"` construction rule holds
        (EXTLINK-07 / EXTLINK-18).** This is the one Phase 18 rule OpenEphys is the first and only
        consumer of, so nothing else in the system exercises it.
        - With the box **powered on and IDLE** (not recording), confirm `openephys.alive` reads
          **true** in the pilot's View while the module is NOT ready — that is the split working.
          A liveness gate alone would have passed a box that never entered RECORD and recorded
          nothing, which is exactly what the readiness amendment exists to prevent.
        - Power the box **off** mid-run and confirm `openephys.alive` flips to **false** within
          roughly `stale_ms` and emits its CONTINUOUS event. This proves the outbound
          `GET /api/status` poll is genuinely running — the data-arrival default could never
          produce this, since a control-only module has no inbound messages. Confirm the
          behavioural session **keeps running**: loss of liveness mid-run is never automatically
          fatal (EXTLINK-07), the FDA author gates on it if the experiment requires it.
        - Confirm the pilot stayed responsive throughout — **press STOP while the box is off**, with
          the liveness poll hitting an unreachable host, and confirm it works promptly. That is the
          check that proves the poll is on its own `LivenessPoller` thread and not the shared
          IOLoop, and that `get_status` is using a bounded client timeout. A hang here means the
          blocking call reached the loop that also services the orchestrator DEALER.
        - **Construction rule:** temporarily upload a version of the lib with `liveness_hook`
          deleted, repin the module to it, and start a task. Confirm it fails at construction with
          a message naming the class and the role in the pilot log (`init_hardware`'s per-module
          `except` logs it), rather than hanging the readiness gate with a permanently
          `alive=False` module. **Repin to the good version and re-run step 4 before continuing** —
          do not leave the rig on the broken version. This mirrors Phase 18 plan 18-12 step 6b;
          if 18-12 has already proven it with its own demo lib, note that and confirm only the
          OE-specific half (that `OpenEphys` itself ships the hook).

    5. **Markers (EPHYS-04).** With a task whose FDA has a state `entry_action` and a trigger action
       both calling `send_marker`, run it and confirm from the ES event log that the marker sends
       were logged — label, run and trial. Confirm the FDA did not stall while markers were sent.
       *(Whether the marker landed inside the recording is Phase 28's job, not this checkpoint's.)*

    6. **Stop paths (EPHYS-01).** Prove all three return OE to IDLE and release the lease:
       (a) let a run complete normally; (b) press STOP mid-run; (c) induce a task exception.
       Verify **by effect** — `GET /api/status` reports IDLE and the lease is gone. Do not look for
       a CONTINUOUS stop event in ES; that race is inherited and out of scope.

    7. **Backend force-stop (EPHYS-01/03).** Start a run, then **kill the pilot process** mid-run.
       Confirm that reconciliation stops the recording (the box returns to IDLE without anyone
       touching it), releases the lease, and that the run's artifact row is closed with
       `coverage_complete = false`.

    8. **Counter behaviour + directory naming** — if `26-REST-SURFACE.md` marked these DEFERRED,
       settle them now: start two runs back to back and record both
       `(experiment_number, recording_number)` pairs and the literal `Record Node` directory name.
       Report whether `NODE_DIR_FORMAT` as shipped matches reality.

    9. **Per-run opt-out.** Start a session with "run without &lt;device&gt;" checked. Confirm the run
       starts, OE stays IDLE, no artifact row is created, and the readiness gate does not block.

    Report any step that failed and what you saw. A failure here is expected to produce a gap-closure
    plan, not a retrofit of the checklist.
