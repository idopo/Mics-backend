<objective>
Build the three pieces that stand between a researcher's acquisition loop and the socket: call-site
dtype validation, the substitutable transport seam with its identity lock, and the bounded
drop-NEWEST send queue.

Purpose: SDK-04 says a bad value must blow up where the researcher called `send_signal`, not
silently become a `type_mismatch` the Pi counts and drops (invisible from the sender). SDK-03 says
it must be impossible to send under any identity but the configured `source_id`. SDK-06 says a
send must never block a vision loop. All three are provable offline — this plan is the bulk of
SDK-11's "the transport sits behind a seam the tests substitute".

Output: `errors.py`, `values.py`, `transport.py`, `sender.py`, `tests/fake_transport.py`, and
three test modules.
</objective>

<decisions>
## Decisions locked by this plan

1. **Strict dtype rejection, no duck typing.** `validate_value` accepts ONLY exact `bool`, `int`,
   `float`, `str`. An object with `__float__` (e.g. a `numpy.float64`) is REJECTED, not coerced.
   Rationale: msgpack cannot pack it anyway, and silent coercion is exactly the invisible failure
   SDK-04 exists to prevent. The error message MUST name the offending type and tell the caller to
   convert explicitly (`float(value)`), because Phase 35's DLC adapter will hit this on day one
   with numpy scalars. Add a test using a local class with `__float__` — do NOT add numpy as a
   dependency.

2. **`bool` is checked first and separately.** `isinstance(True, int)` is `True`, so any
   `isinstance(value, int)` branch must be guarded by an `isinstance(value, bool)` check ahead of
   it. Mirror `external_hardware_wire.coerce_value`'s special-casing (EXTLINK-12). The SDK does NOT
   know the Pi's declared dtype for a signal — it cannot, there is no such channel — so it accepts
   any of the four and forwards the caller's exact Python type. Document that a `bool`-declared
   signal fed an `int` will still be dropped Pi-side and that this is invisible from the sender
   (EXTLINK-02/34-RESEARCH.md Pitfall 5).

3. **`BoundedSender` owns NO thread.** It is a bounded queue plus drop accounting. Rationale: ZMQ
   sockets are not thread-safe and exactly one thread may touch the socket; plan 34-06's client
   runs a single IO thread that pops from this queue and calls `transport.send`. Putting a thread
   here would create a second socket-toucher. The drop POLICY still mirrors `EgressWorker.enqueue`
   verbatim (`put_nowait` / `queue.Full` / `dropped += 1` / swallowed `on_drop`) — that is the part
   SDK-06 actually specifies. State this deviation-with-reason in the module docstring.

4. **Drop visibility is on by default** (CONTEXT.md): a readable counter (`stats.dropped`) AND a
   rate-limited log AND an optional `on_drop` callback. Rate limit: at most one log line per
   `drop_log_interval_s` (default 5.0s), and the line reports the CUMULATIVE dropped count so a
   suppressed burst is never invisible. `should_log_drop` is a pure function so the policy is
   testable with an injected clock.

5. **`on_drop` exceptions are swallowed.** Same as `EgressWorker`. No exception ever escapes into
   the caller's loop — absolute, per CONTEXT.md.

6. **Identity is set once, at construction.** `ZmqTransport.__init__` calls
   `setsockopt(zmq.IDENTITY, source_id.encode("utf-8"))` exactly once and exposes `source_id` as a
   read-only property with no setter. `validate_target` rejects an empty/whitespace `source_id`, a
   `source_id` that is not `str`, a port outside `1..65535`, and an empty `host` — all with
   `MicsLinkError`. There is no `bind()` and no `sub_connect` anywhere: `role: router_bind` only,
   the Pi binds, we dial in (SDK-03).

7. **`zmq` is imported inside function bodies only**, never at module scope, even in
   `transport.py`. This is stricter than "outside transport.py" and it is what makes plan 34-01's
   hygiene guard a whole-package invariant. It also mirrors the existing driver's proven pattern
   (`extlink_driver.py:_connect`) so `--help` works before pyzmq is installed.
</decisions>
