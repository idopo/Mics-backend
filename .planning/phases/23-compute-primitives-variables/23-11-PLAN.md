pickers. **The governing rule: write by name (flag/tracker actions); read anything through
`view`.**

This is not new capability. It makes one rule true in four places that currently disagree:

read the view at all, and a write picker that cannot name a variable and offers two tracker
methods that do not exist.

particular picker happens to support, and stops being offered spellings that save cleanly and
raise on the rig.

Output: three new pure `.mts` modules with `node --test` contracts, one extracted component,
and edits to four editor components. **Frontend only** — the Pi and backend halves of the same
rule are plan 23-12.

- `{flag: X}` → `self.flags[X].value`; `{view: X}` → `self.view.view[X].get_state()`, and

  and the variables loop (`:1060-1061`) register **the same Tracker object** in both dicts.
  Retiring `flag` from the *read* pickers therefore changes nothing at run time.
- `{hardware: X}` is retired because it is **broken**, not merely redundant.
  `_build_condition_operand` (`mics_task.py:633-634`) reads `_hw.value`; the `Hardware` base
  (`hardware/__init__.py:148-153`) defines `hardware_state` and `get_state()` and **no
  `.value`**. That operand raises `AttributeError` whenever it is evaluated.
- `view` is the strict superset: toolkit flags + declared variables + hardware +
  detector-derived keys.
- **Backward compatibility is REQUIRED here** (explicit user decision, unusual for this
  project). See `<legacy_escape_contract>` — it is a rendering rule, never a migration.

<legacy_escape_contract>
**This is the single most misimplementable part of the plan. Read it twice.**

The escape is a **rendering rule**, not a data migration. The codebase already applies it
twice — `ArgInput.tsx:82` (the trigger pill kept visible when the stored value is a trigger
operand) and `ConditionBuilder.tsx:120-127` (an unknown view key kept as an option, flagged).
Follow those precedents exactly.

MUST:
- `getOperandType` / `getOperandKey` / `buildOperand` keep **every** existing branch, including
  `flag` and `hardware`. Deleting a branch makes a stored operand render with a `<select>`
  whose `value` is absent from its options — the select renders blank, and the researcher's
  next interaction silently rewrites the operand to something else.
- The legacy type appears in the type list **only when the operand currently stored in that
  slot already has that shape**, and is labelled `(legacy)`.
- The moment the researcher switches that operand to `view`, the legacy option disappears from
  that slot's list. The key carries over (`{flag: "my_var"}` → `{view: "my_var"}`), which is
  correct — same Tracker, both dicts.
- Rendering a stored legacy operand and saving without touching it must round-trip the JSON
  **unchanged**.

MUST NOT:
- No sweep, no `useEffect` normalisation, no "upgrade on load", no backend/DB rewrite, no
  codemod over `fda_json`. If you find yourself writing code that changes a stored operand
  the researcher did not click on, you have implemented the wrong thing.
- Do not remove `'flag'` or `'hardware'` from the `OperandType` union or from `FdaOperand`.
</legacy_escape_contract>
