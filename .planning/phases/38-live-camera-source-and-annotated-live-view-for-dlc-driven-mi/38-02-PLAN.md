<objective>
Build the pure half of the viewer: what to draw, what the researcher's authored thresholds mean, and
where the pilot's FDA state honestly comes from. No rendering, no threads, no camera — all of that is
plan 38-03. Everything here is testable on the dev host with nothing installed.

Purpose: CAM-05 and CAM-08. Splitting the pure half out is what makes the viewer testable at all;
the alternative is a module that can only be exercised on a Windows box with a GPU and a live rig,
which is the same trap `35-04` avoided by keeping `cv2` and `dlclive` behind deferred imports.

Output: three modules with no third-party imports at module scope, and three test files that run in
under a second with no network, no cv2 and no numpy.
</objective>

**`GET /pilots/live` does not carry the FDA state.** Verified this session, in this repository:

- `orchestrator/orchestrator/orchestrator_station.py:236-253` (`on_state`) writes whatever the pilot
  reports into `redis pilot:<name> state`, and lines 214-228 seed that key as `IDLE` / `RUNNING`.
- `orchestrator/orchestrator/api.py:24-56` reads it back with a default of `UNKNOWN` and returns
  `{connected, state, active_run, updated_at}` per pilot.
- The FDA state name is emitted only as an ElasticSearch event:
  `autopilot/autopilot/utils/FiniteDeterministicAutomaton.py:17` —
  `Event(event_type='state_transition', event_data={"current_state": next_state_name})`.
  Phase 35 run 588 put 232 of those documents into `event_log_v2` on `132.77.73.217`.

So the design is not a preference between "simpler" and "authoritative": the simple source does not
contain the value the researcher asked to see. It contains something better than nothing, though —
`active_run.subject_key`, **verbatim**, which is exactly the filter the ElasticSearch query needs.
That is why both are used and why the orchestrator is queried first.
</the_fact_that_decides_this_plan>

Write `dlc_link/src/dlc_link/overlay.py` first — the draw plan consumes it.

`Clause` — `signal`, `op` (one of `>`, `>=`, `<`, `<=`), `value` (float), and the original text.
`OverlayError(Exception)` quotes the offending clause.

`parse_overlay(text, signal_map=None)` — splits on commas, tolerates whitespace, and refuses:
an empty string, a clause with no recognised operator, `=`/`==` (with a message saying an equality
test on a float coordinate is never what the author meant), a non-float right-hand side, and — when
`signal_map` is given — any signal not in `SIGNAL_NAMES`, listing the declared names in the message.
That last refusal is the point of the whole function: a typo'd signal name that silently never
matches is exactly the failure class this repository keeps finding on the rig, and it costs one
comparison to make impossible.

`evaluate(clauses, values)` -> `(overall_bool, [(clause, result_or_None), ...])`. A clause whose
signal is absent from `values` evaluates to `None`, and `overall` is the AND over clauses treating
`None` as False. Never raises. Docstring states plainly that this is a DISPLAY aid computed from the
researcher's own numbers on the vision box, that the Pi evaluates its own conditions from its own
tracker values, and that the two can legitimately disagree for a moment; the viewer is not a
substitute for the FDA and must never be described as one.

Write `dlc_link/src/dlc_link/annotate.py`. **No cv2, no numpy, no PIL at module scope or anywhere.**
It computes WHAT to draw; plan 38-03 executes it.

- `CONFIDENT` / `UNCONFIDENT` — named style records (colour as a BGR tuple, radius, thickness).
  Colours are chosen for a colour-blind-safe pair and the choice is stated in a comment; do not use
  red/green as the only distinction.
- `DrawPrimitive` — `kind` (`"circle"` / `"text"` / `"line"`), plus the fields that kind needs, in
  integer pixel coordinates. Nothing float reaches the renderer.
- `build_draw_plan(pose, signal_map, frame_width, frame_height, min_likelihood, overlay_clauses=None,
  overlay_values=None)` -> a record with `primitives` (list) and `problems` (list of strings).
  - Iterates `signal_map.SIGNALS` — **never a hardcoded bodypart list and never a hardcoded row
    count** (D-61). A row index beyond `len(pose)` appends to `problems` and continues; that is what
    a future unique-bodypart-head model, or a mismatched map, will look like, and it must be
    visible rather than fatal in a viewer.
  - Reads columns 0, 1, 2 of each row and NOTHING else. `35-HARDWARE-VALIDATION.md` §4 records that
    the observed array has five columns whose last two are uncharacterised; a comment says so at the
    read site.
  - Pose x/y are PIXELS in the possibly-resized frame (mirroring `processor.py:110-111`); the
    overlay's thresholds are NORMALISED 0..1 because that is what the FDA compares. The conversion
    happens in exactly one place, with a comment naming both conventions, because mixing them is
    the single likeliest bug in this module.
  - Emits, per declared keypoint: a circle at its position styled by whether its likelihood meets
    `min_likelihood`, and a text label `"<bodypart> <likelihood:.3f>"`.
  - When `overlay_clauses` is given: a vertical line for each `_x` clause and a horizontal line for
    each `_y` clause, at the threshold scaled into pixels; a likelihood clause contributes no line
    (it has no position). Each line carries a short text label with the clause as the researcher
    typed it.
  - When `overlay_values` is given, `evaluate` is called and the overall result is emitted as a text
    primitive reading `condition: HOLDS` / `condition: does not hold`, immediately followed by a
    second text primitive reading exactly
    `overlay: authored locally, not read from the task definition` (D-60). That second line is not
    optional and is not abbreviated: it is what stops a viewer from being mistaken for ground truth.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| orchestrator HTTP (unauthenticated, `0.0.0.0:9000`) -> the sender process | An unauthenticated lab-network endpoint now supplies text that is rendered in the researcher's viewer. |
| ElasticSearch HTTP -> the sender process | Same, for the FDA state name. |
| researcher's `--overlay` string -> parser -> drawing | Free text becomes drawing instructions. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-10 | Spoofing | anything on the lab network can answer as the orchestrator; `/pilots/live` has no auth (`api.py`, `main.py:90`) | accept | Read-only display of data the lab network already exposes to every host on it; no decision, no actuation and no experiment record depends on it. Named rather than fixed: authenticating the orchestrator API is a backend change with its own blast radius and does not belong in a viewer plan. |
| T-38-11 | Tampering | a stale FDA state rendered as current | mitigate | No cache and no last-known-good path exists in `pilot_state.py`; a failed fetch renders `unavailable - <reason>`. Enforced by a grep gate in this plan's verify block. |
| T-38-12 | Tampering | the viewer being read as the FDA's own verdict | mitigate | D-60: the overlay is the researcher's own numbers and every render carries `overlay: authored locally, not read from the task definition`; `evaluate`'s docstring states the Pi computes its own conditions from its own tracker values. |
| T-38-13 | Denial of Service | a hung or slow HTTP endpoint stalling the process that feeds the Pi | mitigate | Every fetch takes an explicit timeout, asserted in the tests; every exception is caught and turned into a reading. Plan 38-03 puts these calls on their own thread so even a timeout cannot touch the inference loop. |
| T-38-14 | Denial of Service | an enormous or hostile JSON body | accept | Both endpoints are on the lab's own network and the responses are bounded by `size: 1` and by the pilot count; `json.loads` on a few kilobytes is not a hazard worth engineering around. Named so the choice is deliberate. |
| T-38-15 | Tampering | an overlay clause naming an undeclared signal, silently never satisfied | mitigate | `parse_overlay` refuses it at parse time and lists the declared `SIGNAL_NAMES`. | T-38-16 | Information Disclosure | subject keys, run ids and session ids drawn on frames a researcher may screenshot | accept | These are the researcher's own experiment identifiers, on their own machine, and seeing them is the point (they are how a screenshot is tied to a run). No personal data is involved. |
| T-38-SC | Tampering | npm/pip/cargo installs | mitigate | **This plan installs nothing and adds no dependency.** `json`, `urllib.request` and `dataclasses` are stdlib; `requests` is deliberately NOT used, because adding a dependency to the vision box's DLC environment for one GET is exactly the risk `RUNBOOK.md` step 2 warns about. The blocking human legitimacy checkpoint lives in plan 38-04. |
