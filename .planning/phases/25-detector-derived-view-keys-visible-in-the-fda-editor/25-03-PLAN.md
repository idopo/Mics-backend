<decisions>
**R1 — an out-of-range detector channel REUSES `view_key_unresolved`; it does not get its own
issue kind.** (25-CONTEXT lists this explicitly under Claude's Discretion.)

- The researcher-facing content is the same in both cases: *this operand cannot resolve on this
  pilot; here is what does exist.* `HardwareCheckModal` gains **one** read-only branch instead of
  two, and plan 05 task 1 stays as scoped.
- What differs is the *fix* (edit the channel vs edit the key vs edit the pilot's
  `first_channel`), and that is information, not taxonomy. It travels in **fields**: the issue
  gains an optional `detector: {"ref": ..., "channel": ...}` and `available_channels: [...]`
  alongside the existing `key` / `available_keys`. A renderer that ignores them still renders
  something correct.
- Rejected: a `detector_channel_unresolved` kind. It would force plan 05 to write and test a second
  branch, force every future consumer to learn two names for one condition, and buy nothing that a
  field does not.

**R2 — the resolver reports the RESOLVED KEY even though the definition does not store it.**
A `view_detector` issue's `detail` reads *"references MPR121 channel 5, which would be `LICKER5` on
this pilot — this pilot's MPR121 has channels 1–4 (`LICKER1`…`LICKER4`)."* The stored artifact stays
pilot-agnostic (CONTEXT D1); the **diagnostic** is allowed to be pilot-specific, because it is
generated per `pilot_id` and never persisted. Suppressing the resolved name here would make the
message strictly harder to act on for no gain.

**R3 — a `view_detector` whose `ref` names a module the pilot has no config row for is NOT
reported twice.** Step 6 already emits a `missing` issue for every toolkit module lacking a config,
and step 7's `already_flagged` set exists precisely to suppress the duplicate. Detector-ref issues
join that suppression. A `ref` naming a module that is not in the toolkit at all is a **save-time**
422 (plan 01 task 4) and cannot reach here on a definition that was saved after this phase.

**R4 — a `view_detector` whose channel IS in range produces nothing, even if the resolved Tracker
would be missing for some other reason.** Preflight resolves against the *declared* config, which
is the same declaration `check_for_detectors` consumes (DVK-01). If the two disagree the Pi is
wrong, not the definition, and inventing a speculative issue here would produce false rejections.
Precision over coverage: a false rejection on a preflight the researcher sees before every run is
worse than a missed one, because preflight is advisory and a noisy modal gets clicked through.
</decisions>

<interfaces>
**FDA JSON shape the scanner must cover** — the condition half is delegated; the action half is
this plan's:

```
fda_json
├── states: { <name>: { entry_actions: FdaAction[], wait_condition?: FdaCondition } }
├── transitions: FdaTransition[]        # condition_tree | condition_groups | conditions
└── trigger_assignments: [{ trigger_name, actions: FdaAction[] }]
```

View operands: `{"view": "KEY"}`, the DVK-11 `{"view_detector": {"ref": "MPR121", "channel": 2}}`,
and `{"tracker": "KEY"}` — which the scanner treats as a view key **for preflight purposes only**.

**`{"tracker": ...}` is NOT a view operand on the Pi, and this plan must not claim it is.**
`mics_task.py:545-549` maps both `tracker` and `flag` to `self.flags[key].value`; neither ever
touches `self.view`. The UI's `getOperandType` calls the form "tracker" and the FDA editor offers
it beside `view`, which is where the confusion comes from. Scanning it here costs nothing and can
only produce a **false negative** (a flag-shaped key that happens not to be a valid view key is
reported): the resolver's valid-key set already includes every toolkit flag and every declared
variable, so a legitimate `{"tracker": "some_flag"}` resolves clean. The UI/Pi naming mismatch is
pre-existing and out of scope — do not "fix" it here, and do not write a test asserting the Pi
reads `{"tracker": ...}` from the view.
View actions: `{"type": "view", "key_template": "...", "source_ref": "...", ...}`, with `if`
actions nesting further actions under `then` / `else`.

**New pure functions (plan 05 consumes the issue shape, not these signatures):**

```python
def scan_fda_view_keys(fda_json: dict) -> list[dict]:
    """Every place a view key or detector channel is named. Never raises.
    -> [{"location": "transitions[0].condition_tree.left",
         "kind": "operand" | "detector" | "key_template",
         "value": "LICKER0" | None,       # literal key, or raw template; None for a detector
         "ref": "MPR121" | None,          # detector ref, or a view action's source_ref
         "channel": 2 | None},            # detector channel only
        ...]
    """

def resolve_view_key_issues(fda_json: dict, valid_keys: set[str],
                            device_names: dict[str, str],
                            module_channels: dict[str, list[int]],
                            detector_keys: list[str],
                            skip_modules: set[str] | None = None) -> list[dict]:
    """-> preflight issues, in the shape preflight_validate already returns."""
```

`module_channels` is `{module_name: derive_channels(cfg)}` for this pilot — the DVK-11 range check.
`device_names` is `{module_name: cfg["device_name"]}` — used for both `{device_name}` template
resolution and R2's resolved-name diagnostic. `skip_modules` is step 7's `already_flagged` (R3).

**Issue shape (must match the existing contract so `HardwareCheckModal` can render it — plan 05
adds the branch):**

```json
{
  "module_id": null,
  "module_name": "MPR121",
  "issue": "view_key_unresolved",
  "detail": "Transition 0 condition operand references MPR121 channel 5, which would be 'LICKER5' on this pilot. This pilot's MPR121 has channels 1, 2, 3, 4 (LICKER1, LICKER2, LICKER3, LICKER4).",
  "location": "transitions[0].condition_tree.left",
  "key": "LICKER5",
  "available_keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"],
  "detector": {"ref": "MPR121", "channel": 5},
  "available_channels": [1, 2, 3, 4]
}
```

For a plain literal-key issue, `detector` and `available_channels` are **absent** and `detail`
reads *"names view key 'LICKER0', which this pilot does not have. This pilot's detector channels:
LICKER1, LICKER2, LICKER3, LICKER4."* — the R1 single kind, two shapes.

`module_name` carries the detector `ref`, or a `key_template`'s `source_ref`, or `""` when neither
applies. `module_id` is always `null` — the same convention `fda_ref_unresolved` already uses.

**Resolution rules — precision matters more than coverage; a false rejection trains researchers to
click through the modal.**

Valid key set for a pilot =
  derived detector keys (this toolkit's modules × that pilot's configs)
  ∪ toolkit flag names
  ∪ `fda_json["variables"]` names
  ∪ `{"trial_counter"}`
  ∪ the toolkit's hardware module names
The last one is not decoration: `task.init_hardware` does `self.view.view[pin] = hw`
(`task.py:~204`), so every module name really is a live `view.view` key, and `init_flags` writes
every flag into `view.view` too (`mics_task.py:307-308`). Rejecting those would be wrong.

Per scanned entry:
- **`kind: "detector"`** → if `ref` in `skip_modules`, report nothing (R3). Else if `ref` is not in
  `module_channels`, report nothing — step 6 already covers a module with no config, and a ref that
  is not a toolkit detector was a save-time 422. Else if `channel` not in `module_channels[ref]`,
  report one issue with the `detector` / `available_channels` fields and the R2 resolved name.
- **`kind: "operand"`** (always a literal key) → report if not in the valid set.
- **`kind: "key_template"` with no `{` tokens** → same as an operand.
- **`key_template` containing `{device_name}`** → the `ref` (its `source_ref`) must resolve to a
  config row on this pilot carrying a non-empty `device_name`; if it does not, report (DVK-08's
  negative case: "a definition whose key_template names a device that pilot does not have"). If it
  does, substitute `device_name` and then: if the remainder still contains tokens (the canonical
  `{device_name}{pin_number}`), **report nothing** — the key varies per interrupt and is
  unresolvable statically. If nothing remains (`{device_name}2` → `LICKER2`), check the resolved
  key against the valid set.
- **`key_template` with tokens but no `{device_name}`** → report nothing. Unresolvable statically.

The "report nothing" cases are deliberate (R4).
