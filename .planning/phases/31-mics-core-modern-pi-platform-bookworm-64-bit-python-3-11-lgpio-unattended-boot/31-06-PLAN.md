<instrument_design>
From `31-RESEARCH.md` `## Validation Architecture`. Reproduce the reasoning in
`tools/pulse_timing/README.md` — an instrument nobody can justify is an instrument nobody trusts.

**Method.** Jumper a spare output pin to a spare input pin. Claim the output normally; claim the
input for BOTH edges with **no debounce** (`gpio_set_debounce_micros` shifts every reported
timestamp by exactly the debounce window — Pitfall 3 — which would silently bias every number).
Command a pulse through **the production code path**, and read the resulting edge timestamps from
the alert callback. Measured width = `t_falling - t_rising`.

**Why this is right, not a compromise:** the measurement clock is the kernel's hardirq timestamp on
`CLOCK_MONOTONIC`, nanosecond resolution, taken as close to the physical edge as the hardware
allows. Both edges of a pulse ride the same clock through the same latency path, so **IRQ latency
largely cancels in the width difference** even though it does not cancel in the absolute timestamp.
Width accuracy is therefore much better than absolute-timestamp accuracy.

**Its honest limit, which must be in the README:** a loopback cannot distinguish "the output edge
was late" from "the input interrupt was serviced late", and under heavy load the input-side jitter
contaminates the measurement. That is why plan 10 includes a ONE-TIME cross-check with an external
observer (a ~£10 24 MHz USB logic analyser via `sigrok-cli`, 41.7 ns resolution, or a scope). After
that calibration, the loopback is the routine instrument — a scope is worse for routine use because
it cannot produce n>=1000 automatically.

**Profiles** (`profiles.py`, one dict per profile so a capture is named, not hand-typed):

| Profile | Stimulus | Why |
|---|---|---|
| `valve` | 1000 x one-shot 200 ms pulse, 300 ms apart | The reward-volume path. 200 ms is the duration actually in prefs. |
| `valve_short` | 1000 x one-shot 40 ms pulse | The odour / air-puff duration. |
| `ttl` | 1000 x TTL pulse at the configured `pulse_width`/`interval` | Sync-pulse width. |
| `train` | 60 s continuous `Pulse20Hz` train | Period jitter AND cumulative drift. |
| `mixed` | `valve` + `train` concurrently | The tx thread services all GPIOs from one loop; contention is the realistic case and is invisible in single-profile runs. |

Each profile x two load conditions (**idle**; **loaded** = `stress-ng --cpu 4 --io 2 --vm 1
--vm-bytes 128M --timeout 120s` plus a live ZMQ session generating CONTINUOUS traffic) x arms
(pigpio baseline as-is; lgpio at `SCHED_OTHER` and at `SCHED_FIFO:10`) = 30 captures, roughly one
afternoon of user-run work.

**Statistics** per profile x load x arm, n >= 1000 (`train` gives ~3600 at 62.5 Hz over 60 s):
`n`, `n_missing` (commanded vs observed edge pairs — **`n_missing > 0` is an automatic fail**),
`err_median` (systematic bias), `err_sd` (the jitter figure), `err_p99`, `err_max`, `err_iqr`
(reported alongside SD because the distribution is expected right-skewed), and for trains
`period_sd` and `rate_ppm` (slope of a least-squares fit of edge index vs edge time, as ppm
deviation from commanded — this is the cumulative-drift test). Report a table plus an ECDF of
`|err|` per arm. **Never report only the mean.**

**Gates.**
- **G1 (primary, comparative, needs no arbitrary numbers):** for every profile x load, the lgpio
  arm's `err_p99` and `err_sd` must be **<= 1.25x** the pigpio baseline captured on the same
  hardware in the same session, and `n_missing` must be 0 in every capture.
- **Absolute (secondary — they exist so a JOINTLY BAD baseline cannot pass by comparison alone),
  derived from the science not from what the hardware happens to do:**

| Profile | Statistic | Threshold | Derivation |
|---|---|---|---|
| `valve` (200 ms) | `err_p99` | <= 1.0 ms (0.5 %) | Reward-volume reproducibility; valve flow is roughly linear in open time and 0.5 % is well inside the solenoid's own volumetric variance. |
| `valve_short` (40 ms) | `err_p99` | <= 0.5 ms (1.25 %) | Same argument where relative error is larger. |
| `ttl` | `err_p99` | <= 200 us | The TTL is the cross-device alignment ground truth (Phase 28); its width need only be unambiguously detectable, but its EDGE is the alignment point. |
| `train` | `period_sd` | <= 200 us | ~1.2 % of a 16 ms period; below the temporal resolution of any downstream behavioural analysis. |
| `train` | `rate_ppm` | abs <= 100 ppm | Guards the drift-free property of absolute-deadline scheduling. A failure here means something is re-basing the schedule — a genuine bug. |

`31-RESEARCH.md` rates these thresholds MEDIUM confidence: they are proposed from the science, not
measured. **G1 is the gate that carries the weight.** Say so in the README.

**`--check-step` (PLAT-25):** given a capture taken across a forced clock step, assert
`t_mono_ns` strictly increasing with **no discontinuity** (the interval between the pulses
straddling the step equals the commanded interval within the profile's jitter budget); the derived
`t_utc` steps by **exactly** the applied amount and by nothing else (this is CORRECT behaviour, not
corruption — saying so is what keeps the claim honest); and the field width is 64-bit.
</instrument_design>

<backend_facts>
- **pigpio arm:** the tree today drives pulses through `Digital_Out.store_series()`/`series()`,
  which use pigpio daemon scripts (`store_script`/`run_script`/`script_status`/`stop_script`/
  `delete_script`, with a `PI_SCRIPT_INITING` polling loop at `gpio.py:673-681`). Edge timestamps
  come from `pi.callback()` ticks, 32-bit microseconds.
- **The patched `pigpio.py` is NOT in this repo.** `synchronize()` (`:5306`) and
  `ticks_to_timestamp()` (`:5320`) are Autopilot patches present only in the LIVE RIG's
  site-packages, not upstream and not vendored. `capture.py` must therefore **not** depend on
  them — use raw callback ticks and do the tick->seconds conversion in the harness. That keeps the
  baseline capturable on any pigpio install.
- **Counter wraparound (V2):** pigpio's tick is 32-bit microseconds and wraps every
  `2**32 / 1e6 / 60` = **71.58 minutes**, ~20 times a day under 24/7 operation. `capture.py` must
  detect and record a wrap in the pigpio arm rather than silently producing a negative interval.
  A single 75-minute baseline capture demonstrating the re-sync discontinuity is a plan-08 task;
  the harness must be able to record it.
- **lgpio arm:** `tx_wave` for one-shots, `tx_pulse` for repeating trains; edge timestamps from the
  `callback(chip, gpio, level, ts_ns)` argument — 64-bit nanoseconds, `CLOCK_MONOTONIC`, taken by
  the kernel in hardirq context. **Do not read a clock inside the callback**; the argument is the
  edge time, anything you read includes the full ppoll + FIFO + Python-dispatch latency (lgpio's
  alert thread polls with a 0.5 ms `ppoll` timeout).
- lgpio raises where pigpio returned negative numbers (`exceptions = True` module-global). Wrap
  every lgpio call in `try/except lgpio.error` and count failures; never let one escape a callback.
</backend_facts>
