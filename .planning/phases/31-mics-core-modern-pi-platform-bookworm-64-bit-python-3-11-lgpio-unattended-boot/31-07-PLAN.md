<objective>
Stage 2, part 3. One idempotent script that turns a stock Raspberry Pi OS Lite 64-bit (Bookworm)
card into a provisioned MICS rig.

Purpose: this is the phase goal's load-bearing sentence — "runs one installer script from a
`mics_core` clone, reboots, and the pilot comes up on its own". The hardware configuration surface
is genuinely small, which is the whole reason an installer is viable rather than an SD image: four
config lines (`dtparam=i2c_arm=on` — currently listed TWICE in the rig's file, `dtparam=audio=on`,
`dtoverlay=disable-bt`, `enable_uart=0`), one `/etc/modules` line (`i2c-dev`), and group membership
(`pi` in `i2c, gpio, spi, dialout`).

**Locked scope decision (CONTEXT §11.2): the installer OWNS THE BOX.** A dedicated rig Pi is
assumed — one per cage, doing nothing else. It may write `/boot/firmware/config.txt`, apt-install,
enable services, and disable Bluetooth. **No coexistence mode, no interactive prompting, no
`--dry-run` requirement.** This overrides `31-RESEARCH.md` Open Question 1's hedged recommendation.
That is what keeps the script small enough to be reviewable — which matters more than defensive
options nobody exercises.

Output: `install.sh`, a matching `uninstall.sh`, a static test, and a README section that says
"this script owns the box" in the first line.
</objective>

<verified_installer_facts>
Each of these is a verified finding, not a suggestion.

**`raspi-config nonint do_i2c 0` does the whole I²C job in one line** (bookworm branch, read
directly): the `dtparam` in the right file with `/boot/firmware/` auto-detection, un-blacklists
`i2c-bcm2708`, un-comments or appends `i2c-dev` in `/etc/modules`, and applies both live via
`dtparam` + `modprobe`. Its `set_config_var` is a lua-based idempotent upsert, so it is safe to
re-run. **Do not hand-edit `config.txt`, `raspi-blacklist.conf` and `/etc/modules` separately.**

**`/boot/config.txt` is a decoy.** Bookworm moved the firmware partition to `/boot/firmware`;
`/boot/config.txt` was a symlink and is now a **placeholder file** containing "DO NOT EDIT THIS
FILE — The file you are looking for has moved to /boot/firmware/config.txt", because scripts kept
breaking the symlink and then editing the wrong file. An installer written against the old path
reports success and does nothing. Detect the way raspi-config does
(`if [ -e /boot/firmware/config.txt ]; then FIRMWARE=/firmware; fi`) or just delegate to
`raspi-config nonint`.

**PEP 668 blocks system-wide pip.** Bookworm ships `/usr/lib/python3.11/EXTERNALLY-MANAGED`, so
`pip install` outside a venv exits with `error: externally-managed-environment`. Install into the
venv. **Do NOT pass `--break-system-packages`.**

**venv WITHOUT `--system-site-packages`** (PLAT-06). Verified empirically that
`--system-site-packages` also puts `~/.local/lib/pythonX.Y/site-packages` on `sys.path`, letting a
stray `pip install --user` shadow a pinned rig dependency. The **pigpio CLIENT** comes from the
`requirements.txt` pin (plan 03) into that venv — it is pure Python, so there is nothing to compile
and no platform wheel to miss. **Do NOT `apt install python3-pigpio`:** a system-wide client is
invisible to a `--system-site-packages`-free venv, so it would be dead weight at best, and at worst
it is a second, unpinned copy of the one library PLAT-28 requires to be pinned and unpatched.

**pigpio is INSTALLED, not purged — this inverted on 2026-08-17** (`31-REVISED-SCOPE.md` §3). An
earlier version of this plan purged `pigpio pigpiod python3-pigpio` because lgpio was going to
replace them and a stray daemon would have fought lgpio for a chardev line. The lgpio migration is
gone; **pigpio is the destination.** The installer must:

- `apt install pigpio` — the DAEMON (`pigpiod`), which is the DMA sampler and the genuinely hard
  part. It is stock and carries none of the clock defects this phase fixes; every defect lives in
  the ~50 patched lines of the Python client, which `requirements.txt` now pins from upstream.
  **This install is mandatory, and the reason is a hard runtime dependency rather than tidiness:**
  `autopilot/external/__init__.py:15` sets `PIGPIO = shutil.which('pigpiod') is not None`, and
  `start_pigpiod()` (`:31-32`) raises `ImportError('the pigpiod daemon was not found!')` when that
  is false. Without the package the pilot cannot start a session at all.
- **NOT** install a `pigpiod` drop-in, and **NOT** run `systemctl enable pigpiod`.
  **PLAT-33 was WITHDRAWN 2026-08-17 by user decision** (`31-REVISED-SCOPE.md` §5): the pilot keeps
  spawning the daemon. The stated reason was `external.start_pigpiod()`'s `atexit`/`SIGTERM`
  `kill_proc` hook (`:55-60`) — **but that reason was verified FALSE on 2026-08-17**: `proc` is the
  shell, not `pigpiod`, which daemonises because `PIGPIOARGS` carries no `-g`, so the hook never
  reaches it. The daemon already outlives the pilot today. The withdrawal stands by user
  instruction; its premise does not. See `31-REVISED-SCOPE.md` §5. Plan 05 therefore ships no `deploy/pigpiod-mics.conf`, so there is
  nothing to install; enabling the packaged unit would create exactly the outliving daemon the
  withdrawal exists to prevent. **If the apt package turns out to enable `pigpiod.service` by
  default, that is a finding for plan 09 to observe and report — do not pre-emptively disable it
  here, and do not enable it.**
- **NOT** install `python3-pigpio` (see the venv note above), and **NOT** purge anything pigpio.
  The "no `python3-pigpio`" rule is unchanged and independent of PLAT-33: the client is the
  `requirements.txt` pin inside the venv, and a second unpinned system-wide copy is exactly what
  PLAT-28 forbids.

Record the installed daemon version (`pigpiod -v`) in the install log: the rig currently runs a v78
source build in `/usr/local/bin`, and Bookworm's package is a different, packaged version. If a
`/usr/local/bin/pigpiod` from a source build is ALSO present on the card it will shadow the packaged
one on `PATH` — check for it and say so rather than ending up with two daemons. This matters more
now than it would have under PLAT-33: `shutil.which('pigpiod')` is exactly what the pilot resolves,
so whichever binary is first on `PATH` **is** the daemon the rig runs.

**Bluetooth off** (`dtoverlay=disable-bt`) matches the current rig's config and frees the PL011
UART. `enable_uart=0` likewise. Both go through `raspi-config`'s `set_config_var` if you can; a
direct idempotent upsert of `/boot/firmware/config.txt` is acceptable for `dtoverlay` lines, which
`set_config_var` does not manage.

**apt packages needed:** `python3-venv python3-dev i2c-tools chrony pigpio`. `git` is already present if
the user cloned the repo. Add `stress-ng` only if the loaded capture profile needs it — it does
(plans 08 and C4); put it behind a comment saying it is for the acceptance measurement, not for the
rig.

**`REPODIR`/`BASEDIR`/`VENV` in prefs are hardcoded to `/home/pi/Apps/mice_interactive_home_cage`
and `/home/pi/.venv/autopilot`.** The installer either honours those paths or parameterises them.
The `<installer_contract>` above chose `/opt/mics` and `/home/pi/.venv/mics`, so the TEMPLATE must
carry the new values and `render-prefs.sh` must emit them. If plan 04's template still holds the
old paths, fix the template here and say so — do not let the installer and the prefs disagree.

**The repo is private (404) on GitHub.** "Outside users clone it" stays blocked until that is
resolved. That is explicitly out of scope for this phase; the README may note it, and must not
pretend otherwise.
