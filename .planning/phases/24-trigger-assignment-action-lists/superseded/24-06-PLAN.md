<objective>
Remove the Python this phase exists to replace, and write the contract down.

Purpose: lick detection must run from a UI-assigned action list with **no Python callback registered
for `TOUCH_INT`**. What has to go is the *registration* — `detect_change()` mutates `self.prev`, so
while both callbacks sit in `self.triggers['TOUCH_INT']` whichever fires first consumes the change and
the other silently sees `(None, None)`, making the rig proof unfalsifiable. The `detectedLick` method
itself is unreachable once unregistered (no `CALLABLE_METHODS` on `learning_cage`, so FDA JSON cannot
call it either) and is **deliberately retained** as the reference implementation and a one-line
rollback.

Also fix the one thing that would make the whole mechanism silently produce nothing the day MPR121
stops living in `prefs.json`'s `I2C` group: `check_for_detectors` finds detectors with
`isinstance(v, Touch_Detector)` against the class imported at `mics_task.py:17`. A detector declared
through the backend hardware-module registry arrives under group `"Modules"` as a `source_code` string
that `_resolve_hardware_classes` `exec`s — a *different class object*, so the isinstance filter matches
nothing, `add_Tracker` is never called, `LICKER0…LICKER3` never exist, and the trigger's `view` action
writes into a view that has no such key. No exception, no lick data. `i2c.py` is off-limits, so the
fix belongs here: match on capability instead of identity.

Output: a `learning_cage` with no hard-coded lick handler, a `check_for_detectors` that survives the
registry path, and `.claude/docs/trigger_action_lists.md` carrying the schema, the canonical payload,

**2. Schema reference.** The five vocabulary additions this phase landed:

| Addition | Shape | Implemented in |
|---|---|---|
| `variables` registry | `"variables": {"name": {"initial_value": null}}` | `mics_task.load_fda_from_json` |

```json
{
  "variables": { "pin_number": {}, "level": {} },
  "trigger_assignments": [
    {
      "trigger_name": "TOUCH_INT",
      "actions": [
        { "type": "hardware", "ref": "MPR121", "method": "detect_change",
          "args": [], "output": ["pin_number", "level"] },
        { "type": "if",
          "condition": { "left": {"flag": "pin_number"}, "op": "!=", "right": null },
          "then": [
            { "type": "view", "key_template": "LICKER{pin_number}",
              "value": {"flag": "level"} }
          ],
          "else": [] }
      ]
    }
  ]
}
```

State explicitly that `pi_timestamp` appears nowhere in the payload and has no UI control: it is read
from the thread-local trigger context, is absent entirely outside a trigger, and an explicit
`kwargs.pi_timestamp` in a hand-written definition still wins.

State explicitly that the prefix is `LICKER`, not `MPR121`: `check_for_detectors` builds tracker keys
as `f"{detector.device_name}{i}"` and `prefs.json` sets `device_name: "LICKER"`, `num_detectors: 4`.

**4. Why the hardware returns a tuple.** Four electrodes share ONE `i2c.Touch_Detector` and ONE GPIO
interrupt (`TOUCH_INT`, pin 8). The interrupt says *something* was touched; the I2C query says
*which* electrode. The per-electrode abstraction is created in the view. This is deliberate
standardization — `hardware/i2c.py` is off-limits and `detect_change()`'s `(index, value)` return is
correct by design.

**Where LICKER0…LICKER3 come from, and what a detector must expose.** `check_for_detectors`
(`mics_task.py:241-266`) runs at `__init__` after `init_hardware()` and before `init_flags()`. It
scans **every** hardware group — including `"Modules"`, where backend-registry hardware lands — and
for anything exposing `num_detectors`, `device_name` and `read()` it calls
`view.add_Tracker(f"{device_name}{i}", read()[i])`. State the two consequences plainly:
- Discovery is **capability-based, not isinstance-based** (changed in this plan). A hardware module
  whose class arrives from the backend as `source_code` is `exec`'d into a fresh class object and can
  never be `isinstance` of the imported `i2c.Touch_Detector`; identity matching silently produced
  zero trackers.
- Detector trackers are **view-only**. `add_Tracker` writes `self.view.view` alone, whereas
  `init_flags` writes both `self.flags` and `self.view.view`. So `LICKER0` is readable as
  `{"view": "LICKER0"}` and writable by the `view` action's `key_template`, and will never resolve as
  `{"flag": "LICKER0"}`. Do not try to make detector trackers flags.

Add a forward pointer: the *derivation of those key names on the backend/UI side* — so the FDA editor
can offer `LICKER0…LICKER3` in transition-condition and `key_template` pickers instead of free text —
is the follow-up phase, not this one. `grep -rn "num_detectors\|device_name" api/ web_ui/react-src/src`
returns nothing today.
