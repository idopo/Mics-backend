<objective>
Take the "before" half of the acceptance measurement on the pre-migration image, and capture the
defect this phase exists to fix while the broken client is still running somewhere.

**The framing changed on 2026-08-17, and it changed honestly.** This plan used to open with "this
is a one-way door". It largely is not, and overstating it is how a plan loses credibility:

- **Nothing irreplaceable is being rescued.** The patched `pigpio.py` is **not** carried forward —
  PLAT-28 deletes it and pins stock upstream. No code is at risk here.
- **The baseline is measurement data, not an artifact of record.** It is re-derivable: reflash the
  spare card back to the Buster image and re-run the campaign. The cost of getting it wrong is an
  afternoon, not a capability.
- **What genuinely wants doing first** is (a) taking the paired arm on the *same board in the same
  session*, because pairing is what makes G1 meaningful without arbitrary absolute numbers, and
  (b) recording the wrap defect from the deployed client while a machine is running it. The live
  rig also runs it, and the file itself can be copied, so even this is recoverable — it is simply
  cheapest now.

So Task 0 stays, and it stays an exit code rather than agent discipline — not because the door is
one-way, but because a `capture.py` that cannot parse on Python 3.7.3 wastes a wired-up afternoon,
and that is worth two seconds of checking.

Output: committed baseline captures, a committed wrap-witness artifact proving the ~4294.97 s
backward jump, a calibration verdict, and the phase evidence log.
</objective>

  <action>
    AGENT: do not execute anything on the Pi.

    **Why this task exists.** The phase's central claim is that every GPIO event timestamp on the
    deployed rig jumps **backwards by ~4294.97 s every 71.6 minutes**, because the patched client's
    callback thread converts ticks with no wrap detection (`pigpio.py:1206-1207`) and holds its sync
    offset by value (`:5264` -> `:1157`), so the wrap-detecting re-sync on the `pi` object never
    reaches it — while `Event_Dispatcher`, which goes through the `pi` object, DOES re-sync. After
    the first wrap the two event paths are on different clocks. That is a specific, falsifiable,
    dated claim about a running system, and PLAT-29/PLAT-30 are written on it. **It must be
    demonstrated, not computed.** `2**32 / 1e6 = 4294.967296` is arithmetic; a file showing the jump
    against a monotonic reference is evidence.

    Note honestly what this does and does not prove: it demonstrates the defect in the **callback
    delivery path** of the deployed client on this board. It does not by itself prove the two event
    paths diverge — that needs both paths instrumented, which is plan C2's regression test on the
    dev host, and C4's soak on hardware. Say so in the evidence log rather than letting the artifact
    carry more weight than it has.
