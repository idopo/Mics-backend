<objective>
Make the camera's footage this system's own deliverable instead of IC Capture's by-product: one
ffmpeg invocation on the lab computer records to segmented files AND pushes the live feed to the
vision box, a generated PowerShell supervisor restarts it, and a four-witness test PROVES no frames
were lost while the DLC model consumed the same capture.

Purpose: CAM-18, under D-88. The researcher decided on 2026-09-10 to replace IC Capture. That makes
"all frames were saved" a claim this system has to be able to substantiate rather than assert.

Output: a pure command builder and a `dlc-link-relay` console script that PRINT the ffmpeg argv and
the PowerShell supervisor; a checked-in reference supervisor; a runbook acquisition section; and a
rig-session validation document carrying the measured transport decision, the measured encoder
decision, and the completeness ledger.
</objective>

<why_this_plan_exists_and_what_it_is_not>
Plans 38-01 through 38-06 build a camera that the model can SEE. This plan builds a camera whose
output is KEPT. They are different problems and the second one was not in scope until today.

Three things this plan is deliberately not:

1. **Not simultaneous IC Capture access.** That is D-75's multicast-monitor hatch; it needs the
   `imagingcontrol4` vendor stack, i.e. the whole CAM-17 / T5b build that confirming T5a made
   unnecessary. Recording at the source makes IC Capture *less* necessary — the footage exists
   without it — and does not make it concurrent. Stated once, here and once in the runbook, and not
   built toward.
2. **Not a fix for the unsupervised-host problem** (D-87, defect 8.6). A supervisor that restarts a
   dead ffmpeg is in scope because D-88 asks for it. Turning a dead relay into a LOUD failure on the
   vision box, or refusing to run a pilot on a stale `required` source, is Phase 18/32 substrate work
   and stays out.
3. **Not a second pilot run.** The Pi half is 38-04's. The completeness run loads the model and runs
   it with `--dry-run`, which satisfies "while the model runs" — inference genuinely consumes the
   capture — without starting, stopping or touching anything on a Pi.
</why_this_plan_exists_and_what_it_is_not>

<constraint_D88_did_not_state>
**The `tee` muxer does ONE encode and feeds the SAME packets to every slave.** D-88 says the delivery
leg binds MJPEG and that the file leg "may use H.264". With `tee`, that is only achievable by mapping
the video stream twice, encoding it twice, and giving each slave a `select=` option. A single `-c:v`
serves both legs or neither.

This is a refinement of D-88, not a contradiction of it, and it decides the builder's shape:

- **Default: one encode, MJPEG, both legs.** Cheapest, satisfies the per-frame-coding requirement for
  delivery, and an MJPEG file is large but robust — every frame is a keyframe, so a segment cut is
  exact and a truncated segment is still readable.
- **Escalation: the two-stream `select=` form.** Needed in either direction: if MJPEG cannot keep up
  on the file leg (hardware H.264 there, MJPEG delivered), or if MPEG-TS refuses to mux MJPEG (MJPEG
  file, all-intra `-g 1` H.264 delivered). The builder emits it when `file_codec != delivery_codec`.
  Whether it is NEEDED is §3/§4's measurement, not this plan's guess.

**Second unstated constraint: the tee muxer uses `\` as an escape character.** A Windows path inside a
tee slave spec is silently mangled. The builder therefore takes a **relative segment filename
pattern** with forward slashes only, and the caller sets ffmpeg's working directory. This removes the
drive letter, the backslashes and the colon from the tee spec entirely rather than escaping them, and
it is asserted by a test rather than discovered on the rig.

**Third: `-v error` would make witness 3 vacuously pass.** `frame dropped` is a warning from the dshow
demuxer. Any run whose log is a witness is captured at ffmpeg's DEFAULT verbosity with `-hide_banner`
and nothing else. The builder never emits a `-v`/`-loglevel` flag and a test asserts that.
</constraint_D88_did_not_state>

**Invariants that must hold for EVERY accepted `AcquireSpec`** (drive them with a parameterised
matrix: delivery on/off, mpjpeg/mpegts, single-encode/two-stream, duration set/unset):
    - no token of the argv, and no substring of the tee spec, contains `listen` — in any form
    - no token is `-v` or `-loglevel`; the builder never lowers verbosity
    - the tee spec's file slave contains no `onfail`
    - when a delivery leg exists, its slave contains `onfail=ignore`
    - the tee spec contains no `\`, no `[`/`]` outside the slave-option brackets, and no `|` inside a
      filename
    - `build_ffmpeg_argv` returns a `list` of `str` and never a single joined string
    - `-f dshow`, `-rtbufsize <value>` and `-i video=<device>` appear in that order before any output option
    - `-fps_mode passthrough` appears exactly once in the single-encode form; in the two-stream form
      `-fps_mode:v:0 passthrough` and `-fps_mode:v:1 passthrough` each appear exactly once and the bare
      `-fps_mode` does not
    - the segment slave carries `f=segment`, `segment_time=<n>`, `reset_timestamps=1`, `strftime=1` and
      `segment_format=<fmt>`

**Shape:**
    - with `delivery_url=None` the output is a PLAIN `-f segment` output and `-f tee` does not appear —
      a tee with one slave buys nothing and obscures the command
    - with a delivery URL and `delivery_codec` unset (or equal to `file_codec`), one `-c:v` is emitted,
      the stream is mapped once, and both slaves read the same encode
    - with `delivery_codec != file_codec`, `-map 0:v` appears twice, `-c:v:0`/`-c:v:1` are set, and the
      slaves carry `select=0` and `select=1` respectively
    - `select` is emitted unquoted for a single index; a multi-index select list is escaped as `\'0,1\'`
    - `duration_s` emits `-t <n>` immediately before `-f tee` (or before the plain segment output), and
      nothing when unset
    - `file_extra` and `delivery_extra` are passed through verbatim in order, after their codec flag

**Refusals** (`AcquireSpecError`, each with the reason in the message):
    - `segment_pattern` containing `\`, `:`, `|`, `[` or `]`, or being absolute — with the message naming
      the tee-escape hazard and telling the caller to pass a relative pattern plus a working directory
    - `segment_pattern` with no `%` strftime pattern — a non-templated name with `strftime=1` would make
      every restart overwrite the same file, which is the exact ambiguity segmenting exists to remove
    - `delivery_url` set with `delivery_format` unset, or vice versa
    - `delivery_format` not in `{"mpjpeg", "mpegts"}`
    - `device` empty
    - `duration_s` <= 0 when set

**Nothing hardcoded** — asserted by a test that reads `acquire.py`'s and `acquire_supervisor.py`'s own
source and fails on `132.77.`, `DMK `, `8080`, `D:` or any `http://`/`tcp://`/`udp://` literal. The
only literals allowed are ffmpeg flag names and the two format names.

**`build_supervisor_ps1`:**
    - the returned text's longest line is under 100 characters (a paste-safety assertion, not a style one)
    - it contains no `python`, no `py `, no `pip`, no `conda` token
    - it builds the argument array with one short `$a=@(...)` / `$a+=@(...)` assignment per logical group
      and invokes through `Start-Process -FilePath $ff -ArgumentList $a`
    - every attempt gets its OWN `-RedirectStandardError` path under the log directory, named with a
      timestamp and the attempt number, because `-RedirectStandardError` truncates and witness 3 needs
      every attempt's warnings to survive
    - `-NoNewWindow -Wait` is used, so the exit code is observable and no console window is needed
    - `-WorkingDirectory` is set to the segment directory, which is what makes the relative segment
      pattern legal
    - the restart loop is bounded by `max_restarts`, prints the attempt number and the previous exit
      code on each restart, and on giving up prints a line naming the exit code and the log path —
      a camera that is permanently gone must not spin silently forever
    - the text ends with a `Write-Host` line stating the segment directory and the log directory, so
      the operator can see the write footprint without reading the script

  <action>
Create `dlc_link/src/dlc_link/acquire.py` — pure, no imports beyond `dataclasses`, `typing` and
`posixpath` if needed. **No `cv2`, no `subprocess`, no `os.path` on Windows semantics, no network.**
Follow `source.py`'s precedent: this module decides, and nothing else in the package re-derives it.

Build the argv in this order, because ffmpeg's input options must precede `-i` and the order is part
of what the tests assert:

    -hide_banner  -f dshow  -rtbufsize <rtbufsize>  -i video=<device>
    [ -map 0:v  -map 0:v ]                        (two-stream form only)
    -c:v <file_codec> [ -q:v <file_quality> ] <file_extra...>        (single-encode form)
    -c:v:0 ... -c:v:1 ... <extras>                                   (two-stream form)
    -fps_mode passthrough   |   -fps_mode:v:0 passthrough -fps_mode:v:1 passthrough
    [ -t <duration_s> ]
    -f tee <tee_spec>        |   -f segment <segment options...> <segment_pattern>

`build_tee_spec` assembles `[k=v:k=v]name|[k=v:onfail=ignore]url`. Sort the option keys
deterministically so the tests can assert on an exact string rather than on substrings alone — a
builder whose output order drifts cannot be diffed against the checked-in reference script.

Create `dlc_link/src/dlc_link/acquire_supervisor.py` — `build_supervisor_ps1` emits text only. Keep
the emitted PowerShell boring: parameters at the top as `$var=` assignments with a comment naming what

### Part 5 — THE COMPLETENESS TEST: four witnesses, twice

The whole point of this plan. Run it **twice** — once with auto-exposure as found, once with exposure
pinned — because the auto-exposure caveat is discharged by a control run, not by widening a tolerance.

**Run A — auto-exposure as found.** 300 seconds, `-t 300`, the adopted transport and encoder, with
`dlc-link-live --dry-run --max-seconds 300` running on the vision box for the whole interval.
*Writes: 15 segments and one log.*

Collect, with the commands from Part 2:

| Witness | What it is | Where it comes from | Machine |
|---|---|---|---|
| **W1** | ffmpeg's final `frame=` total | the captured log's last `^frame=` line | lab |
| **W2** | summed `nb_read_frames` over every segment | `ffprobe -count_frames` | lab |
| **W3** | count of `frame dropped` lines | the same captured log | lab |
| **W4** | `frames_read` from the sender summary | `dlc-link-live`'s own output | **vision box** |

W4 is on a different machine with a different clock, which is what makes it independent.

**Also confirm ffmpeg actually stopped itself at 300 s.** If `-t` was ignored on the tee output, record
that as a defect and take the duration of record from the log's final `time=` instead of from the
request — a duration nobody verified is not a known duration.

**The decision table. Apply it as written; do not widen it.**

| Observation | Verdict |
|---|---|
| `W1 != W2` | **DEFECT.** The muxer or the disk lost frames ffmpeg believed it had written. Record it in §8; do not proceed to a rate comparison. |
| `W3 > 0` | **DEFECT.** Frames were delivered by the camera and lost at the capture buffer. The encoder or the disk cannot keep up. |
| `W3 == 0` and `W1 == W2` and `W2 < 30 x duration` | The camera delivered fewer frames than nominal. Under auto-exposure this is **NOT a loss** — record `W2 / duration_s` as the delivered rate together with the exposure state from Part 1. |
| `W4 > W1` | **DEFECT** and an impossible one: the consumer cannot have read more frames than the recorder muxed. Re-check that both numbers come from the same interval. |
| `W4 < W1` | **EXPECTED, not a defect.** The delivery leg is droppable by design and `LatestSlot` keeps only the newest frame. Record `W4` and `W4 / duration_s`; this is the simultaneity witness, not an equality. |

**Run B — exposure pinned.** This is the run that makes the nominal comparison sharp.

1. Stop ffmpeg. Open IC Capture. Untick Auto Exposure and set exposure to **1/60 s** (16.6 ms, safely
   inside the 33 ms budget a 30 fps frame interval allows). Untick Auto Gain and set a fixed gain that
   leaves the image usable. Record both values verbatim.
2. Close IC Capture. Re-run the identical 300 s command.
3. With exposure pinned, **the nominal comparison is now a real equality**:
   `W2` must equal `30 x 300 = 9000`.

   **The tolerance, stated before the run with its arithmetic:** `|W2 - 9000| <= 16`. That is at most
   one frame per segment boundary (`segment_time 20` over 300 s = 15 boundaries) plus one for the `-t`
   cut landing mid-interval. For MJPEG every frame is a keyframe, so segment cuts should in fact be
   exact and the expected discrepancy is 0 — the 16 is a ceiling, not a budget.

   **A discrepancy larger than 16 with `W3 == 0` and `W1 == W2` is a DEFECT and gets a row in §8.
   It is not an occasion to widen the tolerance.** Exposure is pinned, so exposure is no longer an
   available explanation.
4. Record whether you restored the original auto settings afterwards, and if not, say so — the next
   session inherits whatever you left in the driver (§2.4).
