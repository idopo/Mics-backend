<objective>
Close the gap that would make the whole clock refactor invisible in production.

**The finding, verified 2026-08-24 against the live database.** Hardware classes on the Pi do not
come from the repo file. `api/routers/toolkit_dispatch.py:99-104` ships
`hardware_lib_versions.source_code` inside the START payload and `mics_task.py:222`
**`exec()`s it**; `orchestrator_station.py:977-983` separately writes the same source to
`~/apps/hardware_overrides/`. The database, not the tree, is what runs.

The database *has* the new file - version **159** of lib 8 is byte-identical to C2's `gpio.py`. But
the resolution chain is pin -> toolkit_default -> stable -> active
(`api/lib_version_resolution.py:29-70`), and:

```
hardware_libs id=8 (GPIO Driver):  stable_version_id=25   active_version_id=159
toolkit_hardware_libs:  106->(8:25)   105,104,100,95,94,88,84,24->(8:19)
task_definitions:       434 pins {"8": 25}
toolkit 154 (door_test): no gpio pin at all -> falls through to stable = 25
```

**Not one toolkit and not one task definition resolves to 159.** Every backend-dispatched run on a
Phase-31 Pi would exec gpio v19/v25 - 265 diff lines old, no `_edge_timestamp_adapter` - against
C2's `task.py`. The failure is silent and worse than the defect being fixed: raw stock-pigpio ticks
reach `execute_trigger`, `hardware._edge_source_for()` returns `None` so
`task.py:261-262`'s `or TS_HARDWARE` **labels it hardware-captured**, and `localize_tz` reads
microseconds as nanoseconds and emits a plausible ISO string. A wrong hardware-stamped value is
indistinguishable from a correct one once it is in Elasticsearch - `gpio.py`'s own comment says so.

`hardware/__init__.py` (lib 7, version 13) is stale by 173 lines for the same reason: C2 put the
per-edge slot there.

Purpose: make the deployed artifact a **published build of the tree**, not a hand-maintained copy,
and make a mismatch between a pilot's clock contract and its gpio version a refusal rather than a
silent deployment.

Output: a publisher, a drift test that is red before the publisher runs, a repointed resolution
table, and a symmetric dispatch-time contract guard.
</objective>

<repo_boundary_deviation>
**This plan deliberately breaks the phase's repo boundary, and says so rather than smuggling it.**

ROADMAP's Phase 31 entry says *"all code changes land in `~/mics_core` on the dedicated feature
branch, never in `mics-backend`"*. That rule was written when the phase was believed to be Pi-only.
It is not: the artifact the Pi executes is a **backend database row**, so a Pi-only phase cannot
deliver a Pi-only fix. Landing this in a later phase would ship Phase 31 in a state where its
central claim is false in production, which is worse than the boundary change.

<what_the_resolver_actually_does>
Read `api/lib_version_resolution.py` before touching anything. Two rungs matter here and both are
counter-intuitive:

1. **`toolkit_default` outranks `stable` and `active`.** A toolkit pin is not a preference, it is a
   freeze. Publishing a new version and promoting it to stable changes **nothing** for a toolkit
   that carries a `default_version_id`. Repointing those pins is therefore the substance of Task 3,
   not its bookkeeping.
2. **The `active` rung is a deliberate documented deviation** (the module docstring explains it:
   implementing the literal chain would break every toolkit whose lib has no promoted stable).
   Do not remove it and do not reorder the chain. This plan changes *data*, and adds a *guard* -
   it does not re-litigate the chain.
</what_the_resolver_actually_does>
