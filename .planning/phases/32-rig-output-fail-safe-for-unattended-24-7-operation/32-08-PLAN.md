<objective>
Make the two pilot-scoped faults visible: `pigpiod_unavailable` (A2) and `task_start_failed` (A4).

Purpose: FAULT-02 — `core/pilot.py:797` catches `ImportError`, sets `self.pigpiod = None` and logs;
every GPIO device then fails downstream, and `PI_TRIXIE_INSTALL.txt` already lists "the pilot comes
up without a GPIO daemon" as a known symptom of the sudoers path mismatch. FAULT-04 —
`core/pilot.py:578` sets `state = "IDLE"` and logs, while the backend has already marked the run
`RUNNING` and the watchdog will not notice for 30 seconds; this is also the input to RECOV-02's
ordering gap.

`subject`, `session` and `run_id` — physically cannot carry them. They use the pilot-level
`node.send(self.parentid, KEY, {...})` path that `HARDWARE_LIB_TEST_RESULT` already uses, into the
`PILOT_FAULT` handler plan 06 built.

Output: a reporting helper and two emitter pairs (raise and clear) in `pilot.py`.

**Nothing in this plan reaches a Pi.** It edits the branch in `/home/ido/mics_core`; the user
deploys with their own `git pull`.

<!-- Verified ordering facts. Getting these wrong produces an AttributeError at pilot startup. -->

**`init_pigpio()` runs BEFORE `self.node` exists.** In `Pilot.__init__`:
line 201 `self.init_pigpio()`; line 220 `self.networking = Pilot_Station()`; line 225
`self.node = Net_Node(...)`. So A2's emitter cannot call `self.node.send` at the moment it fires.
It must buffer, and something must flush the buffer after the node exists.

`self.parentid` is set at lines 185/188 — `prefs.get('PARENTID')` with the literal `'T'` as
fallback — so it IS available at line 201.

**`handshake()`** (line ~516) is the flush point and the reconnect point in one. It is registered as
`self.networking.set_handshake_callback(self.handshake)` at line 222 and sends
`self.node.send(self.parentid, 'HANDSHAKE', value=hello)`. Flushing there means a standing fault is
re-delivered whenever the pilot reconnects — which is also what makes the fault survive an
orchestrator restart, since the orchestrator's in-memory `_pilots` starts empty.

**`init_pigpio()`** (line ~796) today:
`try: self.pigpiod = external.start_pigpiod(); log debug` / `except ImportError as e:
self.pigpiod = None; self.logger.exception(e)`. `external.start_pigpiod` raises `ImportError` when
the binary is not on PATH and `RuntimeError` when `shutil.which` returns None after the PATH check —
the second currently propagates and stops pilot startup.

**`l_start()`** (line ~560) today: a broad `try` around task-class resolution,
`prefs.set('SUBJECT', ...)`, and the `threading.Thread(target=self.run_task, ...).start()`, with
`except Exception as e: self.state = "IDLE"; self.logger.exception("couldn't start task: {}".format(e))`.
`value['subject']` and `value.get('run_id')` are available in that scope and belong in the fault
detail — a `task_start_failed` that does not say which run it was is much less useful.

**The orchestrator's payload contract** (plan 06's `on_pilot_fault` docstring): `pilot` (optional),
`fault_key` (required), `state` (`"raised"` | `"cleared"`, default `"raised"`), `severity`
(`"warn"` | `"error"`), `message` (str), `detail` (dict).

**Excluded from this work:** `Message` and `hardware_state`. Do not touch either.
**Not in this plan:** the run-scoped sites A1, A3 and B1 — those are plan 09, and plan 09 also
edits `pilot.py`, which is why these two are separated by wave.
