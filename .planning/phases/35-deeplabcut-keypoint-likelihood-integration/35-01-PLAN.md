`DecimateStats`: integer counters `considered`, `passed`, `suppressed_deadband`, `suppressed_rate`,
plus `snapshot()` returning them as a dict. Counts only; no timing figure of any kind, and no
field whose name or value could be read as a latency (module docstring must state this and cite
DLC-10).

`Decimator(deadband=None, min_interval_ms=None, default_deadband=0.0, default_min_interval_ms=0,
clock=time.monotonic)`: `deadband` and `min_interval_ms` are per-signal-name dicts overriding the
defaults. `clock` is injected exactly as `Pacer` injects it, so tests drive it with a list-backed
fake and never sleep.

`should_send(name, value)` returns `True`/`False` and always increments `considered`.
Order of checks, which matters: (1) first sample for a name always passes — there is no previous
value to compare and no previous send time; (2) rate cap — if `min_interval_ms` for this name is
greater than zero and the elapsed time since this name's last PASSED send is below it, increment
`suppressed_rate` and return False; (3) deadband — if the value is numeric and
`abs(value - last_passed_value)` is at or below this name's deadband, increment `suppressed_deadband`
and return False; (4) otherwise increment `passed`, record the value and the send time under this
name, return True. A non-numeric value (bool or str) skips the deadband check entirely and is
governed by the rate cap alone. Rate-cap and deadband state are recorded against the last PASSED
send, never against the last considered sample — otherwise a stream of suppressed samples silently
slides the reference and the signal never updates again.

Add a module-level `RECOMMENDED_DEFAULTS` dict documenting, with the arithmetic written out in a
comment, the D-22 budget: likelihood deadband `0.02`, coordinate deadband `0.002` (about two
pixels on a one-thousand-pixel frame, since coordinates are normalised 0..1 per D-18), and a
per-signal cap of `100` ms (10 Hz). The comment must state the resulting budget explicitly —
2 bodyparts times 3 signals at 10 Hz is 60 messages per second, which is Phase 18's proven
envelope — and must state the two consequences from D-21 that make this load-bearing: the Pi has
no ingress queue, so ingress runs synchronously on the Tornado IOLoop that also serves the STOP
channel; and every accepted signal emits one CONTINUOUS Elasticsearch event, a one-to-one
amplification, so the message rate IS the Elasticsearch load.

Add `reset()` clearing per-name state and counters, so a long-running process can start a fresh
accounting window per run.
