Teach the hardware-libs AST extractor to recognise `@signal` / `@event` / `@command` /
`@decoder` and emit an `extlink` block in `ast_metadata` — so the FDA editor and future
state-builder UIs can render typed forms without importing the lib.

Purpose: the decorators declare the wire contract once per class. Without this, every consumer
of an `ExternalHardware` lib would have to import and execute it to know what signals exist —
impossible on the backend, which has no `autopilot` and no rig hardware.

```python
def extract_ast_metadata(source_code: str) -> dict:
    tree = ast.parse(source_code)
    classes = []
    for node in ast.walk(tree):
        if not isinstance(node, ast.ClassDef): continue
        methods = []
        for item in node.body:
            if not isinstance(item, ast.FunctionDef): continue
            args = []
            for arg in item.args.args:
                if arg.arg == "self": continue
                args.append({"name": arg.arg,
                             "annotation": ast.unparse(arg.annotation) if arg.annotation else None})
            defaults = item.args.defaults
            for i, default in enumerate(defaults):
                args[len(args) - len(defaults) + i]["default"] = ast.unparse(default)
            methods.append({"name": item.name, "args": args})
        classes.append({"name": node.name, "methods": methods})
    return {"classes": classes}
```

    Create `api/extlink_ast.py` with `EXTLINK_DECORATORS` and `extract_extlink_metadata`.

    **The one real trap (18-RESEARCH.md Pitfall 5):** `@signal(default=0.0,
    stale_after_ms=200)` is all literals, but `@event(payload={"object": str, "confidence":
    float})` is NOT `ast.literal_eval`-safe — `str` and `float` are bare `ast.Name` nodes
    referencing builtins, and `literal_eval` raises `ValueError: malformed node or string` on
    them. Walk the `ast.Call` node's keywords by hand:
    - `ast.Constant` value -> take `.value`
    - `ast.Dict` value -> zip `keys`/`values`, take each key's `.value`, and `ast.unparse` each
      VALUE node into a string (`"str"`, `"float"`)
    - anything else -> `ast.unparse` into a string

    Everything the extractor emits is STRING-typed. It cannot import the lib — the backend has
    no `autopilot`, no `pigpio`, and no rig hardware — so a real `type` object is not obtainable
    and must not be faked.

    `dtype` for a `@signal` resolves from the method's RETURN ANNOTATION first, then from
    `type(default)` rendered as a string, mirroring the Pi-side `resolve_dtype` chain
    (EXTLINK-12). When neither is available, emit `dtype: null` rather than raising — the
    extractor's job is description, not enforcement; the `TypeError` belongs at class-build time
    on the Pi where the real annotation object exists.

    A bare `@signal` (no parentheses) is an `ast.Name`, not an `ast.Call` — handle both forms.
    `@command` and `@decoder` will usually be bare.

    A class with zero `@signal` must produce `signals: {}` and no error (EXTLINK-18 —
    control-only modules are legal and are exactly what OpenEphys's HTTP side is).

    Keep the file under 150 lines. It is pure `ast`; no DB, no FastAPI, no imports from
    `routers/`.
