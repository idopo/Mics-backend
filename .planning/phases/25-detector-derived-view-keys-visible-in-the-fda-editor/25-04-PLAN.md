conditions, state-body operands, trigger action lists (DVK-03), and the `view` action's
`key_template` (DVK-04) — while preserving the keep-current-value escape that lets an unknown
stored key survive a round trip (DVK-05) and keeping detector keys out of the flag picker
(DVK-07).

so `LICKER0` is currently unreachable *even by typing*. Attaching MPR121 to a toolkit surfaces
`MPR121` — the device — and never its channels. This is the visible half of the phase.

Output: one new pure `.mts` module with real automated tests, plus prop threading and three
picker changes.
</objective>

<decisions>
**D4 — no Vitest. Automated React coverage comes from Node's built-in test runner over pure
`.mts` modules.** Proven working in this repo on node v24.14.0 during planning:
`node --test "tests/**/*.test.mts"` passes, `npx tsc --noEmit` stays clean, and `npx vite build`
still succeeds. Zero new dependencies, no change to `vite.config.ts`, `tsconfig.json` or the
web_ui Dockerfile.

Mechanics that make it work — follow them exactly, they were each a failure during planning:
- The pure module must be `.mts`, not `.ts`. **Corrected reason (the earlier one was wrong and is
  recorded here so nobody re-derives it):** Node does *not* refuse a bare `.ts`. With no
  `"type": "module"` in `web_ui/react-src/package.json`, node v24 emits a
  `MODULE_TYPELESS_PACKAGE_JSON` warning, reparses the file as ESM, and named imports of **real
  runtime exports** resolve fine. The *"does not provide an export named …"* failure seen during
  planning came from importing a **types-only** module as a value import (see task 1) — a
  different bug entirely. `.mts` is kept anyway because it is ESM unambiguously and by extension,
  emits no warning, and does not depend on a reparse heuristic. (Adding `"type": "module"` to
  package.json instead would touch the vite build for every future change — still rejected.)
- Test files live in `web_ui/react-src/tests/`, **outside** `tsconfig.json`'s `include: ["src"]`,
  so `tsc` never type-checks the `node:test` / `node:assert` imports and `@types/node` is not
  needed.
- `.tsx` files import it as `./detectorOptions.mts` **with the extension** — the repo already sets
  `allowImportingTsExtensions: true` and `noEmit: true`, so `tsc` accepts it and Vite resolves an
  explicit path directly.
- `node --test tests/` (directory form) does **not** pick up `.mts`. The working invocation is
  `node --test "tests/**/*.test.mts"`, quoted.

Rejected: scoping a Vitest + jsdom + testing-library setup in this phase. It changes
`npm install` in the web_ui Docker builder stage for all future work, and the failure mode of
these particular changes (a wrong option list) is instantly visible in the editor and is covered
end to end by plan 06's rig checkpoint. Rendering and interaction stay manual-only; the *logic*
that decides which keys are offered does not.

**D5 — one option builder, not per-component logic.** Everything that decides which keys appear,
how they are grouped, and whether a stored key is unknown lives in `detectorOptions.mts`. The
components become dumb renderers. This is what makes DVK-03/04/05 automatically testable at all,
and it is the reason `ConditionBuilder` and `ViewActionFields` cannot drift apart.
</decisions>

**New pure module `src/components/detectorOptions.mts`:**

```ts
export interface ViewOptionGroup { label: string; keys: string[]; warning?: string }

/** Grouped view-operand options. Detector channels are their own group per device. */
export function buildViewOptions(
  hwNames: string[], flagNames: string[], detectors: DetectorChannelGroup[],
): ViewOptionGroup[]

/** Is `key` offered anywhere in `groups`? Drives the DVK-05 unknown flag. */
export function isKnownViewKey(key: string, groups: ViewOptionGroup[]): boolean

export interface KeyTemplateSuggestion { insert: string; label: string; hint: string }

/** DVK-04: what the key_template field offers instead of free typing. */
export function buildKeyTemplateSuggestions(
  detectors: DetectorChannelGroup[], variableNames: string[], sourceRef: string | null,
): KeyTemplateSuggestion[]
```

`buildViewOptions` group order and labels — the grouping IS the requirement, do not flatten:
1. `{label: "Hardware", keys: hwNames}` — devices (`MPR121`), the thing that *produces* channels.
2. one group per detector, **labelled by the device name, not the module name**:
   `{label: "LICKER channels", keys: [...], warning?: ...}`.

   The label is `` `${group.device_names.join(' / ')} channels` `` — the user names the device, and
   the label must follow that name so a rename is visible where the keys are picked. Fall back to
   `` `${group.module_name} channels` `` only when `device_names` is empty (which the backend
   should never emit — a group with no device name derives no keys and is omitted). Two entries in
   `device_names` means pilots disagree on the name itself; the joined label surfaces that.

   **Never derive the prefix by stripping digits off a key.** That re-implements the key format in
   TypeScript — the duplication DVK-01 exists to prevent — and it breaks for any `device_name`
   ending in a digit (`SPOUT2` × 4 channels → `SPOUT20…SPOUT23`, from which no regex can recover
   `SPOUT2`). The prefix arrives from the backend or not at all.

   When `conflict` is true, `warning` reads
   `"pilots disagree: pilot_a has LICKER0…3, pilot_b has LICKER1…4"` built from `by_pilot`.
3. `{label: "Flags & variables", keys: flagNames}`.
Empty groups are dropped. Keys are deduplicated across groups by first occurrence.

`buildKeyTemplateSuggestions` returns, in order:
- `{insert: "{device_name}", label: "{device_name}", hint: "resolves on the pilot at run time from the action's source device"}` — **only when `sourceRef` is set**, because
  `fda_validation` hard-422s a `{device_name}` template with no `source_ref`. When `sourceRef` is
  null the entry is still returned but with a hint saying a source device must be picked first;
  the caller renders it disabled.
- one `{insert: "{<name>}"}` per declared variable (this replaces the existing raw pill list, same
  behaviour, now single-sourced).
- one literal entry per detector key (`{insert: "LICKER2", hint: "pilot-specific — prefer {device_name}"}`).
  These are offered because a state body legitimately writes one fixed channel, but the hint must
  say they hard-code a pilot.

**Existing behaviour that must survive verbatim (DVK-05):**
`ConditionBuilder.tsx:85` — `{!viewOpts.includes(key) && key !== '' && <option value={key}>{key}</option>}`.
That line is the only reason a stored `LICKER0` on a toolkit without detectors is not silently
rewritten to `""` on the next save. Keep the escape; add the flag.

**Prop threading route — `detectorChannels` goes exactly where `variableNames` already goes:**
```
TaskEditor.tsx
 ├─ ConditionGroupsEditor  (line ~813, transition condition modal) → ConditionRow → OperandEditor
 ├─ StateBodyPanel         (line ~759) → ActionEditor → IfActionEditor → ConditionRow
 │                                                    → ViewActionFields
 └─ TriggerAssignmentPanel (line ~784) → ActionEditor → (same two)
```
Every one of those components already declares `variableNames?: string[]` and forwards it. Add
`detectorChannels?: DetectorChannelGroup[]` next to it and forward identically. No new context,
no new store.
