<objective>
Build the two pure state machines that make a quiet sender look alive and a Pi restart survivable:
heartbeat scheduling and the connect/disconnect state machine.

Purpose: SDK-05 is what makes EXTLINK-07's split observable from the sender side — a source that
has nothing to report stays `alive == true` while its signals go stale under their own declared
policy. Without it an idle sender silently looks dead. SDK-07 is what lets a researcher restart a
pilot without also restarting a running acquisition.

Both are built here as PURE functions/objects with injected clocks and synthetic events, with zero
sockets and zero threads — that is 34-RESEARCH.md's Pattern 3 and the reason plan 34-06 can wire
them to a real ZMQ monitor without any of this logic being untestable.

Output: `heartbeat.py`, `reconnect.py`, and their two test modules.
</objective>

**Heartbeat default must survive Windows' sleep granularity (SDK-14).** Below Python 3.11 on
Windows, `time.sleep()` resolution is ~15.6 ms (the default WinAPI timer period); Python 3.11+ uses
high-resolution waitable timers. The vision box is Windows and its Python may be 3.9 or 3.10.

Consequences for this plan:

- Choose `DEFAULT_HEARTBEAT_S` well above 15.6 ms so the granularity is irrelevant to liveness —
  a value on the order of ~1 s against the fixture's `stale_ms: 3000` already satisfies this. State
  the reasoning in the module docstring alongside the `stale_ms` derivation.
- **No test may assert a scheduling interval finer than ~20 ms**, even with the injected clock,
  if that assertion could ever be re-pointed at a real clock. The tests here use an injected clock
  and must stay that way — say so explicitly so nobody "improves" them into real sleeps that then
  flake only on Windows.
- `heartbeat_due` / `HeartbeatSchedule` stay pure and clock-injected; nothing in this module calls
  `time.sleep`. That is already the plan and it is what makes the OS difference a non-issue here.
</amendments>

<decisions>
## Decisions locked by this plan

1. **`DEFAULT_HEARTBEAT_S = 1.0`.** Derivation, to be written into the module docstring: the one
   real fixture observed on the rig (`ExtlinkDemo`, `pilot_hardware_config` row 21) uses
   `stale_ms: 3000`, and the Pi's own liveness poller checks at `stale_ms / 2`. A 1:3
   heartbeat:timeout ratio is the standard keepalive convention and survives one dropped or
   delayed heartbeat. The caller must NEVER have to look this number up in a database row
   (CONTEXT.md) — it is a constructor kwarg with a safe default. Document that a Pi configured with
   `stale_ms` below ~3s needs an explicit override.

2. **Any outbound frame refreshes the heartbeat timer.** The Pi's `default_liveness` is
   `(now - last_msg_ts_ms) < stale_ms` over ALL inbound messages, not heartbeats specifically —
   so a sender streaming signals at 60 Hz does not also need to inject heartbeats. `note_sent` is
   therefore called on every outbound frame, and `heartbeat_due` suppresses the HB while traffic
   flows. This is a real load reduction for the Phase 35 soak, not a micro-optimisation.

3. **`on_state_change` fires on EDGES ONLY**, with the signature `on_state_change(connected: bool)`
   — a single bool, because CONTEXT.md's additive principle says a researcher must be able to write
   `lambda ok: print(ok)` and be done. Repeated `MONITOR_CONNECTED` events while already connected
   produce nothing.

4. **`MONITOR_RETRIED` does NOT change state.** libzmq emits `CONNECT_RETRIED` on every reconnect
   attempt; treating it as a disconnect would produce a stream of spurious edges during a normal
   backoff. It is recorded (a `retries` counter) and logged at debug level, nothing more.

5. **No exception ever escapes.** `ConnectionState.apply` wraps the callback in
   `try/except Exception` and logs the failure at warning level. A callback that raises must not
   break the IO thread, and a caller who ignores the callback entirely must be safe (CONTEXT.md).

6. **`seq` continuity is a NON-ACTION here.** SDK-07 permits maintained-or-reset; CONTEXT.md locks
   MAINTAINED. `reconnect.py` therefore must not touch, own, or reference a sequence counter at
   all — the guarantee is structural (plan 34-01's `SeqCounter` has no reset), and the assertion
   that a reconnect leaves it climbing belongs to plan 34-06's integration test. Add a comment in
   `reconnect.py` saying exactly this, so nobody later "helpfully" adds a reset on reconnect.

7. **No latency, jitter or round-trip timing is computed anywhere in this plan.** There is no ACK
   for HB on this wire — it is fire-and-forget by design — so any timing number here would be
   meaningless. Phase 28 owns clock-domain comparison.
</decisions>
