<leading_hypothesis>
## H1 — the two sides of the liveness subtraction are on DIFFERENT clocks (mics_core only)

Verified by reading both trees, 2026-08-31. The executor MUST re-confirm these five readings before
acting on them; they are the whole basis of the fix.

1. `mics_core/autopilot/autopilot/hardware/external_hardware_binding.py` `_now_ms()` returns
   `int(time.time() * 1000)`, and its comment says it is *"deliberately NOT converted through the
   one clock"* (Phase 31 Plan 10's F7 exempts the site by name).
2. `_liveness_tick(owner, pred)` in the same file calls `pred(owner._last_msg_ts_ms, now_ms, owner.stale_ms)`
   with that `time.time()`-derived `now_ms`.
3. `external_hardware_wire.default_liveness(last_msg_ts_ms, now_ms, stale_ms)` returns
   `(now_ms - last_msg_ts_ms) < stale_ms` — a bare subtraction of the two.
4. `mics_core/.../external_hardware_ingress.py` `on_recv` sets `owner._last_msg_ts_ms = ts_ms`
   where `ts_ms` comes from `_now_ms_and_mono_ns()`: `clock.now_from_tick()` (the pigpio-tick
   fitted mapping) converted by `MicsClock.to_utc_ns`. That is the ONE CLOCK, not `time.time()`.
5. `pi-mirror/.../external_hardware_ingress.py` stamps `int(time.time() * 1000)` instead.

So on the `mics_core` stack, `now_ms` (system wall clock) is subtracted from `last_msg_ts_ms`
(pigpio-tick-derived), and the difference includes whatever offset the fitted tick mapping carries
at that moment. If that offset exceeds `stale_ms` (3000 ms for the demo fixture) the device reads
dead forever while frames are arriving; if it is negative and large the device reads alive forever.
Intermittency across runs ("2 of 4") is exactly what a mapping re-fit at pilot start produces. On
`pi-mirror` both sides are `time.time()` and the bug cannot occur — which matches the fact that the
symptom appeared as the rig moved to `mics_core`.

**The permitted fix is lib-level, never substrate-level.** A `liveness_hook` override that reads
the CURRENT time from the same source the ingress stamp came from restores a like-for-like
comparison without touching a single Pi file. `make_liveness` (external_hardware_wire.py:170-173)
REPLACES the default with the override, so the hook owns the decision completely.

## Competing hypotheses to rule out before concluding H1

- **H2 — the egress probe, not liveness.** `recompute_alive` is `liveness_alive and not owner._egress_failed`.
  `ExtlinkDemo`'s egress probe targets `132.77.73.125:5597`; with that TCP echo listener down,
  three failed probes at 1/s trip `egress_fail_threshold: 3` and `alive` flips false about three
  seconds into every run regardless of liveness. This would look identical from Elasticsearch.
  **Confirm 5597 is open before drawing any conclusion from any run in this plan.**
- **H3 — poller cadence.** `bind_liveness` sets `interval_s = (stale_ms / 2) / 1000`, so with
  `stale_ms: 3000` the predicate is evaluated every 1.5 s and a false reading can persist up to
  that long after the fact. This affects the timing of an observation, not its truth value.
- **H4 — a genuine `ClockNotReady`/`ClockFault` fallback.** `_now_ms_and_mono_ns` falls back to
  `int(time.time() * 1000)` and counts the fallback. If the pilot is in permanent fallback, both
  sides are on `time.time()` again and H1 predicts NO failure — which would itself be a finding.
</leading_hypothesis>
