<objective>
Add the third mechanism to the same `ExecStopPost` hook: de-energise the I2C motor shield.

Purpose: SAFE-10. `DOOR1`, `DOOR2` and `MOTORIZED_REWARD` are `i2c.Motor_Shield_Hat_extend`, whose
`set()` calls `throttle(self.id, ±1)` with **no timed stop** — the motor runs at 100% until
something calls `throttle(None)`. `Motor_Shield_Hat.release()` does exactly that and, like every
other release, runs only on a polite shutdown. So a pilot dying mid-door-move leaves a DC motor
stalled at full throttle against the door frame, drawing stall current indefinitely, unattended.
This is the highest-energy hazard on the rig.

Neither of the other two mechanisms reaches it: a GPIO write does nothing to an I2C device, and a
pull-down on a Pi pin does nothing to a motor driven by a HAT with its own supply.

Output: an I2C section in `deploy/mics-failsafe.sh`, tests that count the write, and a written
answer on the motor rail.
</objective>

<!-- What the rig actually does today, and why prefs.json cannot be the trigger. -->

`/home/ido/mics_core/autopilot/autopilot/hardware/i2c.py`:
- `Motor_Shield_Hat.__init__` constructs `MotorKit(address=0x60)` inside a bare `try/except` that
  logs `'failed to initialize Motor hat shield!'` and continues — so a missing HAT is silent, and
  the comment on that line records that `i2cdetect` reports both `0x60` and `0x70`.
- `Motor_Shield_Hat.throttle(motor_number, speed)` assigns `self.kit.motorN.throttle = speed`.
- `Motor_Shield_Hat.release()` sets `motor1..motor4.throttle = None` — the polite-shutdown-only path.
- `Motor_Shield_Hat_extend.set(bool)` maps `True -> throttle(id, -1)` and `False -> throttle(id, 1)`.
  There is no zero and no timer.

**prefs.json cannot tell the hook a motor exists.** `mics_task._merge_prefs_hardware` persists only
the backend's `PREFS_HARDWARE` payload — pin/id config. The class comes from the separate
`HARDWARE` dispatch spec (`class_name` + `source_code`, exec'd at `_resolve_hardware_classes`) and
is **never written to prefs.json**. `_merge_prefs_hardware` even overwrites `type` with the group
name when the backend sends none, which is why three template entries read `"type": "Modules"`.
Motor entries carry `id`, not `pin`, so plan 03's numeric-`pin` selector correctly ignores them.

**Consequence for the design:** the I2C de-energise must be **unconditional on the bus**, not
conditional on a declaration. Attempt it whenever the address answers. That is the same
"de-energise more lines, never fewer" rule SAFE-03 applies to GPIO, and it removes the entire class
of failure where a motor was driven but the config no longer says so.

**`32-DISCOVERY.md` §7 `I2C target:` is the input** — which address answered `i2cdetect -y 1`, and
what MODE1 (`register 0x00`) read. The PCA9685 `SLEEP` bit is bit 4 of MODE1, mask `0x10`; setting
it drops all 16 PWM channels at once. `0x70` is the PCA9685 all-call address. If §7 records
`I2C target: UNRESOLVED`, stop and say so — do not pick an address.

**Guard:** `command -v i2cget i2cset`. If absent, log
`mics-failsafe: i2c-tools absent, motor shield NOT de-energised` and continue. A missing tool must
be loud in the journal, never silent — it is exactly the condition under which someone would
believe the fail-safe covered the motors when it did not.

**Address:** take it from `32-DISCOVERY.md` §7 `I2C target:` and bake it in as a named variable
`PCA9685_ADDR`. Alongside it define `PCA9685_ALT_ADDR` for the second address `i2cdetect` reported,
and attempt both in turn, because §7's reading was taken on one rig on one day and the all-call
address is a legitimate second path to the same device. Attempting an address that does not answer
costs one failed `i2cget` and a log line.

**Presence probe before writing:** `i2cget -y 1 <addr> 0x00`. If it fails, log
`mics-failsafe: addr=<..> no response, skipped` and move on. Do not treat a non-responding address
as an error condition for the script as a whole.

**The write:** set the MODE1 `SLEEP` bit. Read MODE1 with `i2cget -y 1 <addr> 0x00` first, OR in
`0x10`, and write the result back with `i2cset -y 1 <addr> 0x00 <value>`. Read-modify-write, not a
blind `i2cset ... 0x10` — MODE1 also carries `RESTART`, `EXTCLK`, `AI`, `SUB1-3` and `ALLCALL`, and
clobbering them would change how the device behaves on the next `MotorKit` init. Log the before and
after values.

Add a comment stating in one or two lines why `SLEEP` and not zeroing the sixteen channel
registers: one register write drops all channels at once, so it is both faster inside
`TimeoutStopSec` and atomic with respect to a second kill arriving mid-sequence. Record the
channel-zeroing alternative in the same comment so a later reader knows it was considered.

**Read back and verify:** `i2cget -y 1 <addr> 0x00` after the write and log whether bit 4 is set.
Emit one line per attempted address in the form
`mics-failsafe: i2c addr=<..> mode1_before=<..> mode1_after=<..> sleep=<set|unset> result=<ok|fail|absent>`.

**Bound it** with the same `timeout 2` wrapper the GPIO section uses.
