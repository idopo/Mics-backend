or the orchestrator. It exists because Phase 26 must close the orphaned-recording gap Phase 18 could

  <name>Task 1: REST surface — URLs, payloads, and the injectable transport</name>
  <files>api/openephys_client.py</files>
  <behavior>
    - set_mode issues exactly one PUT to /api/status with {"mode": mode}
    - build_recording_config raises ValueError naming any key outside the six real fields
    - Every function accepts a `client` so no test can reach the network
    - `httpx` is used, not requests — it is already an api/ dependency
  </behavior>
  <action>
    Create the module. **Read `26-REST-SURFACE.md` FIRST** and set `RECORDING_CONFIG_FIELDS`,
    the status mode strings, and `NODE_DIR_FORMAT` from what the rig actually returned. If that
    record says DEFERRED, use the documented defaults and add a module-level comment naming the
    deferral and the plan-26-13 checkpoint that closes it.

    - `base_url(host, port)` → `http://{host}:{port}`. Normalize a host that already carries a
      scheme or a trailing slash — a config value typed by a human will eventually contain both.
    - Every network function takes `client=None`. When `None`, use `httpx` with `DEFAULT_TIMEOUT_S`;
      when supplied, call the injected object's `.get`/`.put`. **Timeouts are mandatory on every
      call** — an unreachable OE box must fail fast into a preflight issue, never hang a request
      thread.
    - `set_mode` PUTs `{"mode": mode}` to `/api/status` and raises on a non-2xx. Validate `mode` is
      one of the three legal values before the call; a typo must fail locally, not silently put the
      rig in an unexpected state.
    - `build_recording_config(**fields)` raises `ValueError` naming any key not in
      `RECORDING_CONFIG_FIELDS`. `set_recording` routes through it. **An invented field silently
      ignored by OE is the worst outcome** — the recording would land wherever OE's stale config
      pointed, which the persisted path would then misreport.
    - `send_message(host, port, text)` PUTs `{"text": text}` to `/api/message`.

    Do NOT catch exceptions here. Callers decide policy: preflight turns a connection error into an
    issue (plan 26-09), the stop registry swallows it (plan 26-08). A client that swallows errors
    makes both impossible.
  </action>
  <verify>
    <automated>docker compose up --build -d api && docker compose exec -T api python -m pytest -q api/tests/test_openephys_client.py -k "set_mode or recording_config_payload"</automated>
  </verify>

  <name>Task 2: Never-take-over decision and read-back path composition</name>
  <files>api/openephys_client.py</files>
  <behavior>
    - A status of RECORD makes decide_start return (False, reason) with zero PUT calls issued
    - resolved_path_from_recording composes from record_nodes values, never from constants
    - The node-directory separator is honoured as a parameter
  </behavior>
  <action>
    - `is_already_recording(status)` reads the mode key confirmed in `26-REST-SURFACE.md` and
      returns True for the RECORD state. Be tolerant of case and of a missing key (a missing key is
      NOT "not recording" — return a value that makes `decide_start` refuse, because an
      unparseable status means we do not know, and "never take over" beats "assume it's free").
    - `decide_start(status) -> (may_start, reason)`. Pure — it issues no calls at all. This is what
      makes plan 26-01's "zero PUTs" assertion meaningful: refusal is a decision made before any
      request is built, not an exception caught afterwards.
    - `compose_resolved_path(...)` joins `parent_directory` / the composed directory name /
      `node_dir_format.format(id=record_node_id)` / `experiment{N}` / `recording{M}`. The format
      string is a **parameter with a module-constant default** — the separator was undocumented and
      is only known from the rig probe, so it must never be an inline f-string literal.
    - `resolved_path_from_recording(recording, node_dir_format=...)` pulls
      `parent_directory` and `record_nodes[i].{node_id,experiment_number,recording_number}` out of a
      real `GET /api/recording` response and calls the composer. **Always read back; never predict.**
      When several record nodes exist, compose one path per node and return them in a stable order,
      because a signal chain with two record nodes writes two directories and persisting only one
      would misreport where half the data is. Document the multi-node return shape in the docstring.
      Raise a clear `ValueError` when `record_nodes` is absent or empty — that means OE is not
      configured to record at all, which must surface loudly rather than persist an empty path.
  </action>
