Make plan 03's preflight result visible (DVK-06, and the pilot-specific half of DVK-11) and make
DVK-09's `first_channel` declarable from the UI instead of by hand-editing raw config JSON.

Purpose: an issue kind `HardwareCheckModal` does not recognise renders as `null` — the researcher
sees a modal listing nothing and cannot tell why the start was gated. And `first_channel` will
never be offered by the existing config template builder, because that builder derives its fields
from the class's `__init__` AST args and `Touch_Detector.__init__` does not take one
(`i2c.py:957`, off-limits).

Output: one new read-only branch in the preflight modal, one conditional field in the pilot
hardware config editor.
</objective>

**The landmine in the existing modal — read this before writing the branch.**
`handleStart` (`HardwareCheckModal.tsx:309-333`) loops over **every** issue and unconditionally
PUTs `/api/pilots/{pilotId}/hardware-config/{module_name}`. For a `view_key_unresolved` issue that
would either overwrite a good MPR121 config with `{}` or PUT to an empty path segment. The issue
kind must be filtered out of that loop, and out of the `pendingEdits` initialiser above it. This
is not a nicety — without it, opening the modal and clicking Start destroys the pilot's detector
config, which is precisely the data DVK-09 and DVK-11 both depend on.

**`is_detector` on the module read** (plan 03 task 3b) —
`GET /api/hardware-modules/{id}/methods` gains `"is_detector": true|false`. Module 7 (MPR121,
class `Touch_Detector`) is `true`; module 8 (TOUCH_INT, `Digital_In`) is `false`.

**d. The `issues.map` React key — a real duplicate-key bug this plan creates.**
`HardwareCheckModal.tsx:345` renders `issues.map(issue => <div key={issue.module_name}>…)`. That
was safe while every issue named a distinct module. Plan 03 emits **one `view_key_unresolved` issue
per scanned key or channel**, with `module_name` set to the detector ref, the `source_ref`, or `""`
— so two bad channels on the same MPR121 produce two `<div>`s with the same key. React then
reconciles them into one another and the second issue can render the first's content or vanish.
This is now MORE likely than under the old design: picking two wrong channels from one detector is
a single natural mistake.

Change the map to carry the index and key on something unique:
```tsx
{issues.map((issue, i) => (
  <div key={`${issue.issue}:${issue.module_name}:${issue.location ?? i}`} …>
))}
```
Index-throughout (`key={i}`) is also acceptable — the list is never reordered or filtered in
place. Pick one and do it for the whole map, not just the new branch.

**Explicitly: do NOT add a blocking gate.** `handleStart`

to stop the rig. Say this in the summary, and plan 06's success criteria repeats it so the rig
tester does not record "it started anyway" as a defect.
