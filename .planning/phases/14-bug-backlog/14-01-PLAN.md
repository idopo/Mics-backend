## BUG-01: Boolean_Tracker.set double-logs to Elasticsearch

### Root cause

`Tracker.set` has `@log_action` (line 21 of `Tracker.py`). `Boolean_Tracker.set` also has `@log_action` AND ends with `super().set(new_value, **kwargs)` (line 44–47). Because `Tracker.set` is the resolved target of `super().set()` and is also decorated, the `log_action` wrapper fires **twice** for a single logical set call — both with `event_type: "Boolean_Tracker"`, `func_name: "set"`, `value: 0`. Two identical ES documents are dispatched per call.

The same pattern exists in:
- `Counter_Tracker.set` (lines 64–68) — calls `super().set(new_value, **kwargs)`
- `Trial_Tracker.set` (lines 94–98) — calls `super().set(new_value, **kwargs)`

Confirmed in ES run 441 (lines 14–15 of ES output): two identical `Boolean_Tracker / set / 0` events.

### File

`~/pi-mirror/autopilot/autopilot/utils/Tracker.py`

### Fix

In all three subclass `set()` methods, replace `super().set(new_value, **kwargs)` with direct assignment:

```python
# Boolean_Tracker.set (line 44-47)
@log_action
def set(self, new_value, **kwargs):
    if not isinstance(new_value, bool):
        raise ValueError("Boolean_Tracker can only be set to a boolean value.")
    self.value = new_value   # was: super().set(new_value, **kwargs)

# Counter_Tracker.set (line 64-68)
@log_action
def set(self, new_value, **kwargs):
    if not isinstance(new_value, int):
        raise ValueError("Counter_Tracker value must be an integer.")
    self.value = new_value   # was: super().set(new_value, **kwargs)

# Trial_Tracker.set (line 94-98)
@log_action
def set(self, new_value, **kwargs):
    if not isinstance(new_value, int):
        raise ValueError("Trial_Tracker value must be an integer.")
    self.value = new_value   # was: super().set(new_value, **kwargs)
```

`Tracker.set` only does `self.value = new_value`, so this is functionally identical. The subclass `@log_action` still fires and logs one event; the parent wrapper is never invoked.

**Do NOT remove `@log_action` from `Tracker.set`** — `Tracker` instances used directly would lose logging.

### Verification

Call `boolean_tracker.set(False)` on a live Pi run and confirm exactly one ES document appears for that call (not two).

## BUG-02: PilotSessions list does not show the most recently created session

### Symptom

The pilot session window (`/react/pilots/:pilot/sessions-ui`) consistently skips the most recently created session. The list always starts from the second-to-last created session.

### Investigation

**API layer (`GET /sessions`, `api/main.py:845`):**
```python
runs = session.exec(select(SubjectProtocolRun)).all()
by_session = {}
for r in runs:
    by_session.setdefault(r.session_id, []).append(r)
for session_id, sruns in sorted(by_session.items(), key=lambda kv: kv[0], reverse=True):
```
- Sessions are sorted by `session_id` (int) descending — correct in isolation.
- `SubjectProtocolRun` rows are queried without `ORDER BY`, which is fine for grouping.
- Only sessions with at least one `SubjectProtocolRun` record appear. A newly created session **must** have at least one run to be visible here.

**React layer (`PilotSessions.tsx:33`):**
```typescript
const { data: sessions } = useQuery({ queryKey: ['sessions'], queryFn: getSessions })
```
- No `staleTime` override → defaults to 0 (immediately stale).
- React Query refetches on component mount when stale. If the component is already mounted and a new session was created on another page, the cache is **not** automatically invalidated — the stale data is shown until the next mount or window focus.

**Most likely root cause:** When a session is created (from the protocols or subject-sessions page) while PilotSessions is **already mounted** or its cache was populated in the same SPA session, the `['sessions']` query cache is never explicitly invalidated. The user sees the pre-creation list (N sessions) even though N+1 now exists.

**Secondary candidate:** `GET /subjects/{name}/runs` (`api/main.py:191`) has no `ORDER BY`. `SubjectSessions.tsx` reverses the array to derive session order. If DB returns rows in non-insertion order (e.g., after vacuuming or in a replica), `.reverse()` produces wrong session order. This is the same symptom for the subject-sessions view.

### Fix

**Step 1 — Confirm root cause by inspection:**
After creating a new session, call `GET /api/sessions` directly via curl. If the new session appears in the response, the bug is in the React cache layer. If it doesn't appear, the bug is in the API.

**Step 2A — If React cache (most likely):**
Add `refetchOnMount: 'always'` to the sessions query in `PilotSessions.tsx` so it always fetches fresh data when the component mounts:

```typescript
// PilotSessions.tsx line 33
const { data: sessions, isLoading } = useQuery({
  queryKey: ['sessions'],
  queryFn: getSessions,
  refetchOnMount: 'always',
})
```

**Step 2B — If API ordering (secondary):**
Add `ORDER BY` to `GET /subjects/{name}/runs` endpoint in `api/main.py:191`:

```python
runs = session.exec(
    select(SubjectProtocolRun)
    .where(SubjectProtocolRun.subject_id == subject.id)
    .order_by(SubjectProtocolRun.session_id.asc())
).all()
```

This ensures `SubjectSessions.tsx`'s `.reverse()` gives newest-first regardless of DB storage order.

### Verification

1. Open PilotSessions. Note the top-listed session ID.
2. Create a new session from the protocols or subject-sessions page.
3. Return to PilotSessions. The new session (higher ID) should now appear at the top within one render cycle (or immediately after mount with `refetchOnMount: 'always'`).
