<objective>
Distinguish three end-states instead of two, and close the 5 s / 30 s ordering gap.

Purpose: RECOV-01 — a task error (the Pi is alive and reports `TASK_ERROR` in-band), a service crash
(nobody on the Pi can report it) and a user pressing Stop are different events with different
correct responses. The vocabulary already exists; what is missing is that **silence alone cannot
separate "process crashed", "Pi powered off" and "network partition" — only the reconnect
distinguishes them**. RECOV-02 — `Restart=always` / `RestartSec=5` brings the pilot back in 5 s but
the watchdog does not mark the run `ERROR` until it has sat `RUNNING` for 30 s, so there is a window
where the process is up and idle while the backend still believes the run is live.

**The trap this plan exists to avoid.** Reconciling on any handshake is wrong. The pilot's
`_handshake_watchdog` (`networking/station.py:1267-1288`) re-sends `HANDSHAKE` whenever it has not
heard a `PING` from the orchestrator for more than 21 seconds — **including mid-run**. A naive
"handshake means the pilot restarted" rule would kill a healthy run during a network hiccup. The
discriminator has to be whether it is the same process, not whether it said hello.

Output: a per-process incarnation id, a reconnect reconciliation gated on it, and consumption of the
Pi's own `task_end` reason where one was reported.
</objective>

<!-- Verified shapes and the two facts that make a naive implementation destructive. -->

**The pilot re-handshakes mid-run.** `networking/station.py:1267` `_handshake_watchdog` fires every
10 s and calls the handshake callback when `now - self._last_ping_from_orch > 21`. So HANDSHAKE is
not a restart signal.

**`Pilot.handshake()`** (`core/pilot.py:516`) builds
`hello = {'pilot': self.name, 'ip': self.ip, 'state': self.state, 'prefs': prefs.get(), 'tasks': tasks_payload}`
and sends it as `HANDSHAKE`. Adding one key to that dict is the whole Pi-side change.

**`OrchestratorStation.on_handshake`** (`orchestrator_station.py:76-186`) calls `_redis_touch`,
`state.update_handshake(pilot, payload)`, then a large backend-sync `try` block ending in
`except Exception as e: logger.error("Backend sync failed for pilot %s: %s", ...)`. Reconciliation
must NOT live inside that try — a backend-sync failure must not swallow it.

**`state.update_handshake`** deliberately preserves `active_run` across a handshake update
(`state.py:26-31`), and plan 06 extended it to preserve `device_health` too. So after
`update_handshake`, `state.get_active_run(pilot)` still returns whatever the orchestrator believed
before the handshake — which is exactly what the reconciliation needs to compare against.

**The existing watchdog** `_run_watchdog` (`orchestrator_station.py:1062-1116`) polls every 5 s,
looks at each pilot's `active_run`, and after `elapsed > 30` calls
`self.api.mark_run_error(run["id"], error_type="WatchdogTimeout", error_message=...)` then
`self.state.set_active_run(pilot, None)`. Note it does **not** call `_redis_set_active_run(None)` —
so Redis keeps a stale `active_run` after a watchdog timeout and `/pilots/live` keeps showing it.
Fix that while you are here; it is the same bug class this plan is closing.

**`on_task_error`** (line 496) is the model for the full cleanup sequence: `mark_run_error`,
`release_device_leases_for_run`, `state.set_active_run(None)`, `_redis_set_active_run(None)`.
Reuse that sequence rather than writing a second one.

**`_handle_data(value)`** (line 579) is the ES ingestion path; every `CONTINUOUS` event the Pi
dispatches arrives here as a dict with a `subject` key. Plan 09's `task_end` event flows through it,
carrying `event_type='task_end'` and an `event_data` dict with `reason`, `error`, `error_type`,
`run_id` and `subject`.

**`SessionRunStatus`** (`api/models.py`) = `RUNNING / STOPPED / COMPLETED / ERROR / PENDING`.
`session_runs.error_type` and `error_message` are free-form strings today carrying `TaskError`,
`OrchGatewayError` and `WatchdogTimeout`. This plan adds `PilotRestarted`. No migration is needed —
they are `String` columns.

| Pi HANDSHAKE payload -> run lifecycle decisions | A pilot-authored field now determines whether a run is marked ERROR |
| Pi CONTINUOUS events -> run status writes | A data-path event now triggers a backend state change |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-34 | Denial of service | A pilot sending a fresh incarnation on every handshake would kill live runs every 21 s | mitigate | Test 2 asserts one incarnation per process instance; Test 9 asserts an unchanged incarnation reconciles nothing; the reconciliation additionally re-reads the run and requires status `running` |
| T-32-35 | Tampering | A `task_end` event relabelling a run a user deliberately stopped | mitigate | Tests 14 and 19 both assert terminal-status runs are left alone, in the reconnect and data paths respectively |
| T-32-36 | Denial of service | A classification failure stopping ES ingestion | mitigate | `_classify_task_end` is wrapped and runs before an unconditional ES dispatch; Test 18 asserts the event reaches ES for every reason value |
| T-32-37 | Spoofing | A rogue device claiming a pilot identity and forcing a run ERROR | accept | ZMQ DEALER identity on a lab-local network is the existing trust model for `on_task_error` and every other handler; this plan adds no new authentication surface and does not weaken the existing one |
