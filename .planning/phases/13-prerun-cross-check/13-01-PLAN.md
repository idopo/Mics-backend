# Phase 13, Plan 1: Pre-Run Cross-Check

**Requirements:** HW-21, HW-22, HW-23, HW-24
**Phase goal:** Before starting a task, backend verifies pilot has all required hardware configured. On issues, UI lets user fix inline. After a real trial run, hw lib versions are promoted to stable.

**Gate:** Requires Phases 09–12 complete.

---

## Context

The Pi already receives pilot hardware config via `PREFS_HARDWARE` in the `START` payload — this is handled by `toolkit_dispatch.py` → `_inject_backend_toolkit_spec()` → `mics_task._merge_prefs_hardware()`. No new ZMQ messages are needed.

This plan adds the **pre-run gate** (validate before sending START) and **lifecycle close** (promote beta libs to stable on first real trial).

---

## Implementation

### Step 0: Store `class_name` in `pilot_hardware_config` (prerequisite for class_mismatch check)

**File:** `api/routers/pilot_hardware_config.py`

**Problem:** The class_mismatch check requires knowing what class the pilot config was stored with. Currently `pilot_hardware_config.config` never contains `class_name` — the seed endpoint strips the Pi's `"class"` key, and the PUT endpoint stores only what the UI sends.

**Fix:** Modify the PUT upsert endpoint to auto-inject `class_name` from the `HardwareModule` record:

```python
@router.put("/api/pilots/{pilot_id}/hardware-config/{module_id}")
def upsert_pilot_hardware_config(pilot_id: int, module_id: int, body: UpsertConfigBody, token=Depends(verify_token)):
    with _SA_SessionLocal() as session:
        module = session.get(HardwareModule, module_id)
        if not module:
            raise HTTPException(status_code=404, detail="hardware module not found")
        # Inject class_name so preflight class_mismatch check has a value to compare
        config_to_store = {**body.config, "class_name": module.class_name}
        row = session.query(PilotHardwareConfig).filter_by(pilot_id=pilot_id, hardware_module_id=module_id).first()
        if row:
            row.config = config_to_store
        else:
            row = PilotHardwareConfig(pilot_id=pilot_id, hardware_module_id=module_id, config=config_to_store)
            session.add(row)
        session.commit()
        session.refresh(row)
        return {"id": row.id, "pilot_id": row.pilot_id, "hardware_module_id": row.hardware_module_id}
```

**Seed endpoint:** Add `class_name` from the matched `HardwareModule` record:

```python
config = {k: v for k, v in hw_cfg.items() if k != "class"}
config["class_name"] = module.class_name   # authoritative from DB, not Pi-reported
```

**Verification:** `PUT /api/pilots/{pilot_id}/hardware-config/{module_id}` with `{"pin": 7}` → stored config contains `{"pin": 7, "class_name": "Digital_Out"}`.

### Step 1: Server-side preflight validate endpoint

**File:** `api/routers/toolkit_dispatch.py`

```
POST /api/sessions/{session_id}/preflight-validate/{pilot_id}
```

The UI cannot reliably know the `task_definition_id` — this must be resolved server-side from the session's protocol step.

Logic:
1. Load session → get `protocol_id` and current step index
2. Load protocol step → get `task_definition_id` (if present)
3. If no `task_definition_id` or toolkit is not backend-authored: return `{ok: true, issues: [], skip_reason: "not_backend_authored"}`
4. Load task definition → get `toolkit_id`
5. Load toolkit → get `hardware_module_ids`
6. For each `hardware_module_id`:
   a. Load hardware module → get `name`, `class_name`
   b. Check `pilot_hardware_config` for `(pilot_id, hardware_module_id)` row
   c. If no row: issue `{module_name, issue: "missing", detail: "Pilot has no config for module {name}"}`
   d. If row exists but config has no keys other than `class_name`: issue `{module_name, issue: "incomplete_config", detail: "..."}`
   e. If `config.get("class_name")` is not None and differs from `hardware_module.class_name`: issue `{module_name, issue: "class_mismatch", detail: "Config has class {stored}, module expects {expected}"}` — skip check if `class_name` absent (legacy rows)
7. Return `{ok: bool, issues: [...]}`

Also return `module_id` per issue so the React modal can call PUT directly:

```json
{
  "ok": false,
  "issues": [
    {
      "module_id": 3,
      "module_name": "Left_LED",
      "issue": "missing",
      "detail": "Pilot T has no config for hardware module Left_LED"
    }
  ]
}
```

### Step 2: Pre-run check + inline fix modal in session start UI

**File:** `web_ui/react-src/src/pages/subject-sessions/SubjectSessions.tsx`

Before confirming START:

1. Call `POST /api/sessions/{session_id}/preflight-validate/{pilot_id}`
2. If `ok: true` or `skip_reason` present: proceed with start as usual
3. If `ok: false`: show `HardwareCheckModal` — do not start

**File:** `web_ui/react-src/src/components/HardwareCheckModal.tsx` (new)

The modal lets the user fix config issues inline and then start — no need to navigate away. All fixes write to `pilot_hardware_config` via `PUT /api/pilots/{pilotId}/hardware-config/{moduleId}`. Never write to task definitions or toolkit records.

Props:
```ts
interface HardwareCheckModalProps {
  issues: PreflightIssue[];   // from preflight response
  pilotId: number;
  onStart: () => void;        // called after saves, triggers actual session start
  onCancel: () => void;
}
```

Modal content:
- Title: "Hardware Configuration Required"
- For each issue, show module name + human-readable explanation
- **`class_mismatch`:** editable `class_name` text input pre-filled with the stored (wrong) value; note shows "Expected: {hardware_module.class_name}". Saving via Start button calls `PUT /api/pilots/{pilotId}/hardware-config/{moduleId}` with updated config.
- **`missing`:** inline key-value entry form (generic `key` / `value` add-row inputs). Saving via Start button calls `PUT` to create the config row.
- **`incomplete_config`:** existing config fields rendered as editable inputs. Saving via Start button calls `PUT` with updated values.
- **"Start" button** (bottom): saves all pending inline edits sequentially via PUT, then calls `onStart()`. No automatic recheck — user decides when ready.
- **"Cancel" button**: close modal without starting.

### Step 3: Orchestrator — stable promotion on INC_TRIAL_COUNTER

Closes the hardware lib lifecycle: a real trial run confirms a lib version works on hardware, promoting it from beta → stable.

**File:** `orchestrator/orchestrator/orchestrator_station.py`

In `_handle_inc_trial()`, after the graduation check, add stable promotion:

```python
def _handle_inc_trial(self, value: dict):
    subject_key = value.get("subject")
    if not subject_key:
        return
    run = self.api.get_run_by_subject_key(subject_key)
    if not run or run.get("status") != "running":
        return
    resp = self.api.increment_trial(run["id"])
    if resp.get("should_graduate"):
        self._advance_run_step(run)

    # Stable promotion: a real trial run confirms the hw lib works on hardware
    pilot = self.api.get_pilot(run["pilot_id"])
    if pilot:
        pilot_key = self.state.resolve_pilot_key(
            db_name=pilot.get("name"), ip=pilot.get("ip")
        )
        active_run = self.state.get_active_run(pilot_key)
        if active_run and active_run.get("toolkit_id"):
            self.api.promote_active_hw_libs_to_stable(active_run["toolkit_id"], pilot_key)
```

Note: `pilot_name`/`pilot_key` must be resolved via `run["pilot_id"]` — only `subject_key` is in scope from the ZMQ message.

**File:** `orchestrator/orchestrator/mics/mics_api_client.py`

```python
def promote_active_hw_libs_to_stable(self, toolkit_id: int, pilot_name: str):
    libs = self.get_toolkit_hardware_libs(toolkit_id)
    for lib in libs:
        if lib.get("state") == "beta":
            self._patch(
                f"/api/hardware-libs/{lib['id']}/mark-stable",
                {"reason": "protocol_run", "pilot": pilot_name}
            )
```

Only `beta` libs are promoted — `stable` is a no-op, `unvalidated` is skipped.
