<objective>
The hardware spike. Replace three assumptions with three measurements, before the `Digital_Out`
rewrite is planned in detail.

Purpose: `31-RESEARCH.md` is HIGH-confidence on the lgpio API and the clock semantics — those were
read from the shipped C and Python sources and from the kernel uAPI header. It is **LOW confidence
on absolute jitter**, and it says so: "No figure for lgpio's tx-thread jitter on a Pi 4B under
Bookworm appears anywhere I could verify. The mechanism is fully known; the magnitude is not."

The risk this spike addresses inverts the phase's original assumption. On the receive side lgpio is
unambiguously better: kernel hardirq timestamps, `CLOCK_MONOTONIC`, 64-bit nanoseconds, no daemon,
no tick estimation, no 32-bit wrap. On the **transmit** side it is worse by construction:
`tx_pulse`/`tx_wave` are software-timed in a single ordinary `pthread` sleeping on
`clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)`, and lgpio contains **zero** calls to
`sched_setscheduler`, `pthread_setschedparam` or `mlockall`. pigpio put its *whole process* at
`SCHED_FIFO` maximum (`pigpio.c:8340-8343`) and every thread it created inherited that. So a naive
port moves valve-open duration — i.e. **reward volume** — from a real-time-scheduled thread to a
best-effort one. That is a data-quality defect that no functional test would ever surface.

The proposed mitigation is `CPUSchedulingPolicy=fifo` on the unit, relying on
`lgPthTxStart()`/`lgPthAlertStart()` being called from inside `lgGpiochipOpen()` and on POSIX
threads inheriting scheduling policy by default. Every link in that chain is documented. **The
composition is not verified end to end.** One `chrt -p` settles it, and it is cheap.

Output: `31-SPIKE.md` with the numbers, and a go/no-go that plans 11-13 are written against.
</objective>

<open_questions_this_spike_closes>
Taken verbatim from `31-RESEARCH.md` `## Open Questions`. **Do not plan the `Digital_Out`/
`Solenoid`/`TTL`/`Pulse20Hz` rewrite in fine detail until these have answers.**

**Q2 — real lgpio tx jitter on Pi 4B / Bookworm, `SCHED_OTHER` vs `SCHED_FIFO`, idle vs loaded.**
Mechanism known exactly; magnitude unknown. This is the first measurement of Stage 3 and it gates
the design.

**Q3 — does `CPUSchedulingPolicy=fifo` actually reach lgpio's threads?** systemd applies the policy
at `exec`; `lgPthTxStart()`/`lgPthAlertStart()` are called from inside `lgGpiochipOpen()`
(`lgGpio.c:772-774`); `pthread_attr_setinheritsched(3)`'s default is `PTHREAD_INHERIT_SCHED`. What
is unclear is whether CPython does anything between `exec` and `gpiochip_open()` that resets
scheduling — it should not. **Note lgpio does NOT name its threads** (no `pthread_setname_np`
anywhere), so you cannot identify them by `comm`; check that ALL threads report `SCHED_FIFO`.

**Q4 — kernel event-FIFO headroom.** The kernel drops events when the per-request FIFO is full
(`pr_debug_ratelimited("event FIFO is full - event dropped")`), and `event_buffer_size` defaults to
16 x lines. **lgpio never sets `event_buffer_size`** — zero occurrences in `lgGpio.c`. 16 events in
0.5 ms (lgpio's alert-thread `ppoll` timeout) is 32 kHz, so overflow is unlikely — but "unlikely"
is not "measured", and a dropped edge is silent. If drops appear, the escape hatch is a small lgpio
patch or moving that line to libgpiod. **Record the escape hatch; do not pre-build it.**

**Q5 — does anything on the rig still need `tx_servo`?** lgpio's author explicitly warns against
software-timed servo pulses for real use ("The timing jitter will cause the servo to fidget");
pigpio's were DMA-timed. Enumerate the `set_servo_pulsewidth` call sites, and if any is on a
behavioural path, measure it in the same harness as the valve.

**Also settle here (cheap, same session):** the exact gpiochip label and line count for this board
(PLAT-12). CONTEXT §5 named `pinctrl-bcm2835` for Pi 4; the evidence says Pi 4 is
**`pinctrl-bcm2711`** and `bcm2835` is Pi 2/3/Zero. Plan 09 should already have captured
`gpiodetect`; confirm it and add `gpioinfo` line counts.
</open_questions_this_spike_closes>

  <files>

  <action>
    A single self-contained script the user runs on the card. It must NOT import the production
    tree — at this point `gpio.py` is still pigpio-based, and the spike's whole job is to
    characterise lgpio *before* the rewrite commits to a design. Standard library + `lgpio` only.

    Subcommands:
    - `chips` — enumerate `gpiochip_open(n)` for n in 0..31, print `gpio_get_chip_info(h)` as
      `index, status, lines, name, label` for every chip that opens, and close the rest. This is
      the raw input to plan 11's resolver, and it must show what the board reports rather than what
      a document predicted.
    - `sched` — print `os.sched_getscheduler(0)` and `os.sched_getparam(0)` for the process, then
      call `gpiochip_open()`, then re-read the scheduler for **every** thread in
      `/proc/self/task/*`. Since lgpio does not name its threads, print all of them with their
      tids. Take `--expect fifo` and exit non-zero if any thread is not `SCHED_FIFO` — that turns
      Q3 into a pass/fail rather than a paragraph.
    - `tx` — command N pulses via `tx_wave` (one-shot) or `tx_pulse` (train), measure them on the
      loopback input with `gpio_claim_alert(BOTH_EDGES)` and **no debounce**, and write the plan-06
      JSONL format so `analyse.py` reads it unchanged. Take `--on-us`, `--off-us`, `--cycles`, `-n`.
    - `fifo` — drive the input line as fast as the hardware allows for a fixed window, count
      commanded vs observed edges, and report the deficit. That is the Q4 headroom measurement.
      Include a `--burst` mode that emits a tight burst rather than a steady train, since a burst is
      what would actually overflow a 16-slot FIFO.

    Constraints, each of them load-bearing:
    - Wrap every lgpio call in `try/except lgpio.error`. lgpio has a module-global
      `exceptions = True` and `_u2i()` raises on any negative status, so a `TX_QUEUE_FULL` (-96) or
      `GPIO_BUSY` (-79) becomes an exception thrown out of a callback. Count them; never let one
      propagate.
    - `tx_pulse` requires `on_us + off_us > lgMinTxDelay` (default **10 us**), else
      `LG_BAD_PWM_MICROS`. It is adjustable up to 1000 via `lgpio.set_internal(1, value)`
      (`LG_CFG_ID_MIN_DELAY == 1`); **no Python constant is exported for it — pass the literal 1**.
    - The `tx_wave` queue is **`LG_TX_BUF` == 10 entries per GPIO**. There is no maximum pulse count
      within one wave — `tx_wave` copies the list into a malloc'd buffer, so an arbitrary
      `values[]`/`durations[]` sequence of any length is one call — but only 10 *waves* can be
      queued. Handle `TX_QUEUE_FULL` explicitly.
    - Resolve the chip **by label**, never `gpiochip_open(0)`. On Pi 5 Bookworm the header chip has
      been `gpiochip4`, then `gpiochip0` (kernel 6.6.45), then `gpiochip15` (kernel 6.12.96). Take
      `--chip-label` to override.
    - Restore outputs to their safe level and close handles on exit, including on SIGINT.
    - `--help` must be complete enough that the copy-paste blocks in Task 2 are self-explanatory.
  </action>
