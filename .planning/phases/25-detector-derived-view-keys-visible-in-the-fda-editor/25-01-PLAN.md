**D1 — DVK-02 source of truth: the UNION across pilots that have a `pilot_hardware_config`
row named for that module, carrying per-pilot provenance.** (This is the phase's single most
consequential open call. Rejected alternatives and why:)

- *A declared default on `hardware_modules`.* That table stores only `name` / `class_name` /
  `hardware_lib_id` / `description` — verified 2026-07-29. A `default_config` column would be a
  **second** store of `device_name`/`num_detectors` that the Pi never reads: the Pi receives
  `prefs_hardware` built from `pilot_hardware_config` (`toolkit_dispatch.py:96-104`), merged by
  `mics_task._merge_prefs_hardware`. The moment somebody edits the pilot row and not the module
  default, the editor offers keys the Pi will not create. That is precisely the failure DVK-01
  exists to prevent.
- *A per-toolkit declaration.* Worse: a toolkit is not bound to any pilot at all, so it sits one
  step further from the running config, and it adds a third place to edit.
- *The union (chosen).* Reads the exact rows the dispatch spec ships, keyed the same way
  (`WHERE name = :module_name`). Every offered key is therefore a key that some real, configured
  pilot will actually create. Preflight (DVK-06, plan 03) resolves against the same table scoped
  to one `pilot_id`. **One table, one helper, two scopes** — design-time union, run-time single
  pilot. No migration, no new column, no new place to keep in sync.
- **Disagreement is surfaced, not merged.** The return carries `by_pilot` provenance and a
  `conflict` flag. The union is still offered (an editor is never blocked by a mis-configured
  second pilot), but the caller can name the pilots that differ. Silent merging is the thing
  DVK-02 forbids; showing the union *plus* who disagrees is not merging.

**D2 — the derivation exists twice, once per language runtime, and that is deliberate.**
`api/detector_keys.py` (container) and `autopilot.tasks.fda_vocabulary` (Pi, plan 02) cannot
import each other. This is the same situation `fda_validation.py:30-33` already documents for
`RUNTIME_KEY_TEMPLATE_TOKENS`. Mitigation, and it is mandatory: **both test suites pin the same
literal golden table**, reproduced verbatim below and in plan 02. Within each side the format is
single-sourced — every backend consumer calls `derive_view_keys`, and nothing else builds a key
string.

**D3 — a malformed `first_channel` yields no keys on the backend and raises on the Pi.**
Absent/`null` → treated as `0` (today's behaviour, byte-identical). Present but not a
non-negative integer → the backend returns **no keys** (an API read must never 500 on a bad
config row; the module simply offers nothing, and DVK-06 preflight then flags anything that
references it), while the Pi raises `ValueError` at task start (plan 02). Loud where it matters,
safe where it is only a render.
</decisions>

```python
# api/detector_keys.py

def derive_view_keys(config: dict | None) -> list[str]:
    """The ONE key format. f"{device_name}{i}" for i in range(first, first + num_detectors)."""

def module_detector_channels(db, module_names: list[str]) -> list[dict]:
    """Per module, the union of derived keys across every pilot configured for that name."""
```

`module_detector_channels` return shape — this exact JSON is what plan 03 puts on the toolkit
read and plan 04's React code consumes:

```json
[
  {
    "module_name": "MPR121",
    "keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"],
    "conflict": false,
    "by_pilot": [
      {"pilot_id": 1, "pilot_name": "pilot_raspberry_lior",
       "keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"]}
    ]
  }
]
```

- `keys` — sorted union across `by_pilot`, natural order (channel index ascending within a
  device prefix). Deduplicated.
- `conflict` — `true` iff two or more entries in `by_pilot` derive **different** key sets.
  A pilot with no config row for that module is simply absent from `by_pilot` and is **not** a
  conflict.
- Modules that derive no keys anywhere are omitted from the list entirely (an empty
  `detector_channels` is the normal case for a toolkit with no detector).

**GOLDEN DERIVATION TABLE (identical in plan 02's Pi test — change one, change both):**

| config | expected keys |
|---|---|
| `{"device_name": "LICKER", "num_detectors": 4}` | `["LICKER0","LICKER1","LICKER2","LICKER3"]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": 0}` | `["LICKER0","LICKER1","LICKER2","LICKER3"]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": null}` | `["LICKER0","LICKER1","LICKER2","LICKER3"]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": 1}` | `["LICKER1","LICKER2","LICKER3","LICKER4"]` |
| `{"device_name": "LICKER", "num_detectors": 1, "first_channel": 11}` | `["LICKER11"]` |
| `{"device_name": "TONGUE", "num_detectors": 2, "first_channel": 3}` | `["TONGUE3","TONGUE4"]` |
| `{"device_name": "LICKER", "num_detectors": "4", "first_channel": "1"}` | `["LICKER1","LICKER2","LICKER3","LICKER4"]` |
| `{"device_name": "LICKER"}` | `[]` |
| `{"num_detectors": 4}` | `[]` |
| `{"device_name": "", "num_detectors": 4}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": 0}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": -1}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": true}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": -1}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": "x"}` | `[]` |
| `{"device_name": "LICKER", "num_detectors": 4, "first_channel": true}` | `[]` |
| `{}` / `None` | `[]` |

Numeric-string acceptance mirrors the Pi's `mics_task._coerce_hw_value`
(`mics_task.py:215-231`), which turns `"4"` into `4` before the constructor sees it — the same
config JSON must derive the same keys on both sides.

**Live data this runs against (verified 2026-07-29):**
```
pilot 1 (pilot_raspberry_lior)  MPR121  {"name":"MPR121","num_detectors":4,"device_name":"LICKER","address":true}
pilot 1 (pilot_raspberry_lior)  TOUCH_INT {"name":"TOUCH_INT","pin":8,"pull":1,"trigger":"B", ...}
```
So today `module_detector_channels(db, ["MPR121","TOUCH_INT"])` must return exactly one entry,
`MPR121` → `LICKER0…LICKER3`, `conflict: false`. `TOUCH_INT` derives nothing and is omitted.

  <action>
Add to `api/detector_keys.py`:

```python
def module_detector_channels(db, module_names: list[str]) -> list[dict]:
```

One SQL statement, mirroring `hw_introspect.toolkit_hw_capabilities`' caller-owned-session
pattern (`db.execute(sa_text(...), {...}).fetchall()`, never opening its own connection):

```sql
SELECT phc.name AS module_name, phc.pilot_id, p.name AS pilot_name, phc.config
FROM pilot_hardware_config phc
JOIN pilots p ON p.id = phc.pilot_id
WHERE phc.name = ANY(:names)
ORDER BY phc.name, p.name
```

`pilot_hardware_config` is name-keyed (Phase 17 decision, and `get_dispatch_spec` looks it up by
`name` too) — join on `name`, never on `hardware_module_id`.

For each row call `derive_view_keys(row.config)`; drop pilots that derive nothing. Group by
`module_name`. `conflict = len({tuple(keys) for each by_pilot entry}) > 1`. Build `keys` as the
sorted union using a private `_key_sort(key)` that splits the trailing digit run so the ordering
is (prefix, int(index)) — plain `sorted()` puts `LICKER11` before `LICKER2` and the editor
dropdown would read wrong.

Emit the exact JSON shape from the `<interfaces>` block. Do not add extra fields; plan 04's
