<objective>
Prove the phase on the path researchers use.

Purpose: every acceptance artefact in this phase so far measures `mics_core` in isolation - C4's
soak drives `assign_cb` from `tools/pulse_timing/clock_soak.py`, and plan 09 boots a pilot that
never runs a task. Neither one sends a HANDSHAKE that registers a toolkit, receives a START payload,
execs a hardware lib out of the database, dispatches an event through ZMQ to the orchestrator, or
puts a document in Elasticsearch. That whole chain is where plan 11's finding lived, and it is the
only chain a researcher ever touches.

This plan builds the missing asset - a **clock probe** toolkit with two task definitions - and uses
it to close PLAT-24/25/29/30/31/32 on the real path. The short one is a ten-minute regression test
anyone can re-run after any future change; the long one is the backend twin of C4's soak, crossing
three tick wraps with a forced clock step.

**What this adds over C4, stated plainly so the two do not look redundant.** C4 proves the clock
module is correct. This proves the correct clock module is *the one that runs* when the backend
dispatches a session, that its output survives ZMQ and the orchestrator's ingest, and that the
fields land in Elasticsearch with the right types. Plan 11 showed those are different claims: the
tree was right and the deployed artifact was three versions behind it.

Output: a seeder, a read-only Elasticsearch verifier, two runs on spare hardware, and the phase's
end-to-end evidence with an honest NOT PROVEN list.
</objective>

<known_traps>
Each of these has already cost a debugging session on this system. They are not hypotheticals, and
a task definition that walks into one produces a run that looks fine and proves nothing.

1. **FDA `{"param": ...}` args are dead on the Pi.** `self.params` is never assigned anywhere in
   the tree, so a `{"param": "duration"}` argument resolves to nothing. **Use literal args** in both
   task definitions - `{"args": [3]}`, not a param reference. Do not "improve" this.
2. **`special: INC_TRIAL_COUNTER` is a silent no-op.** It sends `{}` and the orchestrator drops it
   on the missing `subject` key, so a GUI-built task definition can never graduate. **Neither task
   definition may depend on graduation, trial counting, or protocol advancement.** Drive both loops
   with TIMER conditions in `condition_tree`, exactly as task def 553 (`door_test`) does.
3. **`{"view": <hardware>}` as a condition operand** was deployed but never rig-exercised (CMP-24b /
   CMP-25). Do not make the probe the first thing to test it - use `{"view": "TIMER"}`, which task
   def 553 proves works.
4. **`hw_lib_versions` must be pinned explicitly.** Relying on the `stable` rung is exactly the
   fall-through plan 11 found; a probe that verifies the new gpio only because stable happens to
   point at it is not verifying anything. Pin lib 8 by id.
5. **Two vocabularies exist in `event_log_v2`** and there is a trial/trail spelling split. Query on
   fields this phase writes (`t_mono_ns`, `ts_source`, `event.event_data.pi_timestamp_mono_ns`),
   not on legacy event names.
6. **Isolate the run** with `subject: bp_s<session>_r<run_id>`; the index holds 2.9 M documents from
   other work.
</known_traps>
