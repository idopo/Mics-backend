<interfaces>
**FDA JSON shape the scanner must walk (verified against `web_ui/react-src/src/types/index.ts:256-315`):**

```
fda_json
├── states: { <state_name>: { entry_actions: FdaAction[], wait_condition?: FdaCondition } }
├── transitions: FdaTransition[]        # TOP-LEVEL array, not per-state
│     each: { from, to, condition_tree? | condition_groups? | conditions? }
│     condition_tree  = leaf FdaCondition | { op: "AND"|"OR", children: ConditionNode[] }
│     condition_groups = [{ conditions: FdaCondition[] }]
│     conditions      = FdaCondition[]                       # legacy flat
└── trigger_assignments: [{ trigger_name, actions: FdaAction[] }]
```

`FdaCondition` = `{ left: FdaOperand, op, right: FdaOperand }`; a view operand is
`{"view": "KEY"}` or the legacy `{"tracker": "KEY"}`.
A view action is `{"type": "view", "key_template": "...", "source_ref": "...", ...}`, and `if`
actions nest further actions under `then` / `else` — mirror `fda_utils._scan_actions`' recursion
rather than inventing a second walker.

```python
         "source_ref": "MPR121" | None} , ...]
    """

                            device_names: dict[str, str],
                            detector_keys: list[str]) -> list[dict]:
    """-> preflight issues, in the shape preflight_validate already returns."""
```

**Issue shape (must match the existing contract so `HardwareCheckModal` can render it — plan 05
adds the branch):**

```json
{
  "module_id": null,
  "module_name": "MPR121",
  "issue": "view_key_unresolved",
  "detail": "Transition 0 condition operand names view key 'LICKER0', which this pilot does not have. This pilot's detector channels: LICKER1, LICKER2, LICKER3, LICKER4.",
  "location": "transitions[0].condition_tree.left",
  "key": "LICKER0",
  "available_keys": ["LICKER1", "LICKER2", "LICKER3", "LICKER4"]
}
```

`module_name` carries the `source_ref` for a key_template issue, or the detector module whose
prefix the key looks like, or `""` when neither applies. `module_id` is always `null` — the same
convention `fda_ref_unresolved` already uses.

**Resolution rules — precision matters more than coverage here; a false rejection blocks a
session start.**

Valid key set for a pilot =
  derived detector keys (this toolkit's modules × that pilot's configs)
  ∪ toolkit flag names
  ∪ `fda_json["variables"]` names
  ∪ `{"trial_counter"}`
  ∪ the toolkit's hardware module names
The last one is not decoration: `task.init_hardware` does `self.view.view[pin] = hw`
(`task.py:~204`), so every module name really is a live `view.view` key, and `init_flags` writes
every flag into `view.view` too (`mics_task.py:307-308`). Rejecting those would be wrong.

Per scanned entry:
- **operand** (always a literal key) → report if not in the valid set.
- **key_template with no `{` tokens** → same as an operand.
- **key_template containing `{device_name}`** → the `source_ref` must resolve to a config row on
  this pilot carrying a non-empty `device_name`; if it does not, report (this is DVK-08's negative
  case: "a definition whose key_template names a device that pilot does not have"). If it does,
  substitute `device_name` and then: if the remainder still contains tokens (the canonical
  `{device_name}{pin_number}`), **report nothing** — the key varies per interrupt and is
  unresolvable statically. If nothing remains (`{device_name}2` → `LICKER2`), check the resolved
  key against the valid set.
- **key_template with tokens but no `{device_name}`** → report nothing. Unresolvable statically.

The "report nothing" cases are deliberate. Preflight's job is to catch the wrong-key class before
START, not to prove every runtime key.
