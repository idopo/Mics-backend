<objective>
Build the software half of the fail-safe: a standalone script that de-energises the rig's GPIO
outputs, invoked by systemd as `ExecStopPost` on `mics-pilot.service`.

Purpose: SAFE-05. The unit today has no `ExecStopPost` and says so in its own comment. The
de-energise must be **unconditional and outside the process** — an in-process `release()` is
best-effort and nice when it works, and if de-energising is optional it is not a fail-safe. This
is the property most likely to be diluted; protect it. Repairing the daemon kill hook is
explicitly NOT a solution: killing the daemon correctly leaves every pin exactly as energised as
it was, because the daemon does not restore GPIO state on exit.

Output: `deploy/mics-failsafe.sh`, an `ExecStopPost=` line, an installer that ships it, and a test
module that counts the pin set rather than eyeballing it.

**Scope boundary, stated so a later reader does not widen it by accident:** GPIO-backed `Modules`
entries only. The I2C motor shield is plan 04's third mechanism in this same script.
`ExternalHardware` is SAFE-11, deferred by user decision — the script records that gap in a
comment and does not pretend to close it.
</objective>

**Unit directives that constrain the hook** (`deploy/mics-pilot.service`):
`User=pi` — `ExecStopPost` runs unprivileged unless prefixed `+`. `pi` is a real member of the
`gpio` and `i2c` groups (`raspberrypi-sys-mods` 99-com.rules grants `GROUP="gpio" MODE="0660"`),
so an unprivileged write is expected to work and `+` should NOT be added unless discovery showed
otherwise. `TimeoutStopSec=20` bounds the whole stop sequence including this hook.
`Restart=always` / `RestartSec=5` — the pilot returns 5 s later and re-runs `_set_initial_state()`;
the hook runs before that and must not fight it.

**The pin set**, from `/opt/mics/pilot/prefs.json` (`BASEDIR` is `/opt/mics/pilot`, and

`.HARDWARE.Modules` — every entry with a numeric `pin` key. `TIMER` has no `pin` and is inert.
`GPIO`, `I2C`, `Mixer` and `Timers` are legacy groups that instantiate nothing; reading them
over-collects and must not be done on the primary path.

**BOARD -> BCM**, copied from

3:2, 5:3, 7:4, 8:14, 10:15, 11:17, 12:18, 13:27, 15:22, 16:23, 18:24, 19:10, 21:9, 22:25, 23:11,
24:8, 26:7, 29:5, 31:6, 32:12, 33:13, 35:19, 36:16, 37:26, 38:20, 40:21.
`polarity: 1` means OFF is logic LOW. Duplicate pins across entries are normal
(`Left_LED`/`Right_LED` both BOARD 11; `Solenoid`/`Mid_LED` both BOARD 12) and writing LOW twice
is harmless — deduplicate for tidiness, not correctness.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
