<!-- The measurement contract, and the three things that make a naive test lie. -->

**`Restart=always` / `RestartSec=5` makes a direct pin read racy.** Five seconds after the kill the
pilot is back and `_set_initial_state()` has run, which can re-drive the very line under test. So
the PRIMARY evidence is the journal: `ExecStopPost` stdout goes to journald, and plan 03's script
prints one line per pin in the form
`mics-failsafe: board=<N> bcm=<M> mode_before=<..> level_before=<..> level_after=<..> result=<..>`
plus a summary `mics-failsafe: pins=<..> ok=<..> fail=<..> source=<..> i2c=<..>`. A direct pin read
inside the 5 s window is corroboration, not the proof.

**BOARD is not BCM.** `Modules` entries carry BOARD numbers; every shell read takes BCM.
BOARD 11 -> BCM 17, BOARD 12 -> BCM 18. Several BOARD numbers used on this rig are also valid BCM,
so a numbering slip reads the wrong line and reports success. Every recorded number in the
validation log must be labelled with which numbering it is.

**What the run instantiated is not what prefs lists.** `OPEN-ITEMS-2026-08-30.md:66` records
`Left_LED` and `Mid_LED` failing to instantiate on every run on pilot 3 while prefs still listed
them. So the acceptance set is "every GPIO-backed `Modules` entry **that run instantiated**", and
establishing which those were is part of the measurement, not an assumption.

**Deployment reaches the Pi only through the user's own `git pull`.** Hardware libs (`gpio.py`,
`i2c.py`) are a separate matter — they execute from `hardware_lib_versions.source_code` in the
backend DB, pinned per task definition, and a Pi `git pull` does not deploy them. This plan changes
none of them and must not repoint any task definition.
</interfaces>
