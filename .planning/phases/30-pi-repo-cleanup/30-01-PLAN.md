<from_package_import_submodule_must_resolve>
## `from <package> import <submodule>` — the alias rule. Measured, not argued.

Resolving only `node.module` makes checks 1 and 2(a) blind to
`from autopilot.hardware import unreal`: `autopilot.hardware` is a package and resolves, the
alias `unreal` is never inspected, and deleting `hardware/unreal.py` produces **0 violations**.
That is not a corner case — it is how **19** files in this tree import `unreal`
(`pilot/plugins/` ×13, `terminal/plugins/` ×6), and it is precisely the acceptance bar stated in
`<dangling_reference_cases_the_guard_must_catch>` case 2. Verified 2026-08-10: the same blind
spot also hides `autopilot.hardware.cameras` from `autopilot/autopilot/tasks/test.py:18` and
`autopilot.core.subject` from `autopilot/autopilot/viz/trial_viewer.py:26`.

**The naive fix is wrong.** "Also resolve `node.module + '.' + alias.name`" flags every
`from autopilot.hardware import Hardware` — 43 distinct `<package>.<name>` targets exist
tree-wide and most are *classes and constants* re-exported by `__init__.py` (`Hardware`,
`Effector`, `Sensor`, `BCM_TO_BOARD`, `Message`, `Net_Node`, `Station`, `Task`, `Stim`, …).
An alias is only a violation when it is **neither a module file nor a name the package binds**:

```python
if isinstance(node, ast.ImportFrom) and node.level == 0 \
        and node.module and node.module.split('.')[0] == 'autopilot':
    if not resolve(node.module):
        violation(node.module); continue          # the package itself is gone
    if not is_package(node.module):
        continue                                  # a module — aliases are attributes, unknowable
    bound, has_star = init_bindings(node.module)  # AST of <pkg>/__init__.py
    if has_star:
        continue                                  # `from x import *` — cannot enumerate; skip
    for alias in node.names:
        if alias.name == '*':
            continue
        full = f'{node.module}.{alias.name}'
        if resolve(full) or alias.name in bound:
            continue
        violation(full)
```

`init_bindings(pkg)` AST-parses `<pkg>/__init__.py` and collects every name it binds at any
level: `ClassDef` / `FunctionDef` / `AsyncFunctionDef` names, `ast.Name` assignment targets,
`ImportFrom` alias names (`asname or name`), and `Import` root names — returning
`(names, saw_star_import)`. Missing or unparseable `__init__.py` → `(set(), False)`.

**Measured on the untouched tree (2026-08-10):**

| Scenario | Violations |
|---|---|
| Untouched tree | **1** — `tasks/mics_task.py:1589 → autopilot.autopilot.core.pilot`, i.e. exactly the `known_dangling` entry, so **0** with the exemption applied |
| Simulated `rm hardware/unreal.py` | **19 importers; 13 visible violations** under the Wave-1 `scan_skip`. The 6 `terminal/plugins/` importers sit under the `terminal/` skip prefix and plan 03 deletes them in Wave 1, before plan 04 removes `unreal.py` in Wave 2 — so the guard never needs to see them. Acceptance case 2 is met by the 13 `pilot/plugins/` hits |
| Simulated `rm hardware/cameras.py` | **5** — incl. `tasks/test.py:18`, invisible to the old spec |
| Simulated `rm core/subject.py` | **4** — incl. `viz/trial_viewer.py:26`, invisible to the old spec |

Calibration is unchanged where it already worked and strictly better where it did not: still
silent on the whole untouched tree, now loud on the orphan shape that dominates it.

<the_docstring_trap>
## 2(b) skips docstrings too — the SECOND narrowing, and it is independently load-bearing.

23 files under `pilot/plugins/` carry, in a **class docstring**:

```
stages. It is used by the :class:`~autopilot.core.subject.Subject` object to make a data table with
```

`autopilot/examples/tasks/blink.py:64` carries the same sentence, and
`autopilot/autopilot/core/pilot.py:1125` carries `Opens a file with :meth:`~.autopilot.open_file``
inside `run_task`'s docstring.

None of these is a reference to anything. They are Sphinx cross-reference prose inherited from
upstream. But plan 03 deletes `core/subject.py` in **Wave 1**, and those 23 plugin files do not go
until plan 04 in **Wave 2** — so a naive 2(b) fails the guard at the end of Wave 1 on 23 files
describing no real breakage.

**The narrowing:** when walking a `.py` file's AST, first collect the docstring `Constant` nodes —
the `Expr(Constant(str))` that is `body[0]` of a `Module`, `ClassDef`, `FunctionDef` or
`AsyncFunctionDef` (equivalently, everything `ast.get_docstring` would return) — and skip them by
node identity. Scan every other string `Constant`.

**This must not weaken case 3.** `setup_autopilot.py:198`'s literal is an *argument to a call*
(`launch_file_open.write("python3 -m autopilot.core.terminal -f " + …)`), never a statement-level
`Expr`, so it is still scanned. Task 1's tests assert **exactly this pair** — docstring passes,
`.write()` argument fails — because that pair is the whole difference between a guard that is
usable and a guard that is either noisy or blind.

**Keep the docstring fixture load-bearing under the `INVOCATION` rule.** The 23 real plugin
docstrings above use Sphinx `:class:` prose, which `INVOCATION` would not match anyway — so a
fixture copying them verbatim would pass for the wrong reason and stop testing the narrowing.
Task 1's docstring fixture must therefore put an **invocation form inside the docstring**, e.g. a
class docstring whose body contains the line `from autopilot.core.subject import Subject` as
example code. That string matches `INVOCATION` and names a missing module, so it is skipped
**only** because it is a docstring — which is the property under test.
</the_docstring_trap>
