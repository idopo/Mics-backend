<interfaces>
Everything below verified by direct read on 2026-08-05.

**The inbound wire format is trivially reproducible.** `RouterGateway._thread_main` binds a ROUTER
with `IDENTITY = NAME` on `MSGPORT`; `_on_recv` takes `frames[0]` as the authoritative sender and
`frames[-1]` as JSON bytes for `Message(raw)`. So a `zmq.DEALER` with
`setsockopt_string(zmq.IDENTITY, <pilot_key>)` connected to `tcp://127.0.0.1:<MSGPORT>` sending a
single frame of `Message(...).serialize()` is indistinguishable from a Pi at this layer.

`prefs.json`: `NAME = "T"`, `MSGPORT = 5560`. Read them through `orchestrator.config.Config` at
`/orchestrator/orchestrator/prefs.json` rather than hardcoding (CLAUDE.md: never hardcode ZMQ
addresses/ports).

`Message.serialize()` calls `validate()`, which requires `id`, `to`, `sender` and `key` to be
non-None. Set all four or serialize returns `False`.

**`/pilots/live` enumerates Redis, not `OrchestratorState`** (see `19-01-SUMMARY.md`). A pilot exists
for the UI iff `pilot:<key>` exists, and `connected` is `(now - updated_at) < 15 s` — so the probe
must both create the hash and **refresh `updated_at` on an interval** for the card to stay live while
a human looks at it.

`docker compose` service names: `orchestrator`, `web_ui`, `redis` (`mics_redis`). The orchestrator
runs `network_mode: host` with `REDIS_URL=redis://127.0.0.1:6379/0`, and `main.py:37` builds its
client with `redis.Redis.from_url(REDIS_URL, decode_responses=True)`. Mirror that.

Live baseline, same date: `curl -s localhost:9000/pilots/live` returns exactly one pilot,
`pilot_raspberry_lior`, `connected: false`.

  <files>orchestrator/orchestrator/dev_health_probe.py</files>
  <action>
    Write a dev-only diagnostic, runnable inside the orchestrator container as
    `python -m orchestrator.dev_health_probe`. It lives in the package (not a `scripts/` directory)
    because the Dockerfile only copies `orchestrator/` into the image, so this is the one location
    that needs no build change. Open the module docstring with a plain statement that it is a
    diagnostic, not part of the runtime, and that it writes a temporary Redis key it deletes on exit.

    CLI (`argparse`), all with defaults so the bare command works:
    - `--pilot` (default `health_probe`) — the fabricated pilot key
    - `--device` (default `probe_device`) — the source_id; the tracker sent is `<device>.alive`
    - `--seconds` (default `180`) — how long to hold the pilot "connected"
    - `--alive` flag (default off, i.e. send `alive = false`) — so the same tool proves recovery

    Behaviour:

    1. Build `Config("/orchestrator/orchestrator/prefs.json")` and read `MSGPORT`. Build the Redis
       client from `os.environ.get("REDIS_URL", "redis://127.0.0.1:6379/0")` with
       `decode_responses=True`, exactly as `main.py:37` does.
    2. **Refuse to run against a real pilot.** If `pilot:<args.pilot>` already exists in Redis, print
       an error naming it and exit non-zero. This tool writes and then *deletes* a Redis hash;
       pointed at a real pilot key it would destroy live state. Fail closed.
    3. `HSET pilot:<pilot>` with `state="RUNNING"`, `updated_at=<now ISO, UTC>` and an `active_run`
       JSON blob (`{"id": 0, "session_id": 0, "subject_key": "<pilot>_probe", "started_at": <now ISO>,
       "status": "running"}`) so the card renders its run block and the fabricated pilot is
       recognisable as fake at a glance.
    4. Open a `zmq.DEALER`, `setsockopt_string(zmq.IDENTITY, pilot)`, connect to
       `tcp://127.0.0.1:{MSGPORT}`, sleep ~0.3 s for the connection to establish (a DEALER drops
       messages sent before the peer is connected — this is the one place the script will silently do
       nothing if rushed), then `send_multipart([msg.serialize()])` — **one frame**; the ROUTER
       prepends the identity itself.

       The message value must be the exact `Event_Dispatcher` payload shape, with the liveness bool
       already int-coerced the way the Pi's `coerce_for_event` coerces it:

       ```python
       value = {
           "pilot": pilot, "subject": f"{pilot}_probe", "session": 0, "run_id": 0,
           "task_type": "dev_health_probe", "timestamp": now_iso,
           "continuous": True, "session_progress_index": 0, "subjects": [],
           "event": {"event_type": "Boolean_Tracker",
                     "event_data": {"id": f"{device}.alive", "value": int(alive),
                                    "result": None, "func_name": "set"}},
       }
       msg = Message(id=f"{pilot}_probe_0", to="T", sender=pilot, key="CONTINUOUS", value=value)
       ```
       `to` must be the orchestrator's `NAME` from prefs, not the literal `"T"` — read it from config.

    5. Loop for `--seconds`, refreshing `updated_at` every 5 s (the 15 s `PILOT_TIMEOUT_SEC` window)
       and re-sending the same CONTINUOUS frame every 15 s. Re-sending is deliberate: it proves the
       repeat is a **no-op** — `set_device_health` returns `False` on an unchanged level, so the
       orchestrator log must show exactly one `device health:` INFO line for the whole run.
       Print the elapsed seconds every 15 s so the operator can see it is alive.
    6. **Clean up in a `finally`, and on SIGINT/SIGTERM:** `DEL pilot:<pilot>`, close the socket,
       `term()` the context. Print `PROBE_CLEANED_UP`. The in-memory
       `OrchestratorState._device_health["<pilot>"]` entry survives until the next orchestrator
       restart, which is harmless: `snapshot()` iterates `_pilots` (the probe never handshakes, so it
       has no entry there) and `/pilots/live` iterates Redis (key now deleted), so it is unreachable
       from every consumer. Say so in the docstring so nobody "fixes" it later.

    Print, before the loop starts, the two URLs the operator will need:
    `http://localhost:9000/pilots/live` and `http://localhost:8080/react/`.

    Keep it under ~120 lines. No new dependency: `zmq`, `redis` and `argparse` are all already in the
    image.
