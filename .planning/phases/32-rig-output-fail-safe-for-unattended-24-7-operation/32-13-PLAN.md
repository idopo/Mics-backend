<!-- Where the evidence lives, and the two facts that make a naive test read the wrong thing. -->

**Live rig data is on `.217`, index `event_log_v2`.** `132.77.73.125` holds historical
`restored-*` indices only, and its own `event_log_v2` is a stale 308-document stub. A query against
`.125` will return nothing and look like the feature does not work. Isolate a run with
`subject: bp_s<session>_r<run_id>`.

**Run-scoped fault evidence** is in ES: `hardware_init_failed` (FAULT-01), `extlink_bind_failed`
(FAULT-03) and `task_end` (FAULT-05), all dispatched through `Event_Dispatcher` on the `CONTINUOUS`
key and landing via the orchestrator's `_handle_data`.

**Pilot-scoped fault evidence** is in the UI and at `GET /pilots/live`:
`pigpiod_unavailable` (FAULT-02), `task_start_failed` (FAULT-04) and `hardware_init_failed`
(FAULT-01's badge half), under each pilot's `device_health.faults`.

**Resume evidence** is in PostgreSQL: `session_runs.status`, `error_type`, `error_message`,
`auto_resume_count`, and `run_progress.current_trial`. Read them with
`docker compose exec -T db psql -U <user> -d <db> -c "..."` — check `docker-compose.yml` for the
credentials rather than guessing them.

**The two timing facts a test can trip over:** the pilot returns 5 s after a kill
(`RestartSec=5`), and the watchdog does not mark a run ERROR from silence until 30 s
(`orchestrator_station.py:1106`). Plan 10's reconnect reconciliation is supposed to close the gap,
so the observable claim is that the run flips to `ERROR` in **under 30 seconds** — the measurement
is the point.

**The Pi's handshake retry** fires after 21 s without a PING, mid-run. A network-hiccup arm is
therefore a required negative test, not an optional one: if it kills a live run, plan 10 is wrong in
production even though its unit tests pass.
</interfaces>
