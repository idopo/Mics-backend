<expected_friction>
Named in advance so a round trip is diagnosis, not surprise.

- **`Adafruit-PureIO` is sdist-only** (no wheels). It is pure Python so it should install without a
  compiler — but this is the one dependency that builds from source, and it is unverified. If it
  fails, that is a `requirements.txt` finding, not an installer bug.
- **The two `adafruit-circuitpython-*` lines are deliberately unpinned.** THIS is the "first fresh
  install" the requirements comment refers to. Resolve them here and write the pins back.
- **The packaged `pigpiod.service` may not have the `Type=` the drop-in assumed.** Plan 05 wrote
  `deploy/pigpiod-mics.conf` without being able to see the card. Run `systemctl cat pigpiod.service`
  **before** trusting anything: if the packaged unit's `Type=` differs, or if the drop-in's
  `ExecStart=` reset is missing or misordered, the unit fails to load — and because the pilot
  `Requires=pigpiod.service`, the pilot then never starts either. That is the single most likely
  first-run failure in this plan, and it presents as "the pilot didn't start" rather than as
  anything mentioning pigpiod. Check the daemon first.
- **The `-x` mask may be rejected.** `pigpiod` documents `-x` as a numeric mask; the rig passes a
  28-character string of ones and zeros (`PIGPIOMASK`, reproduced verbatim by plan 05). Check
  `journalctl -b -u pigpiod` for a complaint and `ps -o args= -C pigpiod` for what actually ran. If
  pigpiod rejected or misparsed it, that is a **finding about the live rig's long-standing
  configuration** — record it, convert the mask deliberately to the hex form of the same pin set,
  and say so. Do not silently rewrite it and do not shrug it off.
- **A stale `/usr/local/bin/pigpiod`** from a source build shadows the packaged one on `PATH`. The
  rig's own daemon is a v78 source build installed there. On a freshly flashed card there should be
  none — confirm with `command -v pigpiod` and `pigpiod -v`, and record both.
- **The pilot still tries to spawn its own daemon, and that is a leftover, not a bug to fix here.**
  `pilot.py:205` calls `init_pigpio()`, which calls `external.start_pigpiod()` (`pilot.py:949`),
  which shells out to `sudo pigpiod -t 0 -l -x <mask>`. With systemd already running one, the second
  instance will fail to acquire the daemon's lock and exit; `init_pigpio` catches only `ImportError`,
  so anything else surfaces in the journal. **Expected outcome: a log line, not a dead pilot.**
  Record exactly what appears. **Plan C3 deletes that call under PLAT-33** — do not delete it here,
  and do not disable the systemd unit to make the message go away.
- **The pilot will NOT reach a working session here, and that is bounded and named.** The run path
  still calls Autopilot-patch-only APIs that stock pigpio does not have:
  `pilot.py:1073 pigpio.pi(sync_ticks=True)` and `pilot.py:1079 self.pi.synchronize()`. On the
  pinned stock client those raise `TypeError`/`AttributeError` — but only when a task actually runs,
  which this plan never does. So the expected state after boot is **a pilot unit that is `active`
  and idle**, not a crash loop. Plans C1/C2/C3 replace that block (PLAT-22, PLAT-27, PLAT-28) and
  C4 proves a working session.

  **Consequence you must not miss:** the earlier version of this plan got its PLAT-09 evidence for
  free, because the installer purged pigpio and the pilot crash-looped on `ModuleNotFoundError`.
  That is gone. **PLAT-09 must now be provoked deliberately** — the 10-kills-in-30-seconds storm in
  `<what_the_evidence_must_show>` is mandatory here, not deferred. Without it, "a crash-looping unit
  cannot latch into failed" is an unexercised claim.
- **`gpiodetect` is worth capturing while the card is in hand**, but it is **no longer an input to
  this phase** — the plan that consumed it (the lgpio chip-by-label resolver, PLAT-12) is deferred.
  Capture it anyway for the future Pi-5/RP1 phase: `gpiodetect` and `gpioinfo | head -20`. Expect
  `gpiochip0 [pinctrl-bcm2711] (58 lines)` on a Pi 4 — note CONTEXT §5 said `pinctrl-bcm2835`, which
  is the Pi 2/3/Zero label. Record what the board actually reports and label it "for the deferred
  Pi-5 phase", so nobody in this phase goes looking for the consumer.
- **`NetworkManager-wait-online`** is enabled by default on Bookworm, so `network-online.target` is
  meaningful. On a network-free boot it times out after a couple of minutes rather than hanging
  forever. If first boot is slow, check this before assuming a unit ordering bug.
</expected_friction>
