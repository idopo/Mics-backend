<objective>
Make the per-electrode trackers visible where they are used.

`check_for_detectors` creates `LICKER0…LICKER3` at task start from `device_name` × `num_detectors`
(TRIGA-12). Nothing outside the Pi knows they exist: `grep -rn "num_detectors|device_name"
api/ web_ui/react-src/src` returns **zero hits**. The consequence in the editor is not "no
autocomplete" — it is *impossible input*: `ConditionBuilder.tsx:64-67` builds its option list from
semantic hardware + module names + toolkit flags and renders a closed `<select>` (lines 79-87)
whenever that list is non-empty, so `LICKER0` cannot be picked **or typed**.

User direction, 2026-07-27: *"I want to be able to have the LICKER{pin} tracker derived from the MPR
num of detectors within phase 24 so I can add to the trigger tracker LICKER{num}.set(level) — make
sure it is visible in the GUI as well."*

The Pi already knows the answer at HANDSHAKE time, because `prefs.HARDWARE` carries `device_name`
and `num_detectors`. So: derive on the Pi, ship it in the payload that already carries `flags` and
`semantic_hardware`, store it on the toolkit row, and let the editor read it like any other toolkit
metadata. No new per-pilot plumbing, no new source of truth for the key format.

Output: `LICKER0…LICKER3` selectable in transition conditions and assemblable in the `view` action's
key template, plus declared variables selectable as condition operands so the guard in the canonical
payload is clickable too.
</objective>

<scope_boundary>
**This plan covers prefs-declared hardware only, and that is deliberate.** HANDSHAKE runs at pilot
startup and reads `prefs.HARDWARE`. A detector declared through the backend hardware-module registry
gets its config merged into prefs only at task start (`mics_task._merge_prefs_hardware`), long after
HANDSHAKE — so its keys are NOT covered here. That case is Phase 25 (DVK-01/02): the backend already
holds that config in `pilot_hardware_config` and can derive from it directly.

Second known limitation: HANDSHAKE is per-pilot, `task_toolkits` is per-toolkit, so with two pilots
running the same toolkit with different `num_detectors` the **last handshake wins**. Acceptable for
one rig; surfacing the disagreement and resolving per pilot is Phase 25 (DVK-02/DVK-06).

Both limitations MUST be written into the SUMMARY. They are scoped decisions, not oversights.
</scope_boundary>
